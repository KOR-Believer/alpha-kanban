## 적용 범위

스모크 정의 하나와 실행 기록 여러 개를 Markdown으로 관리하는 작성·해석 계약이다. 원본에는 현재 TC 정의를, 각 회차에는 당시 기준과 결과·관찰·정정을 저장한다. 사람이나 Computer Use / browser use 에이전트가 실제 앱을 조작하며 수행한다. 자동 테스트 성공이나 형식 검사만으로 TC를 통과 처리하지 않는다.

템플릿은 [smoke-template.md](../assets/smoke-template.md), [smoke-run-template.md](../assets/smoke-run-template.md)다. 값과 반복할 TC 블록을 채우고 안내용 플레이스홀더는 제거한다.

스모크 형식 검사는 동봉된 `scripts/check-smoke.mjs`로 수행한다. 브라우저의 스모크 해석과 같은 규칙을 사용한다. `check-ledger.mjs`는 기존 티켓 검사기다. 기존 문서 규약·지원 버전·생성 CLI를 변경하거나 새 `Ledger-Format` 버전을 발급하지 않는다.

## 형식 검사

### 작성·수행 순서

1. 요청된 대상과 범위를 확인한다. 새 TC는 실제 앱의 사전조건·조작·관찰 가능한 기대 결과로 작성한다. 플랜 없이 단독 스모크를 만들어도 된다.
2. 새 파일마다 `document-context.mjs new`의 별도 결과와 해당 템플릿을 사용하고 `check-new`로 헤더를 확인한다. 회차는 현재 원본의 선택한 ACTIVE TC와 공통 조건을 그대로 보존하며 모든 결과를 NOT_RUN으로 시작한다. 브라우저의 **새 회차**로 생성한 파일도 같은 계약을 따른다.
3. 원본과 새 회차를 명시해 아래 검사기에 `--new-run`을 붙인다. 기존 결과가 있는 회차는 이 옵션의 입력에서 뺀다. 검사 후 실제 앱 조작을 시작하며, 이미 있는 정상 회차를 이어가는 경우 먼저 최신 결과와 사용자 정정을 읽는다.
4. 각 TC를 실제로 시도한 다음 현재 Result와 EXECUTION 기록을 함께 갱신한다. 실제 수행자·방식·관찰 시각을 기록하고, 도구나 권한 때문에 끝내지 못했다면 확인한 범위와 미확인 부분을 남긴다. 자동 테스트 결과만 보고 PASS를 쓰지 않는다. 사용자가 바꾼 결과는 USER_EDIT로 보존하며 재검증한 것으로 바꾸지 않는다.
5. 편집 직전 파일을 다시 읽어 다른 수정이 없는지 확인하고 해당 회차·TC만 갱신한다. 예전 기록과 당시 기준을 덮어쓰지 않는다. 저장 후 원본과 회차를 `--new-run` 없이 검사한다. 검사가 실패하면 임의로 제목·ID·과거 결과를 고쳐 통과시키지 말고 원인을 확인한다.
6. 종료를 요청받았으면 남은 미수행과 이유를 포함해 회차를 닫는다. 새 빌드·환경의 재검증은 새 회차로 기록한다. 보고에는 실제 수행 결과, 사용자 정정, 자동 검사 결과와 미확인을 구분한다.

### 명령

스킬의 Node.js 실행 환경에서 검사할 파일을 직접 지정한다. 파일을 만들거나 수정하지 않는다.

```sh
node <skill-directory>/scripts/check-smoke.mjs --json --project . docs/01_notes_smoke.md docs/02_notes_smoke_run.md
```

- `--project`는 지정한 파일들의 프로젝트 루트이며 생략하면 현재 디렉터리다. 다른 폴더·프로젝트를 자동 탐색하지 않는다. 원본과 여러 회차를 함께 지정하면 그 입력 안에서 UUID 연결·중복을 확인한다. 일반 Markdown도 함께 지정할 수 있지만 UUID 충돌 검사에만 참여한다.
- 원본을 입력하지 않아 `orphan`이 나와도 디스크에서 원본이 삭제됐다는 뜻은 아니다. 해당 입력에 원본이 없다는 뜻이며 회차의 당시 기준은 계속 읽을 수 있다.
- 새 회차를 작성한 직후에는 그 파일에 `--new-run`을 추가해 OPEN·NOT_RUN·빈 기록 여부도 확인한다. 결과가 있는 기존 회차에는 이 옵션을 붙이지 않는다.
- 종료 코드는 정상 구조 `0`, 형식·연결 오류 `1`, 인수·읽기 오류 `2`다. JSON에는 원문 범위가 포함된 진단과 파일별 결과·연결 정보가 있다. 알 수 없는 결과를 미실행으로 바꾸거나 이력을 자동 교정하지 않는다.
- 검사 통과는 문서 구조의 확인이다. 앱 조작이나 TC 결과의 진위를 증명하지 않는다.

## 파일과 식별

| 대상 | 규칙 |
| --- | --- |
| 스모크 정의 | 정확한 접미사 `_smoke.md` |
| 실행 기록 | 정확한 접미사 `_smoke_run.md`; 더 긴 접미사를 먼저 판정 |
| 문서 제목 | 첫 H1 본문. YAML title이나 별도 제목 필드는 없음 |
| 문서 ID | 파일마다 별도 UUID v4인 `Document-ID`; 기존 문서 헤더 규칙 재사용 |
| 원본 연결 | 실행 헤더의 `Smoke-Document-ID`; 같은 연결 프로젝트 안에서 해석 |
| TC ID | `TC-001`, `INT-001`처럼 `[A-Z][A-Z0-9]*-[0-9]{3,}`. 원본 문서 ID와 TC ID의 조합으로 식별 |
| 회차 ID | 실행 파일 자체의 Document-ID. 이름·번호·경로와 독립 |
| 회차 번호 | 양의 정수 `Run`; 같은 원본의 알려진 회차 중 최대 번호 다음 값. 삭제한 번호를 채우려고 재번호화하지 않음 |
| 기록 번호 | 각 회차의 각 TC 안에서 `LOG-001`부터 증가. 다른 TC·회차와 공유하는 ID가 아님 |

파일 앞의 문서 번호는 기존 폴더별 규약을 따르며 회차 번호와 별개다. 같은 묶음에서는 기존 슬러그를 유지한다. 예를 들면 다음처럼 회차도 별도 문서 번호를 받는다.

```text
01_notes_plan.md
02_notes_tickets.md
03_notes_inventory.md
04_notes_smoke.md
05_notes_smoke_run.md  # Run: 1
06_notes_smoke_run.md  # Run: 2
```

플랜·티켓·인벤토리는 필수가 아니다. 실행 문서의 파일명이 다르거나 원본과 폴더가 달라도 UUID 연결을 사용한다. 기존 문서 묶음 규칙을 바꾸지 않으며, 회차를 다른 스모크에 파일명만으로 끼워 넣지 않는다. 브라우저의 `d_` ID는 URL·핸들 식별용이고 문서 UUID 자리에 쓰지 않는다.

같은 프로젝트에서 같은 문서 UUID가 두 파일에 있으면 임의로 하나를 선택하지 않는다. 다른 프로젝트의 같은 UUID는 합치지 않는다. 회차 번호가 겹쳐도 UUID가 다르면 별도 회차로 읽고 중복 번호를 알린다. 번호 중복만으로 두 회차를 합치거나 개별 결과 편집을 막지는 않는다.

## 헤더와 소유자

첫 H1 아래에서 필드와 빈 줄이 이어지는 헤더를 사용한다. `Owner`와 `Document-ID`는 기존 공통 헤더 파서와 같은 경계·철자·검증을 따른다. 본문이나 코드 예제의 같은 이름을 메타데이터로 읽지 않는다.

새 실제 문서마다 `document-context.mjs new`를 별도로 실행해 UUID와 위치·선택적 Owner를 얻고, 작성 후 `check-new`로 헤더를 확인한다. 템플릿 파일 자체에는 고정 UUID를 넣지 않는다. 기본 사용에서는 Owner 줄을 제거하며 `.ak.user`를 요구하지 않는다. 소유자 폴더를 선택했다면 기존 경로 소유자 규칙을 따른다.

Owner는 문서 소유자다. 수행자·수정자·마지막 저장자라고 추정하지 않는다. 웹에서 새 회차를 만들 때는 원본 스모크와 같은 허용된 폴더를 기본 대상으로 삼고, 새 파일의 확인된 경로 소유권만 사용한다. 외부 작성자가 다른 허용된 위치에 회차를 만드는 경우에도 원본 연결은 UUID로 유지한다.

새 문서는 기본적으로 `Ledger-Format`을 넣지 않는다. 기존 선언이 있으면 공통 호환 보호를 적용하며, 이 계약이 새 버전 지원을 선언하는 것으로 해석하지 않는다. 기존 ID 없는 문서는 읽을 수 있고 열람만으로 ID·Owner를 추가하지 않는다. 정확한 원본 ID가 없으면 회차 자동 생성·연결은 추측하지 않는다.

## 스모크 정의

문서 헤더 뒤에 `## 메모`, `## Test Cases`를 순서대로 한 번씩 둔다. 메모에는 목적·공통 사전조건·데이터·주의사항을 자유롭게 작성한다. `Test Cases`에는 한 개 이상의 TC를 문서 순서대로 둔다.

각 TC는 `### TC-001. 제목`으로 시작한다. 제목은 한 줄이며 그 다음 필드가 첫 하위 섹션 전까지 이어진다.

| 필드 | 필수 여부와 의미 |
| --- | --- |
| `Revision` | 필수. 1부터 시작하는 양의 정수 |
| `Lifecycle` | 필수. `ACTIVE` 또는 `RETIRED` |
| `Summary` | 필수. 표에 보여 줄 한 줄 요약. 판정 기준을 대체하지 않음 |
| `Change reason` | 필수. 현재 개정의 이유. 최초에는 `최초 정의` |
| `Retired at` | RETIRED에서 필수. 폐기 시각 |
| `Retirement reason` | RETIRED에서 필수. 폐기 이유 |

이어 `#### 사전조건`, `#### 수행 절차`, `#### 기대 결과`를 한 번씩 순서대로 둔다. 사전조건이 없으면 `- 없음`을 사용한다. 절차는 실제 앱 조작을 순서 있는 목록으로 작성하고, 기대 결과는 관찰 가능한 기준을 작성한다. 세 본문은 표·목록·링크·코드 등을 포함할 수 있다. 원본 TC에는 `Result`나 수행 기록을 두지 않는다.

의미가 달라지는 사전조건·절차·기대 결과의 변경은 Revision을 올리고 Change reason을 바꾼다. 오타·띄어쓰기·동일 의미의 표현 교정만으로는 올리지 않는다. 제목·요약을 고쳤더라도 실제 검증 범위가 달라졌다면 개정한다. 비교 시 내용 차이도 확인하므로 같은 개정 번호라는 이유만으로 같은 기준이라고 단정하지 않는다.

폐기할 때 당시 제목·요약·사전조건·절차·기대 결과를 남기고 Lifecycle과 폐기 정보를 바꾼다. 폐기만으로 Revision을 올리거나 ID를 다른 테스트에 재사용하지 않는다. 되살릴 때도 새 TC에 폐기 ID를 재할당하지 않는다. 원본은 현재 정의를 관리하고, 이미 실행한 옛 정의는 회차가 보존한다. 원본 안에 모든 과거 정의를 복제하는 별도 버전 저장소를 만들지 않는다.

## 실행 헤더와 회차 상태

실행 문서 H1은 회차 이름이다. 예를 들어 `# 최초 검증`과 `Run: 1`로 `1차 · 최초 검증` 탭을 표시한다. 다음 필드를 문서 헤더에 둔다.

| 필드 | 필수 여부와 의미 |
| --- | --- |
| `Smoke-Document-ID` | 필수. 원본 스모크의 UUID v4 |
| `Smoke-Title` | 필수. 생성 당시 원본 H1 제목. 원본이 없어도 이름을 읽기 위한 보존값이며 연결 키가 아님 |
| `Smoke-Path` | 필수. 생성 당시 원본 파일의 프로젝트 상대 경로. 스냅샷 링크의 기준이며 연결 키가 아님 |
| `Run` | 필수. 회차 표시 번호 |
| `Run-State` | 필수. `OPEN` 또는 `CLOSED` |
| `Target` | 필수. 실제 앱·빌드 또는 테스트 대상을 식별하는 값. 버전을 모르면 확인하지 못한 부분을 명시하고 지어내지 않음 |
| `Environment` | 필수. 브라우저·OS·계정/권한 등 판단에 필요한 환경. 긴 설명은 메모에 추가 |
| `Created at` | 필수. 회차 생성 시각. 수행 완료 시각이 아님 |
| `Closed at` | CLOSED일 때 필수, OPEN일 때 없음. 명시적으로 종료한 시각 |
| `Close reason` | CLOSED일 때 필수, OPEN일 때 없음. 종료 이유. 미실행이 남으면 무엇을 남기고 왜 끝내는지 기재 |

시각은 타임존을 포함한 RFC 3339 문자열을 사용한다. `2026-11-10T14:20:00+09:00` 또는 UTC의 `Z` 표기가 가능하다. 실제 기록에 근거한 시각만 쓰며, 템플릿 예시 시각을 복사해 실제 수행 시각으로 주장하지 않는다.

OPEN은 결과가 모두 기록돼도 자동으로 CLOSED가 되지 않는다. CLOSED는 실패·진행 불가·미실행이 있어도 가능하고, 종료할 때 결과를 바꾸지 않는다. 전체 통과는 한 개 이상의 TC가 있고 모든 Result가 PASS인 경우에만 계산한다. 기록 수·결과별 수·미실행 수는 계산값이며 별도 수동 집계 필드를 만들지 않는다. `완료` 한 단어로 전체 통과와 종료를 함께 표현하지 않는다.

종료 후 사용자 정정은 Closed at·Close reason을 다시 쓰거나 회차를 재개하지 않는다. 원래 종료 기록과 그 이후 정정 시각을 각각 남기며 현재 결과 집계만 갱신한다. 새 빌드나 다른 환경을 수행하려면 새 회차를 만든다.

## 당시 기준 보존과 링크

실행 헤더 뒤에 `## 메모`, `## 실행 당시 공통 조건`, `## Test Cases`를 순서대로 둔다.

- 메모는 이번 회차의 자유 Markdown이다. 목적·진행·중단·특이사항을 적고 결과는 여기서 추정하지 않는다.
- 실행 당시 공통 조건에는 생성 당시 원본 `## 메모`의 본문 전체를 저장한다. 필요한 조건을 LLM이 요약하면서 누락하지 않게 한다.
- Test Cases에는 선택한 ACTIVE TC의 제목·Revision·Lifecycle·Summary·Change reason 및 세 기준 본문을 그대로 보존한다. 생성 뒤 원본을 고쳐도 이 내용을 갱신하지 않는다.
- 각 보존 TC의 메타데이터에 `Result: NOT_RUN`을 추가하고, 기대 결과 다음에 빈 `#### 기록` 섹션을 둔다. 새 회차는 한 개 이상의 선택 TC를 포함하며 이전 회차의 결과·수행 기록을 가져오지 않는다.
- 선택하지 않은 TC는 실행 문서에 없는 항목이다. 포함했다가 의도적으로 수행 대상에서 제외하는 SKIPPED와 다르다.

공통 메모 수정도 과거 회차의 보존값에 전파하지 않는다. 공통 조건은 자유 Markdown이므로 의미 변경을 자동 판정하는 별도 번호를 만들지 않고, 비교할 때 두 회차의 보존된 본문 차이를 함께 보여 준다.

Smoke-Path는 `/` 구분자의 프로젝트 상대 파일 경로다. 절대 경로·드라이브 문자·상위 이탈 `..`·역슬래시를 허용하지 않는다. 스냅샷의 공통 조건·TC 정의 안 상대 링크는 이 경로의 부모를 기준으로, 회차 메모·실행 증거 안 상대 링크는 실행 파일의 현재 부모를 기준으로 해석한다. 원본 제목·경로를 이용해 UUID를 대신 추정하지 않는다. 링크의 라벨·목적지를 복사하면서 전역 치환하지 않는다.

텍스트 기준은 실행 문서에 남지만 링크 대상 파일이나 이미지까지 복제하지는 않는다. 원본·첨부가 없거나 권한 밖이면 기존 읽기·로컬 링크 동작으로 처리하고 당시 기준 본문 자체는 계속 표시한다. 원본 이동 후에도 과거 Smoke-Path를 자동으로 현재 경로로 바꾸지 않는다.

## 결과와 관찰·정정 기록

| Result | 뜻 |
| --- | --- |
| `NOT_RUN` | 아직 수행하지 않음 |
| `PASS` | 해당 기준으로 실제 조작·관찰을 마쳤거나 명시적인 사용자 정정으로 현재 결과가 통과임 |
| `FAIL` | 실제 관찰이 기대와 다름 |
| `BLOCKED` | 권한·환경·도구 등으로 필요한 확인을 마치지 못함. 미확인 부분과 사유를 남김 |
| `SKIPPED` | 이번 회차에 포함한 TC를 의도적으로 제외함. 범위 결정의 이유를 남김 |

Result는 현재 값이고 집계의 기준이다. 자유 메모나 로그 문장으로 추정하지 않는다. 사용자 정정으로 PASS가 됐다면 그 출처를 함께 표시하며 에이전트가 재검증한 것으로 보고하지 않는다. 코드 작성·빌드·자동 테스트 통과만으로 EXECUTION의 PASS를 남길 수 없다. 제외는 통과가 아니고, 수행 불가를 숨기는 대체 상태로 쓰지 않는다.

`#### 기록` 아래에 `##### LOG-001` 단위로 추가한다. 각 기록은 변경 후 표시할 TC 메모·증거의 전체 본문을 갖는다. 기존 기록을 수정·삭제하는 대신 새 기록을 붙여, 표에는 마지막 기록의 메모·증거를 표시하고 상세에서는 앞선 관찰도 읽게 한다. 새 회차의 빈 기록은 메모·증거가 없다는 뜻이다. 이것은 작성·저장 규칙이며 외부 편집까지 막는 변조 방지 장치는 아니다.

| 필드/섹션 | 규칙 |
| --- | --- |
| `Kind` | 필수. EXECUTION, USER_EDIT, NOTE 중 하나 |
| `At` | 필수. 실제 수행 관찰·사용자 정정·메모 기록에 해당하는 시각. 기록 종류별로 구분해 표시 |
| `Actor` | 알 때만 기재. 실제 수행자 또는 수정자 이름/ID. 문서 Owner에서 채우지 않음; 없으면 수행자 미기록 또는 기본 수정 표시 |
| `Method` | EXECUTION에서 필수. HUMAN, COMPUTER_USE, BROWSER_USE. 다른 종류에서는 없음 |
| `From`, `To` | 필수. 변경 전후 Result 값. 최초 From은 NOT_RUN, 이후 From은 직전 기록의 To |
| `###### 메모` | 필수 섹션. 변경 후 TC 메모 전체. 실제 수행 기록에는 관찰·미확인 부분을 기재 |
| `###### 증거` | 필수 섹션. 변경 후 증거·참고 전체. 비어 있어도 되며 캡처·링크를 지어내지 않음 |
| `###### 수정 사유` | USER_EDIT에서 필수인 비어 있지 않은 Markdown. 다른 종류에서는 없음 |

EXECUTION은 실제 수행·시도한 관찰이며 To는 PASS, FAIL, BLOCKED 중 하나다. 비어 있지 않은 메모가 필요하고 같은 빌드·환경에서 다시 수행한 경우에도 앞선 기록을 남긴다. USER_EDIT는 명시적인 사용자 결과 변경/정정이며 모든 Result 값으로 바꿀 수 있다. NOTE는 결과를 바꾸지 않는 메모·증거 변경이므로 From과 To가 같고, 메모를 비우는 경우에도 앞선 내용이 이전 기록에 남는다. 결과가 같더라도 관찰이나 정정 사유를 추가할 수 있다.

현재 Result는 마지막 기록의 To와 같아야 한다. 기록이 없으면 Result는 NOT_RUN이다. 각 LOG 번호는 해당 TC 안에서 중복되지 않고 증가해야 한다. 타임스탬프로 다시 정렬하거나 같은 시각의 기록을 합치지 않고 파일에 적힌 추가 순서를 보존한다.

사용자 수정의 표시는 기본 `사용자 수정`이다. 소유자 구분 환경에서 실제 수정자의 유효한 `@name`이 Actor에 기록된 경우 `@name 수정`으로 표시한다. 사용자 ID가 없거나 일반 이름이면 기본 표시를 쓰고 상세에 기록된 Actor를 보여 줄 수 있다. `.ak.user` 존재, 폴더 이름, 문서 Owner, 현재 브라우저로 읽고 있다는 사실은 수정자 증거가 아니다.

단순한 결과 변경은 이전 메모·증거를 유지하면서 수정 사유만 추가할 수 있다. 동시에 관찰·증거를 고쳤다면 새 본문 전체를 이번 기록에 남긴다. 현재 Result 변경과 새 기록 추가는 한 번의 보호된 파일 저장으로 처리한다. USER_EDIT와 NOTE를 실제 앱 재수행으로 집계하지 않는다.

실제 수행 기록의 작성 형태:

```md
##### LOG-001

Kind: EXECUTION

At: {{실제 관찰 시각}}

Actor: {{확인된 수행자; 모르면 줄 제거}}

Method: BROWSER_USE

From: NOT_RUN

To: FAIL

###### 메모

{{실제로 한 조작, 관찰한 결과, 기대와 다른 점}}

###### 증거

{{있는 증거·참고만 작성; 없으면 비워 둠}}
```

사용자 정정의 작성 형태:

```md
##### LOG-002

Kind: USER_EDIT

At: {{실제 정정 시각}}

Actor: {{확인된 수정자; 모르면 줄 제거}}

From: FAIL

To: PASS

###### 메모

{{변경 후 TC 메모 전체; 변경하지 않았다면 이전 메모 유지}}

###### 증거

{{변경 후 증거 전체; 변경하지 않았다면 이전 증거 유지}}

###### 수정 사유

{{사용자가 결과를 정정한 이유}}
```

자동 테스트 결과는 증거·참고에 적을 수 있지만 EXECUTION을 만들어 내거나 Method를 대신하지 않는다. 수행자 요약은 실제 EXECUTION 기록의 Actor·Method에서 가져온다. 기록이 없으면 미실행이며, 여러 수행자·방식이면 구분해 보여 준다. 최종 사용자 수정의 Actor를 앞선 실행의 수행자로 대입하지 않는다.

## Markdown 경계와 저장

- 구조는 인용·목록·들여쓴 코드·코드 펜스·HTML 주석 안에 있지 않은 실제 ATX 제목과 각 영역 시작부의 단일행 필드로 판정한다. 앞 공백이 없는 정규 형태로 새 문서를 쓴다. 코드에 적힌 TC 제목이나 Result는 예제이며 구조가 아니다.
- 루트에서 예약된 제목은 `## 메모`, `## 실행 당시 공통 조건`, `## Test Cases`다. TC 시작은 `### <TC ID>. <제목>`, 기록 시작은 `##### LOG-<숫자>`다. 이 예약 구문을 본문 예시로 쓸 때는 인용·코드 펜스 또는 이스케이프를 사용한다.
- TC와 기록의 스칼라 필드는 각각 첫 하위 본문 섹션 전까지만 읽는다. 관찰에 적힌 `Result: PASS`는 현재 결과 필드가 아니다. 필드·예약 섹션 중복이나 잘못된 TC/LOG 경계는 임의로 합치지 않는다.
- 상단 메모와 실행 당시 공통 조건은 다음 루트 예약 섹션 전까지다. TC 기준 본문은 다음 기준 섹션, 실행 문서의 `#### 기록`, 다음 TC 또는 파일 끝 전까지다. 기록 메모·증거·수정 사유는 다음 `###### 메모`·`###### 증거`·`###### 수정 사유`, 다음 LOG·TC 또는 파일 끝 전까지다. 각 경계 제목 자체는 앞선 본문에 포함하지 않는다.
- 기준 섹션은 TC 아래에서만, LOG와 기록 본문 섹션은 해당 TC의 `#### 기록` 아래에서만 해석한다. 허용된 위치 밖에 예약 구조가 나오면 일반 메모로 삼키거나 다른 TC에 붙이지 않고 구조 오류로 남긴다. 일반 Markdown 제목·표·목록·코드·링크는 각 본문으로 보존하며, 예약 구문과 겹치지 않는 제목은 메모 안에서 사용할 수 있다.
- 동일 범위에 같은 필드는 한 번만 둔다. 필드 철자와 enum 값은 대소문자를 구분하며 번역하지 않는다. 표시 언어만 바꾼다. 시트 행 순서는 원문 순서를 사용한다.
- 새 문서는 UTF-8과 LF, 필드 사이 빈 줄을 사용한다. 기존 파일의 BOM·LF/CRLF·끝 개행과 수정 대상 밖의 바이트는 보존한다. 혼합 줄바꿈 등 안전하지 않은 쓰기는 기존 보호 규칙으로 처리한다.
- 알 수 없는 필드·본문은 읽기에서 버리지 않는다. 쓰기에 필요한 범위를 확정할 수 없으면 해당 작업만 거절하고 원문과 읽을 수 있는 부분을 유지한다. 현재 앱의 다른 문서 렌더링·티켓 진행률을 막지 않는다.

## 비교와 검증 규칙

두 회차의 Smoke-Document-ID가 같을 때 TC ID로 행을 맞춘다. 같은 TC라도 각 회차의 제목·정의·Revision·결과·기록을 각각 사용한다. 한쪽에 없는 TC는 `회차에 없음`으로 표시하며 어떤 Result 값도 부여하지 않는다. 원본에서 지금 RETIRED라는 정보는 별도 표시이고 과거의 ACTIVE·PASS를 바꾸지 않는다. 현재 원본이 없으면 현재 유효/폐기 여부를 추측하지 않는다.

Revision뿐 아니라 저장된 기준과 공통 조건도 비교한다. 같은 Revision인데 기준 텍스트가 다르면 내용 차이를 알리고 자동으로 동일 기준이라 표시하지 않는다. 단순 문구 교정인지 의미 변경인지는 프로그램이 확정하지 않는다. 기준 텍스트 비교에서는 LF/CRLF 차이만 정규화하고 나머지 내용을 버리지 않는다. 차이만 보기에는 결과·개정·정의·공통 조건·메모·증거 차이와 한쪽 누락을 포함한다.

| 조건 | 작성·검증 판단 | 읽기와 제한 |
| --- | --- | --- |
| 원본 없이 정상 실행 기록만 있음 | 연결 안내가 필요하지만 자체 기준·기록은 유효 | 보존된 시트·비교 읽기와 안전한 개별 결과/메모 정정 가능; 새 원본 기반 회차 생성은 불가 |
| 같은 프로젝트의 문서 UUID 중복 | 연결 대상 모호 | 임의 선택·합치기 금지; 각 파일 원문과 읽을 수 있는 기록 유지 |
| TC ID·필드·LOG 번호 중복 | 해당 범위 구조 오류 | 중복 대상을 임의로 골라 쓰지 않음 |
| UUID 누락/무효, 원본 ID 무효 | 새 문서 규약 오류 | 읽기 유지; 생성·관계 기반 쓰기에서 추측 금지 |
| 원본에 Result/실행 기록 또는 새 회차에 이전 결과가 들어감 | 정의/생성 규칙 위반 | 기존 문서를 열며 자동 삭제·초기화하지 않음 |
| 알 수 없는 Lifecycle·Run-State·Result·Kind·Method | 값 오류 | 원문 값을 보존하고 미실행·실패·통과로 치환하지 않음; 영향을 받는 쓰기 제한 |
| ACTIVE인데 폐기 필드가 있거나 RETIRED인데 폐기 정보가 없음 | 상태·필드 불일치 | 현재 값을 자동 보정하지 않음 |
| OPEN에 종료 정보 또는 CLOSED에 종료 시각/사유가 없음 | 회차 상태 불일치 | 전체 통과나 종료로 추정하지 않음 |
| 로그 From/To 연결 불일치, 마지막 To와 Result 불일치 | 현재 결과와 이력 불일치 | 어느 쪽을 맞는 값으로 고를지 자동 결정하지 않음 |
| EXECUTION에 Method/관찰이 없거나 NOTE가 결과를 바꿈 | 기록 종류와 내용 불일치 | 해당 관찰을 검증 증거로 확정하지 않음 |
| USER_EDIT에 수정 사유가 없음 | 정정 근거 누락 | 통과 증거를 대신 생성하지 않음 |
| 같은 Revision에서 기준 내용이 다름 | 내용 차이 알림, 의미 판단은 보류 | 양쪽 기준을 보존해 비교 |

유효하지 않은 문서 때문에 프로젝트 전체·다른 시트·다른 문서의 보드를 숨기지 않는다. 검사기는 구조와 관계를 확인할 뿐 앱을 조작했는지, 관찰 내용이 사실인지, 코딩이 완료됐는지를 증명하지 않는다.

## 확인·결정이 필요한 사항

- 없음
