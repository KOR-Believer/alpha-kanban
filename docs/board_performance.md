# 대용량 보드 로딩·검색 검증

검증일: 2026-11-04

## 동작

- 전체보드는 연결된 프로젝트의 티켓, 프로젝트보드는 현재 열린 티켓 문서의 번호·제목·본문을 검색한다. 기존 프로젝트·소유자·완료 필터는 검색 결과와 함께 적용한다.
- 검색 데이터는 원문의 각 티켓 범위에서 만든다. 렌더러가 생략하는 추가 Markdown·여러 줄 지시도 포함하지만 문서 공통 안내나 다른 티켓을 섞지 않는다. 검색용 데이터는 문서 필드로 저장하지 않는다.
- 각 상태 열에 80개 이상이면 화면 주변 카드만 표시한다. 전체 데이터·개수·정렬은 유지하며, 스크롤에 따라 데이터를 추가로 읽는 페이지네이션은 사용하지 않는다. 브라우저의 페이지 내 찾기는 표시 중인 카드만 찾을 수 있으므로 전체 티켓은 보드 검색창으로 찾는다.
- 상태 헤더와 보드 전체 스크롤을 유지한다. 드래그 중이거나 키보드 포커스가 있는 카드는 유지하고, 방향키·Home·End·Tab으로 화면 밖 카드에 접근한다. 검색 조건이 바뀌면 보드의 세로 스크롤을 위로 돌린다.
- 같은 파일의 분석 결과를 재사용한다. 파일 확인은 최대 6개로 제한해 병렬화하며, 파일 ID 등록은 기존 registry 잠금 안에서 묶어 저장한다. 전체보드 부분 결과는 첫 결과를 먼저 표시한 뒤 갱신을 묶는다.
- 캐시는 표시용이다. 실제 저장은 기존의 파일 해시·수정 시각·잠금·복구 사본·저장 후 확인을 사용한다.

## 측정 조건

macOS의 기존 Chrome, 동일 창·기본 화면 크기에서 수정 전 보존 빌드와 개선 빌드를 비교했다. 서로 다른 새 로컬 origin에 동일한 실제 스모크 폴더를 연결했다. 운영 문서와 기존 사용자 연결은 사용하지 않았다.

- Markdown 503개: 티켓 문서 502개 × 20개 = **10,040개 티켓**, 일반 Markdown 1개.
- 프로젝트 첫 표시: 폴더 선택·권한 승인 후 프로젝트 화면에 진입해서 처음 20개 티켓이 표시될 때까지. 문서 목록의 최초 발견·본문 읽기를 포함한다.
- 전체보드 전환: 위 프로젝트의 문서 목록을 읽은 다음 전체보드를 눌러 모든 티켓 개수가 표시될 때까지. 본문 캐시가 있는 상태의 화면 전환이며 앱을 새로 연 뒤의 전체 파일 읽기 시간과 구분한다.
- 동일한 외부 측정 코드로 약 200ms 간격의 카드/개수 확인, animation frame 간격, 50ms 초과 긴 작업을 기록했다. 아래 수치는 조건을 맞춘 1회 비교로 장비 전체의 일반 성능 보장은 아니다. 앞선 별도 비교에서도 전체보드는 약 65초에서 0.2초로 줄었다.

| 항목 | 수정 전 | 개선 후 |
| --- | ---: | ---: |
| 프로젝트 첫 카드 표시 | 6,799ms | 6,157ms |
| 전체보드 첫 카드 표시 | 566ms | 198ms |
| 전체보드 전체 개수 표시 | 66,400ms | 198ms |
| 전체보드 로딩 중 최대 프레임 간격 | 867ms | 18ms |
| 전체보드 로딩 중 50ms 초과 작업 | 189개 | 0개 |
| 전체보드 카드 DOM 수 | 10,040개 | 12개 |

최초 폴더 읽기 개선은 작다. 프로젝트 첫 표시의 최대 프레임 간격도 50ms에서 83ms로 변동했고, 두 경우 모두 50ms 초과 작업은 관찰되지 않았다. 이번 큰 차이는 누적 카드 전체를 반복 표시하던 전체보드에서 발생했다. 처음 파일을 읽는 시간까지 0.2초가 된 것으로 해석하지 않는다.

## 동작·보존 검증

- 별도 500개 티켓 문서의 마지막 티켓에만 있는 본문 문장으로 프로젝트보드와 전체보드에서 검색했다. 화면에 없던 티켓 1개를 찾고 상세의 일치 문장 강조를 확인했다.
- 프로젝트보드에서 500번째, 전체보드에서 10,540번째 카드까지 End 키로 이동했다. 가상화 후에도 상태별 전체 개수와 키보드 포커스가 유지됐다.
- 두 보드에서 드래그 후 상태 변경 확인창이 열리는 것을 확인하고 취소했다. 상세 표시 방식 변경 중 입력 초안도 유지됐다.
- 좁은 다크 화면에서 검색창·전체 개수·가로 스크롤·가상 카드 탐색을 확인하고 기본 화면 크기로 복원했다.
- 검색·확인 취소만 수행한 기존 503개 Markdown의 모든 해시가 유지됐다. 원문 렌더링과 실제 티켓 본문은 변경하지 않았다.
- 웹 회귀 590개, 공용 파서/문서 회귀 205개, 타입 검사와 제품 빌드를 통과했다. 검색 경계·인덱스 갱신·필터 교집합·부분 로딩/취소·카드 수 제한·드래그 카드 유지·키보드 탐색·크기·수정 시각이 같은 외부 수정 감지·ID 등록 묶음 실패 시 원상 보존을 포함한다.

이번 기록은 Mac의 로컬 제품 빌드 검증이다. 공개 배포는 수행하지 않았다.
