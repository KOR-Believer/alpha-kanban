# 대용량 보드 로딩·검색 검증

검증일: 2026-11-04

## AKD-20 적용 당시의 동작

- 전체보드는 연결된 프로젝트의 티켓, 프로젝트보드는 현재 열린 티켓 문서의 번호·제목·본문을 검색한다. 기존 프로젝트·소유자·완료 필터는 검색 결과와 함께 적용한다.
- 검색 데이터는 원문의 각 티켓 범위에서 만든다. 렌더러가 생략하는 추가 Markdown·여러 줄 지시도 포함하지만 문서 공통 안내나 다른 티켓을 섞지 않는다. 검색용 데이터는 문서 필드로 저장하지 않는다.
- 각 상태 열에 80개 이상이면 화면 주변 카드만 표시한다. 전체 데이터·개수·정렬은 유지하며, 스크롤에 따라 데이터를 추가로 읽는 페이지네이션은 사용하지 않는다. 브라우저의 페이지 내 찾기는 표시 중인 카드만 찾을 수 있으므로 전체 티켓은 보드 검색창으로 찾는다.
- 상태 헤더와 보드 전체 스크롤을 유지한다. 드래그 중이거나 키보드 포커스가 있는 카드는 유지하고, 방향키·Home·End·Tab으로 화면 밖 카드에 접근한다. 검색 조건이 바뀌면 보드의 세로 스크롤을 위로 돌린다.
- 같은 파일의 분석 결과를 재사용한다. 파일 확인은 최대 6개로 제한해 병렬화하며, 파일 ID 등록은 기존 registry 잠금 안에서 묶어 저장한다. 전체보드 부분 결과는 첫 결과를 먼저 표시한 뒤 갱신을 묶는다.
- 캐시는 표시용이다. 실제 저장은 기존의 파일 해시·수정 시각·잠금·복구 사본·저장 후 확인을 사용한다.

## 측정 조건

macOS의 기존 Chrome, 동일 창·기본 화면 크기에서 수정 전 보존 빌드와 개선 빌드를 비교했다. 서로 다른 새 로컬 origin에 동일한 실제 스모크 폴더를 연결했다. 운영 문서와 기존 사용자 연결은 사용하지 않았다.

- Markdown 503개: 티켓 문서 502개 × 20개 = **10,040개 티켓**, 일반 Markdown 1개.
- 프로젝트 첫 표시: 폴더 선택·권한 승인 후 프로젝트 화면에 진입해서 처음 20개 티켓이 표시될 때까지. 문서 목록의 최초 발견·본문 읽기를 포함한다.
- 전체보드 전환: 위 프로젝트의 문서 목록을 읽은 다음 전체보드를 눌러 모든 티켓 개수가 표시될 때까지. 본문 캐시가 있는 상태의 화면 전환이며 앱을 새로 연 뒤의 전체 파일 읽기 시간과 구분한다.
- 동일한 외부 측정 코드로 약 200ms 간격의 카드/개수 확인, animation frame 간격, 50ms 초과 긴 작업을 기록했다. 아래 수치는 조건을 맞춘 1회 비교로 장비 전체의 일반 성능 보장은 아니다. 앞선 별도 비교에서도 전체보드는 약 65초에서 0.2초로 줄었다.

| 항목 | 수정 전 | 개선 후 |
| --- | ---: | ---: |
| 프로젝트 첫 카드 표시 | 6,799ms | 6,157ms |
| 전체보드 첫 카드 표시 | 566ms | 198ms |
| 전체보드 전체 개수 표시 | 66,400ms | 198ms |
| 전체보드 로딩 중 최대 프레임 간격 | 867ms | 18ms |
| 전체보드 로딩 중 50ms 초과 작업 | 189개 | 0개 |
| 전체보드 카드 DOM 수 | 10,040개 | 12개 |

최초 폴더 읽기 개선은 작다. 프로젝트 첫 표시의 최대 프레임 간격도 50ms에서 83ms로 변동했고, 두 경우 모두 50ms 초과 작업은 관찰되지 않았다. 이번 큰 차이는 누적 카드 전체를 반복 표시하던 전체보드에서 발생했다. 처음 파일을 읽는 시간까지 0.2초가 된 것으로 해석하지 않는다.

## 동작·보존 검증

- 별도 500개 티켓 문서의 마지막 티켓에만 있는 본문 문장으로 프로젝트보드와 전체보드에서 검색했다. 화면에 없던 티켓 1개를 찾고 상세의 일치 문장 강조를 확인했다.
- 프로젝트보드에서 500번째, 전체보드에서 10,540번째 카드까지 End 키로 이동했다. 가상화 후에도 상태별 전체 개수와 키보드 포커스가 유지됐다.
- 두 보드에서 드래그 후 상태 변경 확인창이 열리는 것을 확인하고 취소했다. 상세 표시 방식 변경 중 입력 초안도 유지됐다.
- 좁은 다크 화면에서 검색창·전체 개수·가로 스크롤·가상 카드 탐색을 확인하고 기본 화면 크기로 복원했다.
- 검색·확인 취소만 수행한 기존 503개 Markdown의 모든 해시가 유지됐다. 원문 렌더링과 실제 티켓 본문은 변경하지 않았다.
- 웹 회귀 590개, 공용 파서/문서 회귀 205개, 타입 검사와 제품 빌드를 통과했다. 검색 경계·인덱스 갱신·필터 교집합·부분 로딩/취소·카드 수 제한·드래그 카드 유지·키보드 탐색·크기·수정 시각이 같은 외부 수정 감지·ID 등록 묶음 실패 시 원상 보존을 포함한다.

이번 기록은 Mac의 로컬 제품 빌드 검증이다. 공개 배포는 수행하지 않았다.

## AKD-21 프로젝트 통합 검색

프로젝트 좌상단 검색은 문서 이름·경로와 티켓·플랜·인벤토리·일반 Markdown의 본문을 함께 찾는다. 기존 묶음과 소유자·문서 표시 필터를 유지하고, 각 결과에 파일 종류·일치 티켓 수·짧은 원문 발췌를 표시한다. 전체보드 검색은 종전처럼 독립적이다.

- 입력 중에는 열린 문서와 상세 초안을 유지한다. 결과를 선택하면 일치한 티켓 보드 또는 공통 Markdown 뷰어의 해당 본문으로 이동한다. 문서 공통 안내는 특정 티켓의 검색 결과에 포함하지 않는다.
- 오른쪽의 적용된 검색어와 `이 문서 전체 보기`로 검색 범위를 확인·해제한다. 전체 보기는 왼쪽 검색을 유지하고, 왼쪽 검색을 지워도 선택 문서는 유지한다. URL에 검색어와 적용 조건을 별도로 두어 뒤로가기·새로고침으로 복원한다.
- 파일을 읽을 때 만든 검색 자료를 16MiB 메모리 캐시와 브라우저의 IndexedDB에서 재사용한다. 검색어가 바뀌어도 폴더를 다시 탐색하거나 본문을 읽지 않는다. 빠진 자료를 준비하는 단계만 파일을 다시 읽을 수 있으며, 실패는 결과 없음과 구분하고 재시도를 제공한다.
- 준비는 최대 4개 작업으로 제한하고, 검색은 약 8ms의 작업 구간 사이에 브라우저에 제어를 돌려준다. 이전 검색이나 해제된 프로젝트의 결과가 늦게 반영되지 않도록 취소한다. 파일 해시·경로·프로젝트가 바뀐 자료는 재사용하지 않는다. 저장 안전장치와 렌더링 규칙은 그대로다.

### 측정 조건과 결과

`node scripts/prepare-project-search-smoke.mjs`로 만든 합성 Markdown 504개·문서 묶음 502개·티켓 10,500개를 사용했다. 기존 Chrome의 서로 다른 로컬 origin에 같은 폴더를 연결했다. 원문 총량은 5,044,602바이트이며, 500개 티켓 문서의 마지막 두 티켓과 플랜·인벤토리·일반 문서에 공통 검색어를 넣었다.

재시작 비교는 같은 500개 티켓 문서를 선택한 등록 프로젝트를 새로고침하고, 문서 목록 전체와 첫 카드가 표시될 때까지 측정했다. 비교 중 탭이 표시 상태를 유지했음을 함께 기록했으며 다른 자동 검증은 실행하지 않았다. 각 빌드 1회 측정이다.

| 항목 | 수정 전 | 통합 검색 적용 후 |
| --- | ---: | ---: |
| 프로젝트 새로고침 후 목록·첫 카드 표시 | 10,421ms | 10,080ms |
| 위 구간의 최대 프레임 간격 | 4,771ms | 4,637ms |
| 위 구간의 본문 읽기 | 506회 | 506회 |
| 준비된 목록에서 첫 본문 검색 | 미지원 | 172ms |
| 검색어 변경·재검색 | 미지원 | 42–48ms |
| 이미 열린 티켓 파일에 검색 결과 적용 | 미지원 | 41ms |
| 검색어 입력 중 파일·본문 읽기 | 해당 없음 | 0회 |

첫 검색의 최대 프레임 간격은 100ms였고, 재검색과 결과 적용은 각각 17ms였다. 추가로 501개 묶음이 일치하는 검색은 195ms, 최대 프레임 간격 150ms였다. 입력마다 파일을 읽는 비용은 없지만, 많은 결과를 한꺼번에 그리는 비용까지 없어진 것은 아니다. 특히 프로젝트 전체를 처음 표시하는 약 10초와 긴 프레임 간격은 전후 모두 남아 있어 이번 변경으로 해결됐다고 보지 않는다.

### 동작·보존 검증

- 실제 Chrome에서 본문에만 있는 문장으로 두 티켓·플랜·인벤토리·일반 문서를 찾고, 일치한 카드만 표시·전체 보기·뒤로가기·문서 본문 위치 강조·새로고침 복원을 확인했다. 430px 영문 다크 화면의 검색 결과와 키보드 선택도 확인했다.
- 합성 일반 문서의 외부 수정을 다음 파일 확인에서 검색에 반영했다. 시험 후 복원한 Markdown 504개 모두 생성 당시 SHA-256과 같았다. 운영 문서는 읽거나 변경하지 않았다.
- 자동 검증은 웹 607개·공용 파서/문서 205개, 타입 검사와 제품 빌드를 통과했다. 캐시 퇴출·저장 실패·외부 변경·이동·삭제·권한/연결 해제·늦게 도착한 검색 결과·검색 취소와 기존 필터·초안·저장 보호를 포함한다. 파일 이동·권한 상실의 검색 회귀는 파일 핸들 대역을 사용한 검증이며 실제 OS 권한 재승인 시험으로 해석하지 않는다.
- 일반·연결 문서는 같은 렌더러를 사용한다. 검색 강조를 해제한 결과가 종전 GFM 구조와 동일하며 원문·문서 메타데이터를 쓰지 않는 것을 확인했다. 공개 배포는 수행하지 않았다.
