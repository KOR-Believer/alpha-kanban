# Alpha Kanban 팀 문서 소유자·이동·형식 마이그레이션 계획

작성일: 2026-10-28
수정일: 2026-10-31

## 목표와 이유

- 개인 작업 기록을 Git으로 공유하면서 동료의 컨텍스트와 현재 agent가 실행할 업무를 구분한다. 회사별 하네스 통합이나 특정 제공자에 종속되지 않는 공개 도구의 규약으로 만든다.
- `docs/@사용자/`에 새 문서를 생성하고 기존 문서도 참조를 유지하며 옮길 수 있게 한다. 문서별 공유 목록을 수동 관리하지 않는다.
- 여러 repo를 참조하는 문서의 로컬 링크를 열 수 없으면 내 폴더를 연결하고 같은 앞 경로의 링크에도 재사용한다. 연결은 브라우저에만 저장하며 원본 Markdown과 agent 설정을 바꾸지 않는다.
- 파일 내부의 지속적인 문서 ID를 처음부터 설계하고 레거시 문서에도 선택적으로 발급한다. 경로 이동과 형식 정리를 별도 수작업 없이 검토·적용할 수 있게 한다.
- 확인된 옛 중복 섹션은 자동 정리하되 과거 수정일이나 완료 증거를 만들어내지 않는다. 자동화는 승인한 변환을 기계적으로 수행한다는 뜻이며, 앱 업데이트나 문서 열람만으로 파일을 바꾸지 않는다.
- 이 문서는 계획이다. 현재 승인 범위는 계획·티켓 작성·수정·커밋이며 구현, 기존 문서 이동·ID 발급·삭제·변환은 포함하지 않는다. 진행은 [티켓](25_alpha_kanban_team_documents_tickets.md)에서 관리한다.

## 영향 범위

- `packages/shared/src/documents.ts`, `packages/shared/src/ticketMarkdown.ts`, `packages/shared/src/index.ts`, `packages/shared/test`: 소유자·문서 메타데이터·참조 변환·형식 판정의 공통 계약.
- `apps/web/src/browser/repository.ts`, `apps/web/src/browser/storage.ts`, `apps/web/src/browser/MarkdownResources.tsx`: 문서 발견·식별·복구·로컬 참조, 미싱 링크의 폴더 연결·IndexedDB 저장·재사용과 파일 작업.
- `apps/web/src/App.tsx`, `apps/web/src/components`, `apps/web/src/i18n/messages.ts`, `apps/web/src/pwa`: 소유자 표시·필터, 이동·마이그레이션 검토, 드래프트·업데이트 보호.
- `skills/implementation-ledger`, `scripts/ticket-md.mjs`: 새 문서 작성과 외부 agent용 동일 변환·검증 절차. 개인 전역 스킬은 제외한다.
- `docs`, `README.md`, `README.en.md`, `CONTRIBUTING.md`, `AGENTS.md`: 구현 후 실제 지원 범위의 규약·사용 안내. 기존 작업 중 파일은 이번 계획 작성에서 수정하지 않는다.

## 확인한 현재 상태

- `docs/21_alpha_kanban_browser_transition_inventory.md`에 따라 브라우저 전용 Markdown 제품을 유지한다. 팀 기능을 이유로 서버·내장 채팅·agent 실행기를 복원하지 않는다.
- `repository.ts`는 하위 디렉터리의 Markdown을 재귀 탐색한다. 문서 목록은 경로 인덱스를 사용하고, 브라우저의 `d_` ID와 파일 핸들은 IndexedDB에 보존한다. 이는 Git으로 전달되는 파일 내부 ID와 다르다.
- 브라우저의 프로젝트 경계는 Git 저장소가 아닌 연결한 폴더다. 하네스 루트를 하나의 프로젝트로 연결하면 그 아래 여러 repo를 포함할 수 있다. 현재 `repository.ts.localResource`는 문서 상대 링크를 해당 프로젝트 안에서만 해석하며 OS 절대경로·file URL·프로젝트 경계 이탈을 거부한다. 중첩된 별도 연결도 기존 연결 경계에 따라 구분하며 프로젝트 간 링크를 자동 재매핑하지 않는다.
- `MarkdownResources.tsx`는 로컬 링크 해석 실패 시 오류만 표시하고 폴더 선택을 제공하지 않는다. 정상 상대 링크의 Markdown은 앱에서 열고 다른 파일은 다운로드한다. 폴더 핸들을 저장하는 기존 IndexedDB 구조는 있지만 원본 앞 경로와 내 폴더를 대응시키는 기록은 없다.
- 현재 파일 핸들이 같은 항목으로 유지되는 이동은 발견 시 연결할 여지가 있지만, 다른 도구의 복사 후 삭제나 다른 PC의 checkout까지 동일성을 보장하는 파일 메타데이터 계약은 없다.
- `ticketMarkdown.ts`는 Status와 Ticket List 및 알려진 티켓 필드를 읽는다. 읽지 않는 본문을 의미 없는 내용으로 판정하지 않는다. `docs/02_alpha_kanban_tickets.md`에는 초기 Progress Board와 템플릿·운영 원칙이 남아 있다.
- 현재 단일 문서 쓰기는 해시/mtime, Web Lock, 복구 preimage, close/readback 확인으로 보호된다. 여러 파일 이동·참조 수정의 원자성을 제공하는 것으로 해석하지 않는다.
- [기존 브라우저 티켓](14_alpha_kanban_browser_local_tickets.md)의 AKL-10은 스킬·문서 형식 버전 계약, AKL-11은 하위 호환 읽기/쓰기와 미지원 형식 보호를 담당하며 현재 TODO다. 새 계획은 이 계약을 재사용하고 명시적으로 요청한 변환 기능을 추가한다.

## 할 일과 선택한 방향

### 1. 사용자 폴더와 실행 범위

- 프로젝트 기준 `docs` 바로 아래의 `@사용자` 디렉터리만 소유자 경계로 해석한다. 하위 문서는 그 소유자를 상속하며 일반 폴더, 더 깊은 `@` 이름, 빈 `@`를 임의로 새 사용자로 해석하지 않는다.
- 사용자 식별자는 프로젝트 안에서 합의한 문자열이다. 인증 계정이나 OS·Git 사용자 이름을 추측해 매칭하지 않는다. 현재 사용자 선택은 프로젝트별 로컬 설정으로 보존하며 선택만으로 파일을 쓰지 않는다.
- 기존 루트 문서와 일반 폴더는 소유자 미지정이다. 개인 폴더로 강제 이동하거나 공용 실행 큐로 취급하지 않는다. 새 업무는 선택한 사용자 폴더에서 생성하고 기존 문서는 원하는 시점에 이동한다.
- 새 문서 번호는 각 `docs/@사용자/`와 그 하위 폴더를 하나의 범위로 삼아 독립적으로 증가시킨다. 그 범위의 기존 Markdown 숫자 접두사 중 최대값에 1을 더하고, 번호가 없으면 `01`부터 시작한다. 다른 사용자 폴더와 소유자 미지정 영역의 번호는 발급 기준에 포함하지 않는다.
- 기존 문서는 이동할 때 번호를 유지한다. 이동·소유자 변경을 이유로 다시 번호를 매기거나 빈 번호를 채우지 않는다. 이동해 온 번호도 이후 신규 번호의 최대값 계산에 포함한다. 번호만 같은 것은 충돌이 아니며 실제 목적지 충돌은 덮어쓰기나 자동 재번호 부여로 회피하지 않는다.
- 문서 번호는 정렬·탐색의 참고값이다. 문서 정체성, 최신 결정, 구현 우선순위나 선행 의존성을 뜻하지 않으며 사용자 간 번호를 시간 순서로 비교하지 않는다. agent는 현재 요청·최신 사용자 지시·티켓 상태·`Depends on`·기준 문서의 내용을 확인해 작업 순서를 판단한다.
- 내 작업·전체 작업·소유자 미지정 필터와 카드/문서의 소유자 표시를 제공한다. 같은 번호·티켓 ID가 다른 사용자에게 있어도 혼동하지 않게 한다. 티켓 식별은 문서 정체성과 티켓 ID를 함께 사용한다.
- 동료 문서 전체를 참조할 수 있지만 그 안의 사용자 지시·미완료 티켓·개인 하네스 규칙은 현재 agent에 대한 명령이 아니다. 실행은 현재 사용자의 명시적 요청 또는 배정 범위로 한정한다. 타 사용자 폴더로 이동할 때는 소유자 표시도 바뀐다는 것을 보여준다.
- 폴더 소유자는 문서의 기본 작업 범위이지 티켓별 강제 접근 권한이나 동시 작업 잠금이 아니다. 명시적 인계는 가능하며, 다른 티켓으로 같은 기능을 동시에 구현하는 문제까지 해결했다고 주장하지 않는다.
- 이번 범위는 개인 소유자 구분과 서로의 컨텍스트 참조로 한정한다. 구체적인 사용처가 정해지지 않은 팀 폴더·팀 소유자 분류·팀용 접두사·공용 업무 배정은 제외한다. `#`, `+`, `@@` 중 어느 것도 채택·예약하지 않는다.

### 2. 파일 내부 ID와 레거시 발급

- 파일 내부의 지속적 ID, 브라우저 로컬 ID, 티켓 ID, 문서 형식 개정, 스킬 개정, 앱 릴리즈는 서로 구분한다. ID는 경로·소유자·제목에서 파생하지 않고 이동·이름 변경 시 유지한다.
- 계획상 기본 후보는 Markdown 파일 맨 위 YAML front matter의 namespaced 메타데이터와 UUID다. 별도 YAML 파일을 생성하지 않으며 YAML에 title 필드를 추가하지 않는다. 정확한 키·스키마·형식 번호는 AKL-10과 AKD-01에서 기존 front matter 및 구버전 파서 fixture를 확인한 뒤 확정한다. 이번 문서에 가상의 배포 버전을 발행하지 않는다.
- ID는 이동 추적을 보조하며 일반 상대 Markdown 링크를 대체하지 않는다. GitHub나 외부 편집기에서도 문서가 읽히고 링크를 따라갈 수 있게 한다.
- 기본 레거시 마이그레이션 대상은 발견한 plan/tickets/inventory 문서다. 일반 Markdown에 대한 ID 발급은 사용자가 추가 선택한 파일만 포함한다. 프로젝트의 모든 Markdown을 자동으로 ledger 형식으로 바꾸지 않는다.
- 유효한 ID는 보존하고 없는 문서에만 발급한다. 변환 계획에서 생성한 ID는 실패 재개에도 그대로 사용한다. 중복·잘못된 ID·손상 front matter·미지원 형식은 추측 수정하지 않는다.
- 같은 문서의 Git checkout은 파일 ID를 유지하되 브라우저에서 서로 다른 프로젝트/checkout을 자동 병합하지 않는다. 한 프로젝트에서 복사본이 같은 ID를 갖는 경우 이동인지 새 문서인지 확인하고 명시적 복제에만 새 ID를 발급한다.

### 3. 문서·폴더 이동과 참조 수정

- 이동 전 각 링크의 실제 대상을 해석하고 이동 후 출발점/대상 경로로 상대 경로를 다시 계산한다. 이동한 파일을 가리키는 링크와 이동한 파일 내부의 바깥 참조를 모두 처리한다.
- 기본 지원은 Markdown inline/reference 링크·이미지와 상대 리소스다. query·fragment·인코딩·제목을 보존하고 문서 내용을 전체 재포맷하지 않는다. 코드 fence·inline code·외부 URL은 자동 치환하지 않는다.
- ledger의 기준 문서처럼 알려진 비링크 경로 필드는 명시적 규칙으로 처리한다. 프로젝트 루트 기준 경로와 문서 상대 경로를 구분한다. 임의 본문 경로, HTML/위키 링크 등 지원하지 않는 구문은 검토 항목으로 남긴다.
- docs 밖의 README·AGENTS 등 접근 가능한 프로젝트 Markdown도 역참조 검사에 포함한다. 여기서 프로젝트는 연결한 폴더 경계이며 Git 저장소 하나로 한정하지 않는다. 스캔 제외·권한 부족·연결 폴더 밖·별도 연결된 프로젝트·채팅의 참조는 미검사 범위로 표시하며 전체 무결성을 보장하지 않는다. AKD-10의 로컬 링크 연결은 열람 시에만 적용하며 이 변환의 검사·쓰기 범위를 넓히거나 원본 링크를 내 PC 경로로 치환하는 근거로 쓰지 않는다.
- AKD-04에서 검토 대상·미검사 범위가 남은 상태별로 적용 가능·추가 확인·보류의 조건과 이유를 정하고 AKD-06의 적용 흐름에 연결한다. 표시만 했다는 이유로 적용 가능으로 간주하지 않으며, UI와 CLI가 같은 판정을 사용한다. 지원 구문이나 검사 범위를 확대하는 요구는 아니다.
- 목적지 충돌·대소문자/Unicode 충돌·경로 이탈을 확인한다. 폴더 이동은 포함 파일 목록을 보여주고 이미지 등 비Markdown 자원은 바이트 그대로 보존한다. 브라우저가 지원하지 않는 이동은 안전하게 중단하거나 검증된 CLI 경로를 제공한다.
- 외부에서 이동한 파일은 ID와 이전 경로로 복구 후보를 찾되 자동으로 파일을 수정하지 않는다. 중복 ID나 오래된 경로 재사용은 자동 연결하지 않고, ID 없는 문서의 내용 일치는 제안 근거로만 사용한다.

### 4. 미싱 링크의 로컬 폴더 연결과 재사용

- 정상 링크는 기존 방식으로 열고, 해석할 수 없는 로컬 링크를 사용자가 눌렀을 때 내 폴더를 연결하는 흐름을 제공한다. OS 절대경로·로컬 file URL·문서 상대경로를 대상으로 하며 HTTP(S)/메일 링크와 문서 내부 앵커의 동작은 유지한다. 문서 열람이나 백그라운드 탐색만으로 폴더 선택·권한 요청을 띄우지 않는다.
- 사용자가 원본 링크에서 폴더에 해당하는 앞 경로와 내 PC의 대응 폴더를 지정한다. 남은 하위 경로로 클릭한 대상 파일을 찾을 수 있는지 확인하고 연결을 저장한다. 파일 하나의 선택만으로 상위 폴더 전체의 대응을 추측하지 않으며 실제 대상이 없으면 연결 완료로 처리하거나 파일을 생성하지 않는다.
- 연결은 출발 문서 프로젝트와 원본 경로 접두사를 기준으로 기존 IndexedDB에 저장하고 대상은 사용자가 선택한 디렉터리 핸들로 보관한다. 대상 PC의 절대경로 문자열을 알아내거나 입력할 필요가 없으며 Markdown·별도 YAML·Git 공유 설정에는 기록하지 않는다.
- 같은 문서 프로젝트에서 같은 앞 경로를 가진 미싱 링크는 저장한 폴더와 남은 하위 경로로 해석한다. 상대 링크는 출발 문서 위치를 반영해 정규화한 뒤 비교하고, 경로 구성요소 경계로 일치시켜 비슷한 폴더 이름에 잘못 적용하지 않는다. 겹치는 규칙은 더 구체적인 경로를 우선하되 같은 키의 충돌은 확인 없이 덮어쓰지 않는다. 해석 결과는 선택한 폴더 안에 머물러야 한다.
- 사용자는 저장한 연결을 재지정하거나 해제할 수 있다. 권한 해제·폴더 접근 불가·파일 부재를 구분해 재승인 또는 위치 재지정을 안내하며 다른 후보를 자동 선택하지 않는다. 대상 Markdown은 대상 연결의 문서 식별을 유지해 앱에서 열고 그 밖의 파일은 기존 다운로드 동작을 유지한다. 연결만으로 문서 내용·소유자·티켓 상태나 작업 배정을 바꾸지 않는다.
- 연결은 같은 사이트·브라우저 프로필의 로컬 상태다. 새로고침·재실행·앱 업데이트 후 기존 저장 구조에서 재사용하되 권한은 다시 확인한다. 다른 PC/브라우저로 동기화하지 않고 사이트 데이터 삭제 후에는 다시 연결한다. 저장·조회 실패를 성공으로 표시하지 않으며 실제 폴더 이동 후 핸들이 계속 유효하다고 보장하지 않는다.
- Git remote 식별자나 웹 파일 URL·push를 전제로 삼지 않는다. 외부 agent용 경로 설정·연결 파일·스킬/CLI 규약을 추가하지 않고 agent는 기존 Markdown을 읽는 흐름을 유지한다. 미싱 이미지의 자동 연결, 원문 링크 자동 재작성, repo 내부 파일 구조 차이의 자동 추론은 이번 연결 기능에 포함하지 않는다.
- AKD-10이 이 흐름과 연결 키·경로 정규화·대상 문서 탐색·저장 수명주기의 설계 및 검증을 맡는다. 문서 이동·ID 발급·형식 변환과 독립적인 브라우저 기능이며 현재 승인 범위는 계획·티켓 반영까지다.

### 5. 버전별 형식 정리

- AKL-10/11의 지원 형식 판정 위에 출발 형식·도착 형식·변환 규칙 ID·조건·변경 범위를 가진 마이그레이션 목록을 둔다. 버전 없는 레거시는 확인된 구조로만 분류한다. 앱 버전 증가 자체를 문서 변환 근거로 쓰지 않는다.
- 최초 자동 삭제 후보는 알려진 옛 Progress Board처럼 티켓 본문과 일치하는 중복 생성 섹션이다. 제목만 같은 사용자 섹션, 본문과 모순되는 표, 고유 메모가 섞인 영역은 보존하고 검토 대상으로 표시한다.
- 옛 상태 설명·내장 Ticket Template 등은 확인된 공식 템플릿과 일치하고 고유 정보가 없다는 규칙과 fixture를 확보한 항목만 추가한다. 파싱하지 않는다는 이유로 모든 섹션을 삭제하지 않는다.
- 계획의 결정·조사 근거·질문, 사용자 지시·진행 메모·완료 증거, 알 수 없는 섹션·front matter는 보존한다. 삭제할 섹션뿐 아니라 삭제 후 남는 제목의 앵커 변화도 확인한다. 동명 제목의 앵커 번호가 바뀌는 경우를 포함해 지원 참조가 같은 보존 섹션을 가리키도록 처리하고, 삭제 대상의 안전한 대체나 보존 섹션의 참조 유지가 확실하지 않으면 해당 삭제를 보류한다.
- 누락된 수정일·작성일·Completed at·작업 이력·검증 결과는 현재 시각이나 파일 mtime으로 보충하지 않는다. ID 신규 발급과 확인된 변환 후 형식 표기는 가능하지만 과거 사실 복원과 구분한다. 실제 변환 시각은 복구/변환 기록에만 남긴다.
- ID 발급·문서 이동·레거시 정리는 각각 선택 가능한 작업이다. 하나를 원한다고 나머지를 강제로 적용하지 않는다. 재실행은 추가 변경을 만들지 않고, 중간 버전 건너뛰기·미지원 미래 형식·부분 실패를 다룬다.

### 6. 안전한 적용과 사용 흐름

- 문서 이동·ID 발급·형식 정리는 진입 → 읽기 전용 분석 → 파일별 diff·이동/삭제/미검사 범위·소유자 변화 검토 → 선택한 변경 확인 → 적용·재검증 → 결과/복구의 흐름을 UI와 CLI에서 공유한다. 미싱 링크의 로컬 연결은 파일 변환이 아니며 AKD-10의 브라우저 흐름으로 다룬다.
- 전체 작업의 원본·목적지 상태·의도한 결과·진행 단계를 내구성 있는 journal에 먼저 보존한다. 다중 문서 잠금 순서를 일정하게 하고 각 파일 직전 해시/mtime과 목적지 부재를 재확인한다.
- 이동은 해당 어댑터에서 검증한 방식으로 수행한다. 복사 후 삭제가 필요하면 목적지 close/readback과 참조 변경 상태를 확인한 뒤 원본 삭제 직전에도 외부 변경을 재확인한다. 중간 실패는 부분 완료를 표시하고 자동 재시도·무조건 롤백하지 않는다.
- 복구는 현재 파일이 예상한 상태일 때만 적용해 동료나 외부 편집기의 새 작업을 덮어쓰지 않는다. 다중 파일 원자성이나 Web Lock의 외부 도구 배제를 주장하지 않는다.
- appActivity/usePwaDraft 및 기존 PWA 세션·업데이트 절차에 참여하고, 복구 기록은 연결 해제·앱 업데이트·repair로 제거하지 않는다. 언어/테마 변경은 계획과 선택을 보존한다.
- 브라우저와 CLI는 같은 변환 의미와 fixture를 사용하되 저장 어댑터를 분리한다. native symlink·파일 속성과 실제 OS 권한은 별도 검증한다. UI·CLI의 동시 적용도 외부 변경으로 취급한다. 브라우저의 미싱 링크 연결표는 CLI에 전달하거나 변환에 사용하지 않는다.
- 신규 문서는 외부 agent가 동봉 스킬·템플릿으로 작성한다. 브라우저/CLI의 결과 동등성은 그렇게 작성된 문서와 기존 문서의 분석·선택적 변환에 적용한다. 브라우저의 신규 문서 생성 UI나 CLI 신규 문서 생성 명령을 추가하는 범위가 아니다.

| 기존/신규 범위 | 책임 |
| --- | --- |

| AKL-11 | 일반 읽기/쓰기의 하위 호환과 미지원 형식 보호. 일상 저장 중 암묵적 변환 금지 |
| AKL-12 | 공식 배포·설치 계약. AKD-08의 동봉 번들·독립 CLI 검증에 필요한 선행 계약 |
| AKU-01~07 | 릴리즈 안내·설치 스킬 업데이트. 프로젝트 문서 변환 엔진과 분리 |
| AKD-01~03 | 새 문서 규약, 소유자 구분, 파일 ID와 레거시 발급 |

- 규약을 먼저 확정하고 순수 변환·식별을 검증한 뒤 저장과 UI를 연결한다. 실행 승인 전까지 모든 신규 티켓은 미착수다.
- AKD-08은 AKL-12를 명시적 선행 조건으로 두고 공식 번들·검증기·설치 결과의 일치를 확인한 뒤 완료한다.
- AKD-05는 이동별 브라우저 직접 적용 가능 여부와 CLI 인계 필요 여부를 조사 결과로 남긴다. AKD-06은 직접 이동 또는 안전한 중단·검증된 CLI 인계 중 해당 경로로 검증한다. CLI 인계가 필요한 경우 AKD-08이 조건부 선행 티켓이며, 그 전의 안전한 중단은 중간 상태이지 해당 이동 경로의 완료가 아니다. 검증되지 않은 명령은 안내하지 않는다.
- 브라우저와 스킬의 호환 계약·검증 자료를 함께 준비하되 앱 적용, 스킬 설치, 프로젝트 문서 변환의 승인은 별개다. 개인 전역 스킬을 시험 대상으로 쓰지 않는다.
- AKD-10은 기존 브라우저 폴더 연결을 바탕으로 독립 수행할 수 있으며 새 문서 ID·폴더 이동·스킬/CLI 변경을 선행 조건으로 요구하지 않는다. AKD-09는 이 기능의 실제 폴더·다른 PC 배치 시나리오와 안내까지 확인한다.
- 정확한 메타데이터 키/스키마, 파일 이동 어댑터, 지원 범위 안의 참조 구문·적용 판정과 로컬 연결 저장 계약은 AKD-01/04/05/06/10의 기술 검토다. 조사 결과 사용자에게 보이는 범위를 바꿔야 하면 해당 티켓에 결정을 요청한다.

## 성공을 확인할 방법

- 일반 폴더·기존 루트·여러 사용자·동일 티켓 ID·소유자 변경 fixture로 발견과 필터·실행 범위를 확인한다.
- 사용자별 독립 증가, 하위 폴더 포함 최대값, 빈 폴더의 `01`, 이동한 번호의 보존과 다음 번호, 번호 중복·빈 번호 및 실제 목적지 충돌을 확인한다. 예를 들어 기존 `24`·`25` 문서를 옮긴 사용자 범위의 최대값이 `25`이면 다음 새 문서는 `26`이다. 번호 순서와 최신 지시·의존성이 다른 사례에서 번호만으로 실행 순서를 정하지 않는지 확인한다.
- ID 없는 기존 문서, 기존 front matter, 중복 ID, 복제·다른 checkout, 외부 이동·내용 동시 변경을 검증한다. ID 발급을 두 번 해도 바뀌지 않아야 한다.
- 문서/폴더 이동 전후 링크가 같은 대상을 가리키는지 검사한다. 이미지·앵커·한글/공백·참조식 링크·루트 경로·코드 예제·모호한 텍스트를 포함하며, 검토 대상·미검사 범위의 상태별 적용·추가 확인·보류가 정한 계약과 일치하는지 확인한다.
- 서로 다른 repo 배치의 미싱 링크에서 폴더 연결 → 대상 열기 → 같은 앞 경로의 다른 링크 재사용 → 재실행 후 재사용을 확인한다. 상대 링크의 출발 문서 차이·접두사 경계/겹침·프로젝트 격리·권한/파일 부재·취소·재지정/해제·IndexedDB 실패를 검증하고 원본 Markdown과 agent 설정이 바뀌지 않는지 비교한다. fake handle/OPFS의 저장 검증과 격리 native 폴더의 재연결·권한 검증을 구분한다.
- 레거시 정리 전후 티켓 ID·상태·진행률·완료 시각·체크리스트·사용자 지시·진행 메모의 파서 결과와 비대상 원문을 비교한다. 동명 제목 중 앞 섹션만 삭제해도 뒤에 남는 섹션의 문서 내부·README 등 지원 참조가 유지되거나 삭제가 보류되는지 확인한다. 파서 결과 동등성만으로 고유 본문 삭제를 정당화하지 않는다.
- 여러 파일 중간 실패, 원본/목적지 외부 변경, 용량/권한/백업 실패, 앱 종료·업데이트·재개를 주입하고 복구가 새로운 편집을 덮어쓰지 않는지 확인한다.
- CLI/공용 변환·브라우저 fake handle/OPFS 검증과 격리 native 폴더·Chrome 수동 검증은 구분한다. 실제 권한·속성·symlink 검증 없이 운영 안전성을 완료 처리하지 않는다.
