# Alpha Kanban 팀 문서 소유자·이동·형식 마이그레이션 계획

작성일: 2026-10-28
수정일: 2026-11-01

## 목표와 이유

- 개인 작업 기록을 Git으로 공유하면서 동료의 컨텍스트와 현재 agent가 실행할 업무를 구분한다. 회사별 하네스 통합이나 특정 제공자에 종속되지 않는 공개 도구의 규약으로 만든다.
- `.ak.config`·`.ak.user` 없는 기본 사용을 유지한다. 기존 docs 위치·번호 규칙으로 문서를 작성·수정할 수 있고 `@사용자` 폴더·owner·사용자 등록을 요구하지 않는다. 최초 플랜 작성 때 팀/개인 여부를 묻는 절차를 추가하지 않는다.
- `.ak.config`는 커밋 가능한 공통 설정, `.ak.user`는 Git에서 제외하는 개인 사용자 설정으로 분리한다. 공통 도구가 `documents.ownerFolders`와 작성 대상·사용자를 판정하고 스킬은 그 결과를 사용한다. 사용자 우선순위는 repo > 지정 workspace > 홈을 유지하며 두 파일 사이에 범용 덮어쓰기를 두지 않는다.
- `documents.ownerFolders = true`일 때만 신규 작성의 기본 위치를 `docs/@사용자/`로 선택하고 필요한 사용자 폴더를 자동 생성한다. 새 소유자 문서는 폴더와 같은 `Owner:`를 기록한다. 이미 있는 @폴더의 owner 없음/불일치 판정과 일반 폴더의 정상적인 owner 부재는 이 옵션과 구분한다.
- 소유자 구분을 선택하면 기존 문서도 참조를 유지하며 사용자 폴더로 옮길 수 있게 한다. 명시적인 업무 인수를 위한 사용자 폴더 간 이동을 지원하며 문서별 공유 목록을 수동 관리하지 않는다. 기본 사용 안내와 선택적 소유자 구분 안내를 나눈다.
- 문서·폴더 이동과 PC 변경 시 경로 일괄 보정은 외부 agent가 호출하는 독립 Node CLI로 제공한다. 실행한 현재 worktree의 지정된 docs만 변경하며 브라우저 이동 기능이나 CLI의 checkout 선택 단계는 제공하지 않는다.
- 여러 repo를 참조하는 문서의 로컬 링크를 열 수 없으면 root 아래 Git repo와 저장한 대응으로 자동 연결을 시도하고, 식별·탐색에 실패하거나 모호하면 repo 선택·수동 폴더 연결로 이어진다. 확인한 연결은 같은 앞 경로에 재사용하며 원본 Markdown과 agent 설정을 바꾸지 않는다.
- 파일 내부의 지속적인 문서 ID를 처음부터 설계하고 레거시 문서에도 선택적으로 발급한다. 경로 이동과 형식 정리를 별도 수작업 없이 검토·적용할 수 있게 한다.
- 확인된 옛 중복 섹션은 자동 정리하되 과거 수정일이나 완료 증거를 만들어내지 않는다. 자동화는 승인한 변환을 기계적으로 수행한다는 뜻이며, 앱 업데이트나 문서 열람만으로 파일을 바꾸지 않는다.
- AKD-01의 규약 확정과 AKD-11 구현에 이어 AKD-02의 브라우저 소유자 표시·필터 구현이 승인됐다. 나머지 구현과 기존 문서 이동·ID 발급·삭제·변환은 포함하지 않는다. 진행은 [티켓](25_alpha_kanban_team_documents_tickets.md)에서 관리하고, 첫 페이즈의 판정표와 조사 근거는 [소유자 규약](team_documents_contract.md)에 둔다.

- `packages/shared/src/documents.ts`, `packages/shared/src/ticketMarkdown.ts`, `packages/shared/src/index.ts`, `packages/shared/test`: 소유자·문서 메타데이터·참조 변환·형식 판정의 공통 계약.
- `apps/web/src/browser/repository.ts`, `apps/web/src/browser/storage.ts`, `apps/web/src/browser/MarkdownResources.tsx`: 문서 발견·식별·복구·로컬 참조, root 아래 repo 발견·미싱 링크 자동/수동 연결·IndexedDB 저장·재사용과 ID·형식 변환의 파일 작업.
- `apps/web/src/App.tsx`, `apps/web/src/components`, `apps/web/src/i18n/messages.ts`, `apps/web/src/pwa`: 소유자 표시·필터, ID·형식 마이그레이션 검토, 드래프트·업데이트 보호. 브라우저의 이동·경로 재작성 UI는 제외한다.
- `skills/implementation-ledger`, `scripts`: `.ak.config` 작성 정책·`.ak.user` 사용자 판정·worktree 상속을 처리하는 공통 도구와 짧은 새 문서 작성 규약, 외부 agent가 programmatic하게 호출하는 독립 `.mjs` 도구·동봉 배포·검증 절차. 기존 ticket-md와 개인 전역 스킬은 무단 변경하지 않는다.
- `docs`, `README.md`, `README.en.md`, `CONTRIBUTING.md`, `AGENTS.md`: 구현 후 실제 지원 범위의 규약·사용 안내. 기존 작업 중 파일은 이번 계획 작성에서 수정하지 않는다.

## 확인한 현재 상태

- `docs/21_alpha_kanban_browser_transition_inventory.md`에 따라 브라우저 전용 Markdown 제품을 유지한다. 팀 기능을 이유로 서버·내장 채팅·agent 실행기를 복원하지 않는다.
- `repository.ts`는 하위 디렉터리의 Markdown을 재귀 탐색한다. 문서 목록은 경로 인덱스를 사용하고, 브라우저의 `d_` ID와 파일 핸들은 IndexedDB에 보존한다. 이는 Git으로 전달되는 파일 내부 ID와 다르다.
- 브라우저의 프로젝트 경계는 Git 저장소가 아닌 연결한 폴더다. 하네스 루트를 하나의 프로젝트로 연결하면 그 아래 여러 repo를 포함할 수 있다. 현재 `repository.ts.localResource`는 문서 상대 링크를 해당 프로젝트 안에서만 해석하며 OS 절대경로·file URL·프로젝트 경계 이탈을 거부한다. 중첩된 별도 연결도 기존 연결 경계에 따라 구분하며 프로젝트 간 링크를 자동 재매핑하지 않는다.
- `MarkdownResources.tsx`는 로컬 링크 해석 실패 시 오류만 표시하고 폴더 선택을 제공하지 않는다. 정상 상대 링크의 Markdown은 앱에서 열고 다른 파일은 다운로드한다. 폴더 핸들을 저장하는 기존 IndexedDB 구조는 있지만 원본 앞 경로와 내 폴더를 대응시키는 기록은 없다.
- 현재 파일 핸들이 같은 항목으로 유지되는 이동은 발견 시 연결할 여지가 있지만, 다른 도구의 복사 후 삭제나 다른 PC의 checkout까지 동일성을 보장하는 파일 메타데이터 계약은 없다.
- 현재 동봉 스킬에는 `.ak.config`·`.ak.user` 판정, ownerFolders에 따른 작성 위치 선택과 worktree의 개인 설정 상속이 없다. 이 판정을 공통 도구로 구현해야 하며 브라우저의 연결 목록을 agent가 읽는 것으로 가정하지 않는다.
- 초기 도입 기준은 사용자 확인상 `@사용자` 폴더를 아직 사용하지 않는 상태다. 소유자를 구분해 새 규약으로 생성하는 작업 문서는 owner를 기록하고, 이후 `@사용자` 폴더에서 owner가 없는 문서는 레거시 편입 대상으로 분류한다. 기본 사용 문서의 owner 부재는 이행 필요 사유가 아니다.
- 동봉 스킬·템플릿의 작성 규칙 개선은 master의 `0d48dc9`에 포함돼 있다. 현재 템플릿 개선과 기존 Markdown의 중복 섹션을 자동 정리하는 AKD-07은 별개이며 owner 추가는 이번 후속 계획이다.
- `ticketMarkdown.ts`는 Status와 Ticket List 및 알려진 티켓 필드를 읽는다. 읽지 않는 본문을 의미 없는 내용으로 판정하지 않는다. `docs/02_alpha_kanban_tickets.md`에는 초기 Progress Board와 템플릿·운영 원칙이 남아 있다.
- 현재 단일 문서 쓰기는 해시/mtime, Web Lock, 복구 preimage, close/readback 확인으로 보호된다. 여러 파일 이동·참조 수정의 원자성을 제공하는 것으로 해석하지 않는다.
- [기존 브라우저 티켓](14_alpha_kanban_browser_local_tickets.md)의 AKL-10은 스킬·문서 형식 버전 계약, AKL-11은 하위 호환 읽기/쓰기와 미지원 형식 보호를 담당하며 현재 TODO다. 새 계획은 이 계약을 재사용하고 명시적으로 요청한 변환 기능을 추가한다.

## 할 일과 선택한 방향

### 1. 무설정 기본 사용·선택적 소유자 구분과 실행 범위

- 기본 사용은 기존 docs 위치·번호 규칙과 문서 작성·수정 흐름을 유지한다. `.ak.config`·`.ak.user` 생성, 사용자 확인, `@사용자` 폴더 생성 또는 owner 추가를 선행 절차로 요구하지 않는다. 공통 도구의 읽기 전용 조회에서 설정이 없으면 기본 결과를 반환하며 소유자 없는 문서를 오류·불완전한 문서·필수 마이그레이션 대상으로 취급하지 않는다.
- `.ak.config`는 공유 가능한 공통 설정이며 최소 작성 정책은 `documents.ownerFolders`로 둔다. `.ak.user`는 개인 사용자 식별자 `user`를 담고 repo/workspace에서 Git 공유 대상에서 제외한다. 파일 형식은 Git config와 호환되는 제한된 INI 계열이며 `[documents] ownerFolders = true`, `[user] id = @alice`로 각각 표기한다. 두 파일을 범용 병합하지 않고 중복 키·include·미지원 키를 거부한다. 공유 파일의 user나 개인 파일의 ownerFolders 등 역할이 다른 항목은 위치 오류로 보고하고 사용자·작성 정책으로 채택하지 않는다.
- 신규 문서의 기본 배치는 repo의 `.ak.config` > 명시적으로 지정한 workspace의 `.ak.config` > 기본값 false 순서로 ownerFolders를 판정한다. 항목이 없는 단계만 건너뛰고 명시적 false는 상위 true를 덮는다. true일 때만 유효 사용자를 확인해 사용자 폴더를 자동 생성·선택한다. 미설정/false이면 기존 작성 위치·번호 규칙을 유지하며 홈의 `.ak.user` 존재, 인원수, 발견한 @폴더만으로 활성화하거나 팀/개인 여부를 묻지 않는다.
- ownerFolders가 true인데 사용자가 없으면 현재 사용자 지정이 필요한 결과를 반환하고 해당 사용자 폴더 작성을 보류한다. 손상·읽기 실패·잘못된 설정값은 누락과 구분하며 잘못된 정책을 false나 다른 사용자의 값으로 조용히 대체하지 않는다. 현재 사용자에 의존하지 않는 기존 문서 편집·참조 열람을 이 판정 성공에 종속시키지 않는다.
- ownerFolders는 신규 작성의 기본 위치와 자동 폴더 생성 정책이다. 명시한 작성 대상과 기존 문서 위치를 우선하며 설정 변경만으로 기존 문서를 이동하거나 owner를 추가·삭제·교체하지 않는다. 이미 있는 @폴더의 소유자 인식·열람·명시적 대상 편집과 후속 CLI 이동/인수는 활성화 여부와 별개다. 설정 없는 사용자가 공유된 @문서를 읽어도 소유자 경계를 유지하고 모두 내 업무로 간주하지 않는다.
- 프로젝트 기준 `docs` 바로 아래의 `@사용자` 디렉터리만 소유자 경계로 해석한다. 하위 문서는 그 소유자를 상속하며 일반 폴더, 더 깊은 `@` 이름, 빈 `@`를 임의로 새 사용자로 해석하지 않는다.
- 현재 폴더 소유자와 문서의 기록된 `owner`를 구분한다. owner는 마지막으로 확인·반영한 문서 소유자이며 현재 작업자의 `.ak.user`, 최초 작성자, 과거 파일 경로 또는 실행 허가를 뜻하지 않는다. 현재 소유자 표시·필터는 계속 경로를 기준으로 한다.
- 소유자를 구분해 작성하는 새 plan/tickets/inventory 문서는 사용자 폴더에 작성하면서 제목 아래의 문서 공통 헤더에 폴더와 같은 `Owner: @alice` 한 줄을 기록한다. 기본 사용에서는 이 줄과 빈 메타데이터를 넣지 않는다. 헤더 인식 범위·중복/잘못된 값·현재 파서 보존 계약은 AKD-01의 [소유자 규약](team_documents_contract.md)을 따른다. 선택적 템플릿 적용과 생성 검증은 AKD-11이 맡는다. 티켓마다 소유자를 반복하거나 YAML front matter·별도 YAML 파일·추가 title을 요구하지 않으며 UUID 도입을 기다리지 않는다.
- `@사용자` 안의 owner 없음은 레거시 편입·소유자 등록 대상, 유효한 owner와 폴더의 불일치는 수동 이동·인수 정합화 대상이다. 일치하면 소유자 기록은 일치하지만 경로·링크까지 정상이라고 보장하지 않는다. 일반 폴더·기존 루트는 계속 소유자 미지정이며 owner 값만으로 임의 배정하지 않는다. 손상된 메타데이터나 잘못된 owner를 단순 누락으로 취급해 덮어쓰지 않는다.
- 대상 발견은 읽기 전용이다. 열람·필터·일반 상태 수정·앱/스킬 업데이트만으로 owner를 추가하거나 덮어쓰지 않는다. 새 문서 기록과 기존 문서의 정합화는 구분하며 기존 문서는 분석 결과를 확인한 명시적 CLI 적용으로만 갱신한다.
- 사용자 식별자는 프로젝트 안에서 합의한 `@사용자` 문자열이다. 현재 사용자 판정이 필요한 소유자별 작성·내 업무 선택·인수에서 스킬·CLI는 repo의 `.ak.user` > 명시적으로 지정한 workspace root의 `.ak.user` > `~/.ak.user` 순서로 유효 사용자를 판정한다. 각 단계는 선택 사항이며 우선순위가 높은 범위에 사용자 지정이 없을 때만 다음 범위를 사용한다. 설정이 모두 없으면 미설정으로 보고하고 현재 사용자에 의존하는 작업 전에만 사용자를 확인한다. 손상·읽기 실패·잘못된 식별자는 누락과 구분하고 조용히 다른 사용자로 대체하지 않는다. OS·Git 작성자·폴더명에서 나를 추측하지 않으며 기본 작성·수정·참조 열람을 사용자 판정 성공에 종속시키지 않는다.
- workspace root는 명시적으로 지정한 설정 범위다. Git 공통 관리 디렉터리의 로컬 config에 단일 `alphaKanban.workspaceRoot` 절대경로로 연결하며 정확한 파일의 값만 읽고 include·전역·worktree 설정을 병합하지 않는다. 여러 workspace가 등록돼도 해당 repo에 지정된 workspace만 사용하며 이름·깊이·임의 상위 설정이나 다른 workspace의 값을 섞지 않는다. 브라우저 등록 목록은 스킬의 설정 연결 정보로 간주하지 않는다. 조회만으로 이 연결·설정·폴더·문서를 생성하거나 덮어쓰지 않는다.
- workspace 밖의 linked worktree도 Git 공통 관리 정보로 확인한 원래 main worktree의 `.ak.user`와 지정 workspace를 이어받아 repo > 원래 workspace > 홈 순서로 사용자를 판정한다. 공유 `.ak.config`의 repo 값은 현재 worktree의 파일을 읽고 없으면 지정 workspace·기본값을 사용하며 원래 repo의 다른 브랜치 파일로 대체하지 않는다. 임시 상위 폴더·브랜치·HEAD·remote 이름이나 같은 remote의 독립 clone으로 개인 설정 기준을 바꾸지 않는다. `.git` 파일/디렉터리는 Git 조회로 확인하고 main 후보의 실제 루트·공통 저장소 일치를 재검증한다. 원래 위치 이동·삭제·접근 실패·특수 Git 구성에서 검증 불가·복수 후보 충돌은 필요한 판정의 미확정으로 보고 명시적인 연결 복구를 요구한다. 정확한 지원 한계는 소유자 규약에 두며 checkout 선택은 추가하지 않는다.
- 공통 판정 도구는 유효 작성 정책·출처, 작성 경로·폴더 생성 필요 여부·기록할 owner, 필요한 경우의 사용자·출처, repo/workspace 설정 기준과 현재 worktree를 구분해 반환한다. 스킬과 후속 CLI는 같은 판정을 사용하며 도구의 조회만으로 쓰지 않는다. 기본 작성에 불필요한 개인 사용자 조회를 요구하지 않는다. 다른 위치의 설정을 읽어도 쓰기는 현재 작업 범위에 남고 현재 사용자 값은 과거 링크의 출처를 증명하지 않는다.
- 기존 루트 문서와 일반 폴더는 소유자 미지정이다. 기본 사용에서 같은 위치에 새 문서를 계속 작성·수정할 수 있으며 개인 폴더로 강제 이동하거나 공용 실행 큐로 취급하지 않는다. ownerFolders로 판정한 새 업무만 현재 worktree의 사용자 폴더에 기본 배치하고 기존 문서 이동은 별도 명시 요청으로 다룬다.
- 소유자별 새 문서 번호는 각 `docs/@사용자/`와 그 하위 폴더를 하나의 범위로 삼아 독립적으로 증가시킨다. 그 범위의 기존 Markdown 숫자 접두사 중 최대값에 1을 더하고, 번호가 없으면 `01`부터 시작한다. 다른 사용자 폴더와 소유자 미지정 영역의 번호는 발급 기준에 포함하지 않는다. 기본 사용의 기존 번호 발급 규칙은 유지한다.
- 기존 문서는 이동할 때 번호를 유지한다. 이동·소유자 변경을 이유로 다시 번호를 매기거나 빈 번호를 채우지 않는다. 이동해 온 번호도 이후 신규 번호의 최대값 계산에 포함한다. 번호만 같은 것은 충돌이 아니며 실제 목적지 충돌은 덮어쓰기나 자동 재번호 부여로 회피하지 않는다.
- 문서 번호는 정렬·탐색의 참고값이다. 문서 정체성, 최신 결정, 구현 우선순위나 선행 의존성을 뜻하지 않으며 사용자 간 번호를 시간 순서로 비교하지 않는다. agent는 현재 요청·최신 사용자 지시·티켓 상태·`Depends on`·기준 문서의 내용을 확인해 작업 순서를 판단한다.
- 브라우저는 경로 소유자를 표시한다. 프로젝트 사이드바는 전체·미지정·단일 소유자를 프로젝트별로 기억한다. 전체 보드는 검색 가능한 다중 선택 하나에서 같은 @이름을 프로젝트와 무관하게 모으고 선택한 이름을 OR로 결합한다. 선택 없음은 전체이며 프로젝트 필터와는 AND로 결합한다. 전체 보드의 선택 목록은 프로젝트별 필터와 독립적으로 저장하고 서로 전파하지 않는다. `.ak.user`를 읽거나 현재 사용자·별칭 연결·내 작업 설정을 만들지 않는다. 공유 `.ak.config`를 개인 사용자 설정으로 취급하지 않으며 경로 소유자·필터는 ownerFolders의 부재/false에도 유지한다. 필터는 열람 상태이며 사용자·업무 배정을 바꾸지 않는다. 같은 번호·티켓 ID도 문서 정체성과 함께 구분하고 첫 페이즈에는 파일 내부 UUID를 요구하지 않는다.
- 동료 문서 전체를 참조할 수 있지만 그 안의 사용자 지시·미완료 티켓·개인 하네스 규칙은 현재 agent에 대한 명령이 아니다. 실행은 현재 사용자의 명시적 요청 또는 배정 범위로 한정한다.
- 퇴사·휴가 등으로 업무를 인수할 때 타인 폴더 → 내 폴더를 포함한 사용자 간 이동을 CLI의 정상 이동으로 지원한다. 사용자가 지정한 원본·목적지와 인수 의도를 작업 계획에 반영하고 경로에서 계산한 변경 전후 소유자를 보여준다. 별도 로그인·원소유자의 도구 내 승인 절차를 요구하거나 현재 사용자와 다른 폴더라는 이유만으로 거부하지 않는다.
- 인계 이동은 문서 ID·기존 번호·티켓 상태·체크리스트·사용자 지시·진행 메모·완료 증거를 보존한다. 폴더 이동 승인만으로 티켓 상태를 바꾸거나 구현을 시작하지 않는다. 일시 인수 뒤 복귀도 명시적으로 요청한 역방향 이동으로 처리하며 자동 복귀·인사 관리 기능은 추가하지 않는다.
- 폴더 소유자는 문서의 기본 작업 범위이지 티켓별 강제 접근 권한이나 동시 작업 잠금이 아니다. 명시적 인계와 타인 티켓의 무단 실행을 구분하며 다른 티켓으로 같은 기능을 동시에 구현하는 문제까지 해결했다고 주장하지 않는다.
- 이번 범위는 개인 소유자 구분과 서로의 컨텍스트 참조로 한정한다. 구체적인 사용처가 정해지지 않은 팀 폴더·팀 소유자 분류·팀용 접두사·공용 업무 배정은 제외한다. `#`, `+`, `@@` 중 어느 것도 채택·예약하지 않는다.

### 2. 문서 메타데이터·소유자 분석과 파일 ID

- 파일 내부의 지속적 ID, 브라우저 로컬 ID, 티켓 ID, 문서 형식 개정, 스킬 개정, 앱 릴리즈는 서로 구분한다. ID는 경로·소유자·제목에서 파생하지 않고 이동·이름 변경 시 유지한다.
- 소유자는 AKD-01의 문서 상단 `Owner:` 한 줄을 사용한다. 문서 ID의 기본 후보는 UUID이며 같은 문서 헤더의 별도 필드로 확장하는 방향에서 AKL-10과 AKD-12가 키·형식 호환·기존 front matter 및 구버전 파서 fixture를 검토해 확정한다. 필수 YAML front matter나 문서별 sidecar YAML·추가 title을 만들지 않고 사용자 설정용 `.ak.user`와도 구분한다. 이번 문서에 가상의 배포 버전을 발행하지 않는다.
- AKD-03의 공용 파서는 기록된 owner·경로 소유자·ID를 각각 읽고 레거시 편입·이동/인수 정합화·소유자 일치·미지정/메타데이터 오류를 분석 결과로 반환한다. 일반 폴더의 owner 부재는 정상적인 미지정이며 레거시 편입 분류는 `@사용자` 안에서만 적용한다. owner 등록과 UUID 발급은 별도 선택이며 기본 사용도 `.ak.config`·`.ak.user`·owner 없이 ID를 사용할 수 있다. 판정만으로 원본을 바꾸거나 일반 Markdown에 메타데이터를 일괄 추가하지 않는다.
- ID는 이동 추적을 보조하며 일반 상대 Markdown 링크를 대체하지 않는다. GitHub나 외부 편집기에서도 문서가 읽히고 링크를 따라갈 수 있게 한다.
- 기본 레거시 마이그레이션 대상은 발견한 plan/tickets/inventory 문서다. 일반 Markdown에 대한 ID 발급은 사용자가 추가 선택한 파일만 포함한다. 프로젝트의 모든 Markdown을 자동으로 ledger 형식으로 바꾸지 않는다.
- 유효한 ID는 보존하고 없는 문서에만 발급한다. 변환 계획에서 생성한 ID는 실패 재개에도 그대로 사용한다. 중복·잘못된 ID·손상 front matter·미지원 형식은 추측 수정하지 않는다.
- 같은 문서의 Git checkout은 파일 ID를 유지하되 브라우저에서 서로 다른 프로젝트/checkout을 자동 병합하지 않는다. 한 프로젝트에서 복사본이 같은 ID를 갖는 경우 이동인지 새 문서인지 확인하고 명시적 복제에만 새 ID를 발급한다.

### 3. 현재 worktree의 CLI 이동·업무 인계·소유자 정합화·PC 경로 보정

- CLI는 실행 위치에서 Git worktree 루트·Git 관리 경로·HEAD를 자동 확인한다. `.git`이 파일인 linked worktree도 Git 조회로 해석하며 checkout·브랜치·rev를 사용자에게 선택받지 않는다. 같은 repo·같은 HEAD인 다른 worktree도 현재 실행 경로와 구분하고 수정하지 않는다. Git 이력의 commit 자체를 바꾸는 기능이 아니라 현재 작업 파일의 diff를 만드는 기능이며 이후 커밋·머지의 취사는 사용자가 결정한다.
- 작업자 식별이 필요한 요청은 AKD-11의 공통 `.ak.user` 판정을 재사용한다. 원래 repo/workspace의 설정 상속은 읽기만 하며 원래 repo의 docs를 이동·수정 대상으로 삼지 않는다. 사용자 판정을 사용한 분석 결과에는 사용자와 설정 출처를 남기고 적용 전 판정이 달라졌으면 소유자·인수 의도를 재분석한다. 명시한 다른 소유자 사이의 인수는 허용하며 설정 일치만으로 자동 배정하지 않는다. 기본 사용의 일반 폴더 이동·참조 보정·PC 경로 보정은 사용자 설정·owner 등록 없이 요청할 수 있으며 기존 쓰기 범위·분석·명시적 적용 보호는 동일하게 적용한다.
- 문서 쓰기는 현재 worktree 안에서 지정한 docs의 파일·하위 폴더와 이동 목적지로 제한한다. 지정 범위에는 레거시 문서와 서로 다른 `@사용자` 폴더를 함께 포함할 수 있다. symlink·중첩 저장소·다른 worktree를 따라 쓰기 범위를 넓히지 않는다. 참조 대상인 소스 파일·다른 repo는 명시한 범위에서 읽기만 하며 옮기거나 수정하지 않는다.
- 작업은 실제 파일 위치를 바꾸는 문서 이동, 이미 배치된 문서의 owner 등록·정합화, 파일 위치를 유지하는 PC 경로 일괄 보정으로 나눈다. 기존 파일의 세 작업은 CLI 전용이며 브라우저에서의 이동·owner 정합화·경로 재작성·CLI 실행이나 이동 마법사는 제공하지 않는다. ID 발급·레거시 섹션 정리는 별도 선택 작업이다.
- 이동은 원래 링크 대상을 해석하고 이동 맵을 출발 문서와 대상에 함께 적용해 상대 경로를 다시 계산한다. 옮긴 문서 내부의 참조와 옮긴 문서를 가리키는 역참조를 모두 분석한다. 포함 파일·소유자 변화·목적지 충돌을 보여주고 번호·ID를 보존하며 이미지 등 비Markdown 자원은 바이트 그대로 옮긴다.
- 경로 보정은 Mac → Windows 등 PC·OS·clone 경로 변경 후 지정 docs의 링크를 현재 배치에 맞게 일괄 재작성한다. 확인된 옛 repo 루트와 현재 repo 루트의 대응에 repo 내부 경로를 결합하고, 로컬 Git 정보로 repo 경계·식별을 검증한다. 현재 문서 repo는 실행 위치로 확정하며 다른 repo는 요청에 지정한 현재 경로를 사용한다. 대상 worktree를 탐색해 골라 바꾸거나 다른 worktree의 문서까지 동기화하지 않는다.
- 옛 루트의 repo가 확인되지 않으면 경로명·동명 파일·후보 하나만으로 추측하지 않는다. 과거 상대 링크를 해석할 때는 문서가 있던 repo의 옛 루트도 필요하다. 원본 PC에 접근할 수 없으면 사용자가 확인한 대응을 입력으로 받고 근거를 분석 결과에 남긴다. remote 표기 차이·fork·여러 remote·중첩 repo를 보수적으로 구분하고 실제 파일의 존재와 정확한 내부 경로를 확인한다. commit·push를 요구하지 않으며 repo 내부 구조 변경이나 없는 파일을 비슷한 대상으로 대신 연결하지 않는다.
- 원본 경로의 POSIX/Windows/file URL 형식을 현재 OS와 별도로 해석한다. 경로 구성요소 경계와 가장 구체적인 확인된 대응을 사용하고 겹치는 대응의 충돌·대소문자/Unicode 충돌·드라이브/UNC 경계를 검사한다. 기본 출력은 문서 상대 링크이며 드라이브가 달라 표현할 수 없으면 보류한다. 로컬 절대 file URL 출력은 요청에 명시된 경우에만 허용하고 다른 PC의 유효성까지 보장하지 않는다.
- Markdown inline/reference 링크·이미지 및 알려진 ledger 경로 필드만 구문에 맞춰 수정한다. query·fragment·인코딩·제목과 루트 기준/문서 상대 기준을 보존하고 전체 문서를 재포맷하지 않는다. 코드 fence·inline code·외부 URL·임의 본문은 일괄 문자열 치환하지 않으며 지원하지 않는 HTML/위키 링크는 검토 항목으로 남긴다.
- 현재 worktree의 README·AGENTS 등 접근 가능한 Markdown은 역참조를 읽기 전용으로 검사한다. 지정 docs 밖의 문서는 자동 수정하지 않는다. 범위 밖의 알려진 참조를 깨뜨리는 이동은 보류하고 영향 파일을 보고한다. docs 안이면 요청한 쓰기 범위를 명시적으로 조정한 뒤 재분석할 수 있으며 docs 밖 참조는 별도 수정이 필요하다. 다른 worktree·미지정 외부 repo의 역참조, 스캔 제외·권한 부족·채팅은 미검사 범위로 보고하며 전체 무결성을 주장하지 않는다.
- AKD-04가 검토/미검사 상태별 적용 가능·추가 확인·보류 조건을 정하고 AKD-06이 이를 그대로 적용한다. 미해결을 성공으로 세거나 agent가 임의로 범위를 넓혀 치환하지 않는다. 분석 결과는 실제 변경 집합을 고정하며 적용 직전 작업 루트·HEAD·원본/목적지를 재검증한다.
- 외부 도구가 이미 옮긴 문서는 현재 worktree 안에서 ID·명시한 이전 경로로 복구 후보를 분석하고 승인된 CLI 계획으로만 참조를 수정한다. 중복 ID·이전 경로 재사용·동일 내용 복사는 추측 연결하지 않는다. 브라우저는 이동 결과를 다시 발견·식별하며 기존 선택·딥링크·드래프트를 보호하고 필요한 재연결만 안내한다.
- AKD-06은 owner 없는 레거시 편입과 owner가 다른 이동·인수의 정합화를 기존 외부 이동 복구 흐름에 연결한다. 이미 옮겨진 파일을 다시 이동하지 않고 지정 docs의 owner·필요한 참조 변경을 diff로 제시한다. owner만으로 과거 경로를 복원하지 않으며 링크 보정은 확인된 이전 경로와 문서 식별 근거를 사용한다. 근거 부족·복사/중복의 모호함은 보고하고 추측 치환하지 않는다.
- 기존 owner·경로·참조와 변경 결과를 AKD-05의 journal에 보존한 뒤 명시적 적용에서 관련 보정과 readback을 확인하고 목적지 폴더의 owner를 기록한다. 필요한 참조 보정이 미해결인데 owner만 바꿔 전체 정합화 성공으로 처리하지 않는다. 부분 실패·외부 변경은 복구 기록에 남기며 분석·취소·보류는 원본을 유지한다. owner 등록은 최초 작성자나 과거 날짜를 복원하는 작업이 아니고 UUID 발급·섹션 정리를 강제하지 않는다.

CLI 입력은 다음 의미를 갖는 구조화된 요청으로 설계한다. 정확한 명령·필드명은 AKD-06에서 기존 ticket-md와 충돌 없이 확정하며 현재 repo·HEAD·checkout 선택값을 사용자 필수 입력으로 만들지 않는다.

| 입력 | 의미 |
| --- | --- |
| 작업 종류 | 문서 이동, owner 등록·정합화 또는 PC 경로 보정. 하나를 요청해도 다른 변환을 강제로 실행하지 않음 |
| docs 범위 | 현재 worktree에서 이동·참조 수정할 파일/폴더와 목적지의 명시적 범위 |
| 이동 목록·인계 의도 | 원본 → 목적지 또는 이미 옮겨진 현재 위치와 확인된 이전 경로. 경로 소유자·기록된 owner와 등록/인수 의도를 계획에 반영 |
| repo 경로 대응 | 보정에 필요한 옛 루트·경로 형식·확인된 repo와 현재 경로. 현재 문서 repo 경로는 자동 확인하고 다른 repo 경로는 참조 검증에만 사용 |
| 링크 출력 규칙 | 기본 문서 상대 링크. 표현할 수 없는 경우 보류하며 절대 file URL은 명시 요청 필요 |
| 적용할 분석 결과 | 고정된 변경 목록·입력/원본 해시·판정·작업 루트/HEAD를 포함한 계획. 승인 범위 안에서 agent가 비대화형으로 적용 |

- 요청·diff·결과·미해결 사유는 기계가 읽을 수 있는 JSON과 명확한 종료 코드로 제공한다. 분석과 적용을 분리하고 파일 경로에 공백·한글이 있어도 셸 문자열 재조립에 의존하지 않는다. 문서별 목록을 영구 하드코딩하거나 별도 meta YAML·agent용 링크 대응 영구 설정을 만들지 않는다. 사용자 식별이 필요한 때만 `.ak.user`를 별도 계약으로 읽고 필요한 요청/결과·백업은 명시한 로컬 작업 산출물로 다룬다.
- AKD-10의 브라우저 IndexedDB 연결은 열람 전용이며 CLI 입력으로 읽거나 동기화하지 않는다. CLI의 명시적 PC 보정만 원문을 바꾸고, 브라우저 연결이나 앱 업데이트만으로 보정을 실행하지 않는다.

### 4. 미싱 링크의 repo 자동 발견·연결과 수동 연결

- 제품의 기본 흐름은 정상 링크 해석 → 저장된 연결 재사용 → root 아래 Git 정보로 repo 식별·자동 연결 시도 → 필요한 최초 repo 선택 또는 수동 폴더 지정이다. 두 방식을 한 resolver·저장 계약·연결 UI로 제공하며 자동 탐색 실패가 수동 연결을 막지 않는다. OS 절대경로·로컬 file URL·문서 상대경로를 다루고 HTTP(S)/메일 링크와 문서 내부 앵커는 기존 동작을 유지한다.
- 사용자가 명시적으로 연결한 root 안에서 repo를 발견한다. workspace 바로 아래 repo와 하네스 아래 여러 깊이에 있는 repo를 같은 규칙으로 다루며 clone 폴더명·깊이를 저장소 정체성으로 쓰지 않는다. 하네스 자체가 repo여도 중첩 repo를 계속 발견하고 파일의 repo 경계는 가장 가까운 해당 작업 트리로 구분한다. 이 탐색이 기존 칸반의 프로젝트 등록·소유자 경계를 다시 정의하지 않는다.
- 허용된 폴더 안의 .git 디렉터리/파일 및 관련 설정을 읽고 remote 식별 정보와 checkout 디렉터리 핸들을 대응시킨다. Git 명령이나 네트워크 조회를 실행하지 않으며 대상 파일의 commit·push를 요구하지 않는다. SSH/HTTPS 표기·remote 별칭·여러 remote·fork·gitdir/commondir의 처리 범위는 fixture로 확정하고 식별할 수 없거나 허용 범위 밖 설정이 필요하면 수동 연결로 넘긴다. 설정 파일 전체나 인증 정보를 연결표에 저장하지 않는다.
- 원본 경로가 어느 repo를 뜻하는지 확인하는 단계와 내 PC에서 그 repo를 찾는 단계를 구분한다. 저장된 원본 경로→repo 대응이나 접근 가능한 출처의 Git 정보가 있을 때만 자동 연결을 시도한다. 임의의 옛 절대경로·clone 이름·파일명 일치 또는 탐색 후보 하나만으로 원본 repo를 추측하지 않는다. 출처가 없으면 사용자가 원본 repo 앞 경로와 발견 목록의 repo를 최초 한 번 연결하며 폴더 직접 지정도 선택할 수 있다.
- 원본 repo가 확인되고 대상 checkout이 하나로 정해졌으며 repo 내부 경로의 파일이 실제 존재할 때 자동 연결한다. 같은 repo의 여러 clone/worktree는 사용할 checkout을 선택해 저장하고, 기존 선택에 접근할 수 없다고 다른 checkout으로 자동 대체하지 않는다. repo 내부 구조나 현재 브랜치에 해당 파일이 없으면 파일 부재로 안내하며 다른 repo의 동명 파일을 대신 열지 않는다.
- 수동 연결은 기존 계획을 유지한다. 사용자가 원본 링크의 폴더 앞 경로와 내 디렉터리를 지정하고 남은 하위 경로로 클릭한 파일을 찾을 수 있는지 확인한 뒤 저장한다. Git 정보가 없는 폴더도 연결할 수 있으며 파일 하나의 선택으로 상위 폴더 대응을 추측하거나 없는 파일을 생성하지 않는다. 폴더 선택·권한 요청은 사용자의 연결 동작에서만 수행한다.
- 두 경로 모두 기존 IndexedDB에 출발 문서 프로젝트·정규화한 원본 경로 접두사·대상 디렉터리 핸들을 저장하고 repo 방식은 확인한 repo 식별 정보·선택 checkout을 함께 기록한다. 대상 PC의 절대경로 문자열을 요구하지 않고 원본 Markdown·별도 YAML·Git 공유 설정·agent 설정을 쓰지 않는다. 같은 앞 경로의 이후 링크는 이 공통 연결을 재사용한다.
- 상대 링크는 출발 문서 위치를 반영해 정규화하고 경로 구성요소 경계로 접두사를 비교한다. 더 구체적인 경로를 우선하되 같은 키의 충돌은 확인 없이 덮어쓰지 않는다. 대상은 승인된 연결 폴더 안에 머물며 문서 프로젝트별 연결을 섞지 않는다. 대상 Markdown은 대상 연결의 문서 식별로 앱에서 열고 다른 파일은 기존 다운로드를 유지한다. 연결은 원문·소유자·티켓 상태·작업 배정이나 이동 변환의 검사·쓰기 범위를 바꾸지 않는다.
- root 탐색은 목록을 캐시하고 링크마다 전체 재탐색하지 않는다. 탐색 제외·중첩 깊이/개수 상한·취소·부분 실패·새로고침·유효성 재확인을 설계하며 미완료 탐색을 저장소 부재나 후보 유일성의 증거로 쓰지 않는다. 탐색 중이거나 지원하지 않는 구성에서도 수동 연결로 진행할 수 있다.
- 저장된 연결은 재지정·해제할 수 있다. 권한 해제·폴더 접근 불가·파일 부재·IndexedDB 실패를 구분해 재승인 또는 위치 재지정을 안내한다. 연결과 repo 목록은 같은 사이트·브라우저 프로필의 로컬 상태이며 재실행·앱 업데이트 후 재사용하되 권한과 대상을 재확인한다. 다른 PC로 동기화하지 않고 사이트 데이터 삭제 후에는 재연결한다. 실제 폴더 이동 후 핸들이 계속 유효하다고 보장하지 않는다.
- A/B 비교는 A: 수동 폴더 지정만 사용, B: repo 자동 발견·기존 대응 자동 연결 → 최초 repo 선택 → 실패 시 수동 연결의 통합 흐름으로 정의한다. 같은 허용 root·링크·정답 대상·출처 정보를 사용하고 초기 연결표와 탐색 캐시는 실험별로 격리한다. 최초 사용과 저장 후 재사용을 나눠 오연결 여부·해결률·사용자 선택 횟수·root 연결/초기 탐색 비용·링크 열기 시간을 비교한다. 두 영구 제품 모드나 별도 저장 체계를 만들기 위한 요구가 아니며 비교용 제어와 결과는 격리 검증에서 관리한다.
- AKD-10이 통합 흐름·Git 식별/탐색·연결 저장과 비교용 제어를 맡고 AKD-09가 같은 시나리오의 A/B 결과와 실제 폴더 검증을 확인한다. 이 브라우저 기능은 외부 agent용 설정·연결 파일·스킬/CLI 연동, 원문 링크 재작성, 미싱 이미지의 자동 연결, repo 내부 구조 차이의 자동 추론을 추가하지 않는다. 열람할 대상 폴더 선택은 CLI의 실행 worktree 선택과 별개다. CLI의 이동·PC 경로 보정 및 ID·형식 변환과 독립적이며 현재 승인 범위는 계획·티켓 반영까지다.

### 5. 버전별 형식 정리

- AKL-10/11의 지원 형식 판정 위에 출발 형식·도착 형식·변환 규칙 ID·조건·변경 범위를 가진 마이그레이션 목록을 둔다. 버전 없는 레거시는 확인된 구조로만 분류한다. 앱 버전 증가 자체를 문서 변환 근거로 쓰지 않는다.
- 최초 자동 삭제 후보는 알려진 옛 Progress Board처럼 티켓 본문과 일치하는 중복 생성 섹션이다. 제목만 같은 사용자 섹션, 본문과 모순되는 표, 고유 메모가 섞인 영역은 보존하고 검토 대상으로 표시한다.
- 옛 상태 설명·내장 Ticket Template 등은 확인된 공식 템플릿과 일치하고 고유 정보가 없다는 규칙과 fixture를 확보한 항목만 추가한다. 파싱하지 않는다는 이유로 모든 섹션을 삭제하지 않는다.
- 계획의 결정·조사 근거·질문, 사용자 지시·진행 메모·완료 증거, 알 수 없는 섹션·front matter는 보존한다. 삭제할 섹션뿐 아니라 삭제 후 남는 제목의 앵커 변화도 확인한다. 동명 제목의 앵커 번호가 바뀌는 경우를 포함해 지원 참조가 같은 보존 섹션을 가리키도록 처리하고, 삭제 대상의 안전한 대체나 보존 섹션의 참조 유지가 확실하지 않으면 해당 삭제를 보류한다.
- 누락된 수정일·작성일·Completed at·작업 이력·검증 결과는 현재 시각이나 파일 mtime으로 보충하지 않는다. ID 신규 발급과 확인된 변환 후 형식 표기는 가능하지만 과거 사실 복원과 구분한다. owner 등록·정합화는 현재 폴더에 대한 AKD-06의 별도 명시 작업이며 섹션 정리가 자동 실행하지 않는다. 실제 변환 시각은 복구/변환 기록에만 남긴다.
- owner 등록·정합화, ID 발급·문서 이동·PC 경로 보정·레거시 섹션 정리는 각각 선택 가능한 작업이다. 하나를 원한다고 나머지를 강제로 적용하지 않는다. 재실행은 추가 변경을 만들지 않고, 중간 버전 건너뛰기·미지원 미래 형식·부분 실패를 다룬다.

### 6. 안전한 적용과 사용 흐름

- 문서 이동·owner 등록/정합화·PC 경로 보정은 CLI에서 요청 → 읽기 전용 분석 → 파일별 diff·소유자 변화·미검사/보류 검토 → 명시적 적용 → 재검증 → 결과/복구로 진행한다. agent는 승인된 계획을 도구로 실행하며 추측 치환 스크립트로 우회하지 않는다. ID 발급·형식 정리는 기존 선택형 UI/CLI 범위를 유지하고 미싱 링크의 열람용 연결은 AKD-10이 맡는다.
- 전체 작업의 원본·목적지 상태·의도한 결과·진행 단계를 내구성 있는 journal에 먼저 보존한다. 다중 문서 잠금 순서를 일정하게 하고 각 파일 직전 해시/mtime과 목적지 부재를 재확인한다.
- 이동은 검증한 native CLI 어댑터로만 수행한다. OS rename을 쓰더라도 참조 수정까지 원자적이라고 간주하지 않으며, 복사 후 삭제가 필요하면 목적지 readback·속성 보존과 참조 변경 상태를 확인한 뒤 원본 삭제 직전에도 외부 변경을 재확인한다. 미검증 방식은 적용하지 않고 중간 실패는 부분 완료로 보고하며 자동 재시도·무조건 롤백하지 않는다.
- 복구는 현재 파일이 예상한 상태일 때만 적용해 동료나 외부 편집기의 새 작업을 덮어쓰지 않는다. 다중 파일 원자성이나 Web Lock의 외부 도구 배제를 주장하지 않는다.
- 브라우저에서 유지하는 ID·형식 변환은 appActivity/usePwaDraft·PWA 세션·업데이트 절차에 참여한다. CLI는 브라우저 잠금에 참여한다고 가정하지 않고 native 잠금·파일 재검증·로컬 journal을 사용하며 브라우저 쓰기와 서로 외부 변경으로 취급한다. 브라우저 복구 기록과 CLI의 미해결 기록을 구분해 보존한다.
- 소유자·ID·지원 참조/형식의 순수 분석 계약과 fixture는 공용으로 유지하되 브라우저 이동 어댑터·이동 UI는 만들지 않는다. native symlink·파일 속성과 실제 OS 권한은 CLI에서 별도 검증한다. 브라우저의 미싱 링크 연결표는 CLI에 전달하거나 변환에 사용하지 않는다.
- 신규 문서는 외부 agent가 동봉 스킬·템플릿으로 작성한다. 브라우저/CLI 동등성은 소유자·ID 읽기와 공통 제공하는 ID·형식 변환에 적용하며 CLI 전용 이동·PC 보정의 브라우저 실행을 요구하지 않는다. 브라우저 신규 문서 생성 UI나 CLI 신규 문서 생성 명령은 추가하지 않는다.

### 8. 기본/선택 사용 안내와 스킬·템플릿·도구의 역할 분리

- 기본 사용 안내는 기존 설치 → 논의 → 문서 작성 → 검토·구현 흐름과 선택형 웹 뷰어를 유지한다. 양쪽 README와 스킬의 첫 사용 절차에서 `.ak.config`·`.ak.user`·사용자 등록·@폴더·owner 또는 팀/개인 선택을 요구하지 않으며 일반 docs 예제와 작성·수정 방법을 제공한다.
- 선택 안내는 해당 프로젝트의 공유 `.ak.config`에서 ownerFolders를 한 번 켜고 개인 `.ak.user`에 사용자를 지정하는 흐름과 `docs/@사용자`·owner·컨텍스트 공유를 설명한다. 매 플랜 생성 때 설정 질문을 반복하지 않는다. 두 파일의 역할·공유 여부·우선순위·worktree 상속은 상세 참조에 두고 후속 인수·정합화 도구는 검증 후 안내한다.
- AKD-11이 페이즈 1에서 기본/선택 작성 안내를 함께 제공하고 AKD-09가 후속 기능의 검증된 공개 사용법을 보완한다. 사용 안내를 읽기 위해 후속 이행 절차까지 모두 이해하도록 요구하지 않는다.
- SKILL.md에는 새 문서 작성 때 공통 도구의 판정 결과를 사용하고 명시적 대상·기존 문서 위치와 이력을 보존하는 짧은 진입 절차를 둔다. ownerFolders 분기, 설정 탐색·유효성·우선순위·worktree 상속·번호/owner 판정은 도구와 필요한 참조가 맡는다. 팀/개인 질문, 전체 분기표·명령 스키마를 스킬 본문에 복제하지 않는다.
- assets의 plan/tickets/inventory 템플릿은 기존 본문 구조를 유지하고 문서 상단 `Owner:` 줄은 소유자별 작성 때만 포함한다. 기본 작성에 빈 owner나 불필요한 front matter를 남기지 않는다. references는 owner 의미·헤더 범위·누락/불일치 상태와 필요한 경우에만 읽는 이행 절차를 소유한다. 상세 파싱·판정·재검증·복구는 공통 코드와 CLI가 수행한다.
- AKD-11은 기본 작성·수정에 사용자 설정이나 전체 마이그레이션 지침을 요구하지 않는 경로를 검증한다. AKD-08은 동봉 참조/템플릿/도구의 일치와 정합화가 필요한 경우의 상세 안내 접근을 검증한다. 내용 중복을 줄이되 필요한 근거·보존 조건·검증을 생략하지 않는다.

## 성공을 확인할 방법

- 페이즈 1의 첫 검증은 격리된 repo/workspace/홈에 `.ak.config`·`.ak.user`가 전혀 없는 기본 사용이다. agent가 기존 위치·번호 규칙으로 plan/tickets/inventory를 작성하고 본문·티켓 상태/지시를 수정한 뒤 parser/writer·검증기가 처리하는지 확인한다. 브라우저의 일반 편집도 유지하며 팀/개인 질문·사용자 확인·@폴더/owner/설정 생성 요구가 없어야 한다.
- 홈의 `.ak.user`만 존재, ownerFolders 누락/false/true와 사용자 있음/없음을 교차 검증한다. true와 유효 사용자일 때만 신규 기본 경로에 사용자 폴더·owner를 적용하며 미설정/false는 기존 위치·번호를 유지한다. 활성화 후 끄기, 명시적 대상과 기존 @문서 편집·열람에서도 위치·소유자·이력이 보존되는지 확인한다. 사용자 미설정 안내는 해당 사용자에 의존하는 작업에만 요구한다.
- 공유 .ak.config의 repo > 지정 workspace > 기본값과 개인 .ak.user의 repo > 지정 workspace > 홈을 따로 검증한다. repo의 false가 workspace의 true보다 우선하고 서로 다른 workspace의 설정이 섞이지 않아야 한다. 잘못된 파일에 둔 키·잘못된 값/손상·읽기 실패를 누락/기본값과 구분하고 범용 덮어쓰기를 허용하지 않는다. worktree는 현재 공유 파일과 원래 개인 설정을 구분하며 원래 위치 이동/삭제·독립 clone·detached HEAD·임시 상위 설정을 포함해 현재 worktree 밖 쓰기가 없는지 확인한다.
- ID 없는 기존 문서와 ownerFolders를 켜 작성한 새 docs/@사용자 문서로 페이즈 1을 검증한다. 브라우저는 `.ak.user` 없이 전체·소유자별·미지정 필터를 제공하고 ownerFolders가 없거나 꺼져도 기존 경로 소유자를 유지해야 한다. 필터/재연결은 사용자·문서·배정을 바꾸지 않으며 초기 작성·최소 owner는 ID·이동·레거시 기능에 의존하지 않는다.
- 소유자별 새 plan/tickets/inventory에만 폴더와 같은 owner가 기록되고 UUID 없이도 기존 parser/writer가 본문을 처리·보존하는지 확인한다. `@사용자` 내 owner 없음·다른 owner·일치, 일반 폴더의 정상적인 owner 없음·손상 메타데이터를 구분하고 읽기·필터·상태 변경에서는 owner가 자동 갱신되지 않아야 한다.
- 수동 이동한 문서의 레거시 편입·소유자 불일치 정합화, 확인된 이전 경로의 참조 보정, owner 갱신·재실행·부분 실패/복구를 검증한다. 같은 owner 안의 이동·UUID 없는 레거시·복사본·이전 경로 불명에서 owner만으로 이동 경로 또는 링크 정상 여부를 추측하지 않아야 한다.
- 일반 폴더·기존 루트·여러 사용자·동일 티켓 ID·소유자 변경 fixture로 발견과 필터·실행 범위를 확인한다. 퇴사자/휴가자 폴더의 명시적 인수·반환을 허용하면서 번호·ID·티켓 이력을 보존하고 자동 구현·상태 변경이 없는지 검사한다.
- 사용자별 독립 증가, 하위 폴더 포함 최대값, 빈 폴더의 `01`, 이동한 번호의 보존과 다음 번호, 번호 중복·빈 번호 및 실제 목적지 충돌을 확인한다. 예를 들어 기존 `24`·`25` 문서를 옮긴 사용자 범위의 최대값이 `25`이면 다음 새 문서는 `26`이다. 번호 순서와 최신 지시·의존성이 다른 사례에서 번호만으로 실행 순서를 정하지 않는지 확인한다.
- ID 없는 기존 문서, 기존 front matter, 중복 ID, 복제·다른 checkout, 외부 이동·내용 동시 변경을 검증한다. ID 발급을 두 번 해도 바뀌지 않아야 하며 `.ak.config`·`.ak.user`·owner 없는 기본 사용에서도 선택적 ID 발급·일반 폴더 이동·참조/PC 경로 보정이 소유자 등록을 강제하지 않아야 한다.
- CLI 문서/폴더 이동 전후 링크가 같은 대상을 가리키는지 검사한다. 이미지·앵커·한글/공백·참조식 링크·루트 경로·코드 예제·모호한 텍스트와 쓰기 범위 밖 역참조를 포함하며 적용·추가 확인·보류가 계약과 일치하는지 확인한다.
- 같은 HEAD의 서로 다른 worktree, detached HEAD, `.git` 파일·중첩 repo·symlink, 기존 미커밋 수정과 범위 밖 docs를 두고 현재 지정 범위만 바뀌는지 검사한다. 분석 후 HEAD/원본 변경을 감지하며 다른 worktree 반영이나 Git 이력 수정을 하지 않아야 한다.
- PC 보정은 Mac/Windows 경로·서로 다른 clone 이름/깊이·복수 repo·원본 repo 미상·잘못된 remote 대응·파일 부재·겹친 접두사·드라이브/UNC 차이를 검증한다. 실제 이동 없이 지정 문서의 지원 경로만 바뀌고 재실행은 무변경이어야 한다. JSON 입출력과 종료 코드를 격리 agent가 비대화형으로 사용하며 checkout 선택을 요구하지 않는지 확인한다.
- 서로 다른 clone 이름·깊이·중첩 repo에서 root 탐색 → 확인된 repo 자동 연결 또는 최초 대응 선택 → 실패 시 수동 연결 → 같은 앞 경로 재사용 → 재실행을 검증한다. 복수 checkout·원본 repo 미상·remote 식별 불가·gitdir/commondir 접근 불가·부분 탐색·권한/파일 부재를 포함한다. Git 정보가 없는 폴더도 수동 연결할 수 있어야 한다.
- 상대 링크의 출발 문서 차이·접두사 경계/겹침·프로젝트 격리·취소·재지정/해제·IndexedDB 실패와 원본 Markdown·agent 설정 무변경을 확인한다. 같은 정답 fixture로 A/B를 비교해 오연결과 잘못된 성공 판정이 없는지 먼저 확인한 뒤 해결률·사용자 선택 횟수·탐색/열기 시간을 기록한다. fake handle/OPFS 검증과 격리 native 폴더의 재연결·권한 및 실제 비교 결과를 구분한다.
- 레거시 정리 전후 티켓 ID·상태·진행률·완료 시각·체크리스트·사용자 지시·진행 메모의 파서 결과와 비대상 원문을 비교한다. 동명 제목 중 앞 섹션만 삭제해도 뒤에 남는 섹션의 문서 내부·README 등 지원 참조가 유지되거나 삭제가 보류되는지 확인한다. 파서 결과 동등성만으로 고유 본문 삭제를 정당화하지 않는다.
- 여러 파일 중간 실패, 원본/목적지 외부 변경, 용량/권한/백업 실패, 앱 종료·업데이트·재개를 주입하고 복구가 새로운 편집을 덮어쓰지 않는지 확인한다.
