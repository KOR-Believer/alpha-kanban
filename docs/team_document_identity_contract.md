# 문서 ID·소유자 분석 계약

작성일: 2026-11-01

## 적용 기준

AKD-12의 계약이며 [Owner 규약](team_documents_contract.md#5-문서-상단-owner-한-줄)과 [AKL-10 형식 계약](../skills/implementation-ledger/references/compatibility.md)을 재사용한다. UUID 없는 기본 사용·새 소유자 작성·브라우저 경로 필터는 그대로 유효하다. ID·Owner·형식 정리는 각각 선택하며 이번 페이즈의 변환 결과는 메모리의 원문/예정문/diff다. 실제 파일 적용은 AKD-05/06/07의 책임이다.

## 필드와 유효성

```markdown
# 검색 계획

Ledger-Format: 1
Document-ID: 33cfe3fc-a0ab-4d1e-9b8b-f30501a2bac1
Owner: @alice

## 목표
```

세 필드는 모두 선택이다. H1 뒤의 동일한 헤더만 읽으며, front matter·본문 예제·티켓 안의 동일한 문자열을 필드로 채택하지 않는다. front matter의 title·id·owner·version도 변경하지 않는다.

- `Document-ID`는 하이픈을 포함한 UUID v4이며 임의 생성은 암호학적 `randomUUID`를 사용한다. 경로·번호·소유자·제목·내용 해시로 만들지 않는다. 대소문자 UUID는 같은 ID로 비교하지만 기존 표기를 자동 정규화하지 않는다. nil, 잘못된 variant/version, 중복 필드와 비표준 키는 오류다.
- 유효한 기존 ID는 일반 수정·이동·이름 변경·owner 등록 때 유지한다. 명시적인 복제 요청만 새 UUID로 교체할 수 있다. 잘못된 ID를 누락으로 간주하거나 ID 충돌을 새 번호 자동 발급으로 해소하지 않는다.
- `Ledger-Format`의 지원/거부 판정은 공통 도구를 재사용한다. 선언이 없는 문서는 기존 구조 확인 후 처리하며 ID 추가만으로 형식 선언·Owner·날짜·title을 추가하지 않는다.

## 읽기와 순수 변환

| 현재 입력 | 분석 / 변환 |
| --- | --- |
| ID 없는 레거시 plan/tickets/inventory, 명시적 선택 | 선택한 파일별 UUID 발급 미리보기. 설정·Owner 불필요 |
| 일반 Markdown | 별도로 명시한 경우만 ID 미리보기 대상. 최초 H1/헤더를 식별하지 못하면 보류 |
| 유효 ID 있음 | 발급은 무변경. 이동해도 그대로 유지 |
| 무효/중복 필드, 미지원 형식, 닫히지 않은 front matter | 해당 변환 거부; 원문 보존 |
| `docs/@alice` + Owner 없음 | 레거시 편입/등록 후보. 별도 선택한 owner 변환만 `@alice` 추가 |
| `docs/@alice` + 유효 Owner `@bob` | 이동·인수 정합화 후보. 명시적 owner 변환만 `@alice`로 교체 |
| 폴더와 Owner 일치 | owner 무변경. 과거 경로·참조 정상·구현 허가를 뜻하지 않음 |
| 일반 폴더 + Owner 없음/있음 | 미지정/기록만 있는 미지정. 기존 Owner 보존, 설정으로 배정하지 않음 |
| Owner 무효, 중복 또는 폴더 식별자 무효 | owner 변환 보류. 정상 누락으로 바꾸지 않음 |

원문 문자열의 필요한 헤더 범위만 편집한다. BOM·CRLF/LF·최종 개행·front matter·주석·다른 메타데이터·티켓/사용자 본문·링크와 과거 기록은 바이트에 대응하는 UTF-8 문자열 그대로 보존한다. 혼합 개행은 변환을 거부한다. 헤더를 벗어난 텍스트나 과거 작성일/수정일은 만들거나 정리하지 않는다.

미리보기는 원문과 예정문, 선택 작업, 생성한 ID, 변경 범위를 포함한다. 첫 분석에서 생성한 ID를 계획에 고정하며, 실패 후 재개는 같은 계획의 원문 또는 이미 적용된 예정문과 정확히 일치할 때만 같은 결과를 반환한다. 다른 편집이 끼면 stale로 거부한다. 적용된 결과로 발급을 다시 분석하면 새 UUID 없이 무변경이다. 복제 미리보기도 재개 시 같은 ID를 사용하고 별개의 명시적 복제만 새 ID를 발급한다. 이 데이터는 적용·안전 백업·트랜잭션이 아니다.

## 브라우저 로컬 식별과 충돌

- UUID 인덱스는 연결한 **프로젝트 ID + 파일 UUID** 범위다. 같은 remote, HEAD, 이름 또는 UUID를 가진 독립 clone/worktree를 병합하지 않는다. 브라우저가 Git checkout을 알아냈다고 주장하지 않는다.
- UUID와 로컬 `d_`를 별도 값으로 유지한다. 기존 handle이 실제 같은 파일을 가리키는 이동이면 기존 경로 인덱스가 `d_`와 딥링크·최근 선택·보드 순서를 보존한다. UUID 추가/변경만으로 이 값을 다시 발급하지 않는다.
- 같은 프로젝트에서 둘 이상의 서로 다른 파일에 같은 UUID가 있으면 충돌 집합을 반환한다. 자동 연결·쓰기 대상을 선택하지 않는다. 쓰기 전에는 현재 프로젝트의 탐색 가능한 전체 Markdown 범위를 다시 확인하고 중복이면 거부한다. 기존의 숨김/빌드/Git 디렉터리 제외와 더 구체적인 폴더 연결의 경계는 유지한다. 부분적인 티켓 전용 스캔으로 전체 범위의 유일성을 확정하지 않는다.
- 복사 후 삭제처럼 기존 handle이 끊긴 이동은 UUID 하나만 같아도 자동 재연결하지 않는다. 원래 딥링크는 명시적 재선택 필요로 남고 발견한 파일은 별도 로컬 ID를 갖는다. 같은 UUID의 독립 복제와 이동을 안전하게 구분할 수 없기 때문이다. 파일 없는 기존 기록·순서는 지우거나 새 파일에 이식하지 않는다.
- UUID 없거나 잘못된 파일은 기존 handle 기반 식별로 읽되 UUID 기반 연결에서 제외한다. 같은 번호·슬러그·본문을 대신 키로 사용하지 않는다. 메타데이터 변환과 중복 ID 쓰기 차단은 현재 파일의 해시/mtime·잠금·복구 보호를 대체하지 않는다.

## 후속 경계와 확인

AKD-03은 읽기/owner 비교·ID 인덱스·순수 변환/재개 분석을, AKD-04는 링크 분석을, AKD-05는 실제 적용·복구를, AKD-06은 이동/인수/owner 정합화를, AKD-07은 선택한 ID 발급·형식 정리를 맡는다. owner 일치와 UUID 일치는 이전 경로나 링크 정답의 근거가 아니며 참조 미확정은 후속 분석에서 보류한다. 일반 상대 Markdown 링크를 유지한다.

위 표에 기존 front matter, 손상 헤더, UUID 대소문자/중복, 다른 프로젝트의 동일 ID, handle 유지 이동, 복사 후 삭제, owner 누락/불일치, 미설정 기본 문서와 재실행/외부 변경을 대입해 각각 보존·거부·재선택 결과를 결정할 수 있다. 원문 변경·ID 실발급이나 실제 폴더 이동은 이 문서 작성으로 수행하지 않았다.
