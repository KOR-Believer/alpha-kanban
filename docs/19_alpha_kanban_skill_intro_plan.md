# 스킬과 칸반을 연결하는 소개·설치 안내 계획

작성일: 2026-10-18
수정일: 2026-10-19

## 목표와 이유

처음 방문한 사람이 Alpha Kanban에서 작업의 흐름과 결과를 확인하고, implementation-ledger로 AI와 합의한 범위·질문·구현 결과를 같은 Markdown에 남기는 관계를 이해한다. 첫 화면부터 보드와 스킬의 가치를 함께 보여준다. 기존 사용자는 같은 `/intro`의 설치 안내에서 공식 원본 비교와 스킬 업데이트를 요청한다.

스킬의 가치는 사용자가 무엇을 만들지, 무엇이 바뀌었는지, 어떻게 확인했는지, 어디서 결정해야 하는지 이해하고 참여하는 데 둔다. AI의 다음 세션을 위한 맥락 보존은 부수적인 이점으로 설명한다. 코딩 품질이나 자동 실행을 보장하는 문구는 사용하지 않는다.

초기 전달물은 계획과 실행 티켓이다. 2026-10-18 Mac에서 [AKI-01 시안과 검증 결과](design/aki-01-intro/README.md)를 추가했다. 첫 시안은 스킬만 강조하고 칸반을 부록처럼 보여준다는 사용자 피드백으로 채택하지 않았다. 2026-10-19 사용자가 진행 막대·배속·채팅과 플랜/티켓 통합 창을 포함한 최신 시안을 승인했다. AKI-02에서 기존 shadcn 테마와 한영 전환을 유지해 실제 `/intro`에 적용하고 로컬 검증한다. 배포는 하지 않는다. 실행 상태는 [관련 티켓](20_alpha_kanban_skill_intro_tickets.md)에 기록한다.

## 구현 전 조사

- `/intro`의 H1은 Alpha Kanban이고 주 행동인 시작하기는 `/`로 연결된다. 큰 칸반 예시가 첫 화면에 있으며, 스킬 설치는 하단의 첫 문서가 필요하다면 영역에 있다. 근거: `apps/web/src/IntroPage.tsx`.
- 공통 설치 대화상자는 master의 동봉 스킬 출처, 개인 수정 보존, 전체 폴더 설치 요청을 제공한다. 설치·업데이트 모드 구분과 특정 배포 버전 연결은 없다. 근거: `components/SkillGuide.tsx`.
- 최신 저장소 스킬은 사용자 참여를 우선하고, 기본적으로 티켓 문서 하나에서 시작하며 필요할 때 플랜·인벤토리를 더한다. 이전 개인 설치본을 제품 설명의 기준으로 삼지 않는다. 근거: `skills/implementation-ledger/SKILL.md`.
- 한영 README는 스킬 설치→논의→티켓 초안·검토→구현→업데이트를 중심으로 정리됐고 웹 뷰어는 선택 사항이다. 설치·업데이트 링크는 `https://kanban.giveit2.me/intro#skill`이며 기존 설치본 비교·백업·개인 수정 보존·덮어쓰기 전 확인을 요청한다. 실행·빌드는 [기여 가이드](../CONTRIBUTING.md), 운영 배포는 [배포 문서](deployment.md)로 분리됐다.
- 패키징은 이미 전체 스킬 파일, 12자리 내용 해시, 해시가 붙은 ZIP, `downloads/manifest.json`, `INSTALL.txt`를 만든다. `pwa.config.ts`의 `skillVersion`·`documentFormat`은 null이다. 번들 해시는 의미 있는 스킬 개정 번호나 호환성 선언이 아니다.
- AKL-10은 버전·형식 계약, AKL-12는 버전 고정 배포와 개인 수정 보존 설치, AKL-13은 공통 설치·버전 안내를 담당한다. 조사 시 AKL-10/12는 TODO, AKL-13은 IN_PROGRESS 50%다. 새 계획이 기존 완료 근거나 상태를 대체하지 않는다.
- PWA manifest의 `id`, `scope`, `start_url`은 `/`다. `/intro`는 프로젝트 쿼리·자동 다시 열기와 분리되어 있다. 근거: `apps/web/pwa.config.ts`, `apps/web/src/browser/browserMode.test.tsx`.
- 기존 소개 시안 승인은 이전 구성에 대한 기록이다. 이번 스킬·칸반 연결 개편의 시각 배치 승인으로 간주하지 않는다.

## 2026-10-19 적용 결과

- 최신 시안의 명시적 승인을 받아 실제 `/intro`에 적용했다. 첫 화면의 칸반과 두 진입 행동, 대화 재생과 문서 통합 창, 설치·업데이트 안내를 기존 React·shadcn 테마와 한영 번역으로 구성했다.
- `components/intro/demo.ts`가 가상 티켓·대화·문서 시점의 공통 원본이다. `IntroConversation`은 진행 막대·배속·종료/다시 재생, 파일 선택과 소스 보기를 제공한다. `SkillInstallPanel`은 소개 전용 옵션을 사용하며 Start·빈 프로젝트의 기본 구성을 유지한다.
- 설치와 업데이트의 주소·선택을 함께 유지하고 한영 README의 업데이트 링크를 `#updates`로 맞췄다. 실제 스킬 개정 번호나 호환성 계약은 AKI-03의 기존 의존 작업으로 남는다.
- 로컬 구현·검증 근거는 [AKI-02 적용 검증](design/aki-01-intro/README.md#aki-02-실제-적용-검증)에 연결한다. 공개 배포·푸시·개인 스킬 변경은 하지 않았다.

## 할 일과 선택한 방향

### 1. 고정할 제품 관계와 경로

- Alpha Kanban은 진행 상태·티켓 상세·남은 결정·검증 결과를 한눈에 확인하는 화면이고, implementation-ledger는 AI와 논의한 내용을 그 Markdown에 작성·갱신하는 스킬이다. 어느 한쪽을 부록으로 밀어내지 않는다. AI 작업에 칸반 연결이나 수동 편집을 강제하지 않으며 각각 사용할 수 있다는 설명은 필요한 지점에서 짧게 한다.
- `/`는 현재 PWA 작업 화면으로 유지한다. `/intro`와 주소를 교환하거나 `/`를 홍보 페이지로 바꾸지 않는다. PWA 식별자·시작 주소·워커 수명주기도 바꾸지 않는다.
- `/intro`는 소개와 공식 설치·업데이트 안내의 진입점이다. 공개 앱 링크는 `https://kanban.giveit2.me`를 사용하고 README의 `/intro#skill` 진입을 유지한다. 업데이트 직접 진입점은 `/intro#updates`로 제공하되 `#skill`에서도 두 경로를 선택할 수 있게 한다.
- 한영 README와 소개의 설치·업데이트 정책을 맞춘다. README 전체 구성은 유지하며 실제 배포 출처·앵커·요청문 정책이 바뀌면 관련 부분을 같은 변경에서 갱신한다. 일반 사용자에게 저장소 클론·로컬 실행·빌드를 요구하지 않고 개발·배포 절차는 별도 문서에 둔다.
- 스킬·웹앱·문서 형식·브라우저 저장 구조 버전을 구분한다. 웹이 개인 설치본을 검사하거나 PWA 업데이트가 스킬을 갱신했다고 표현하지 않는다.
- 아래 문구는 Mac 시안 제작의 구체적인 초안이다. 의미와 주요 행동을 유지하며 길이·줄바꿈·세부 표현은 시안에서 검토한다. 한국어 기본과 영어 전환을 함께 제공한다.

### 2. 페이지 구성과 한국어 문구 초안

섹션 순서는 Alpha Kanban 소개와 두 진입 행동 → 첫 화면의 칸반 예시 → AI 논의·티켓 작성·칸반 검토·구현 결과를 잇는 사례 → 스킬 설치·업데이트 → 마무리다. 상단 메뉴는 작업 예시, 스킬 설치·업데이트, GitHub와 언어 선택을 제공한다. 칸반과 스킬의 행동을 각각 명시하며 웹앱 설치와 스킬 설치가 혼동되지 않게 한다. 업데이트는 별도 대형 섹션으로 반복하지 않는다.

#### 첫 화면

- 제품명과 H1: `Alpha Kanban`.
- 가치 설명: `AI와 계획하고, 칸반에서 한눈에 확인하세요.`
- 본문: `implementation-ledger로 AI와 합의한 내용을 티켓으로 남기고, 칸반에서 진행 상황과 구현 결과를 확인하세요.`
- 두 버튼: `칸반 시작하기` → `/`, `스킬 설치하기` → 같은 페이지의 설치 안내에서 처음 설치 모드. 같은 높이와 충분한 대비로 둘 다 명확히 보이게 한다.
- 재방문 링크: 설치 안내의 `기존 스킬 업데이트`. 최신 여부를 확인하지 못한 실행 상태에서는 최신이라고 단정하지 않는다.
- 화면 예시: 간결한 소개 바로 아래에 같은 가상 프로젝트의 실제 조작 가능한 칸반을 배치한다. 데스크톱 첫 화면에 열 제목과 읽을 수 있는 티켓을, 모바일에도 보드 진입과 티켓 일부를 보여준다.

보드를 하단 부록으로 내리거나 `선택적 칸반`이라는 이름으로 가치를 낮추지 않는다. 기존 디자인의 읽기 좋은 문서 중심 배치와 테마를 이어가며 새 장식 카드·가짜 터미널·사적인 프로젝트 캡처를 넣지 않는다. 첫 화면을 큰 문구만으로 채우지 않는다.

#### 작업 기록 예시

제목: `먼저 이야기하고, 함께 읽고, 그다음 만듭니다.`

본문: `처음에는 문서 없이 AI와 아이디어를 나눠 보세요. 방향이 정해지면 플랜과 티켓 초안을 만들고, 열린 질문을 읽으며 결정을 구체화합니다. 결정이 반영된 문서를 다시 확인한 뒤 구현을 요청하세요.`

가상 독서 기록 앱의 Codex 대화를 감상하는 인터랙션으로 보여준다. 단순 단계 설명이나 초안 직후의 구현 요청으로 축약하지 않는다. 문서 작성 전 토론, 사람의 문서 검토, 질문에 대한 재토론과 문서 갱신을 각각 실제 대화로 드러낸다. 이번 사례는 구현에 필요한 질문이 해결된 뒤 진행하며 모든 미래 질문 해소를 스킬의 보편적 강제 규칙으로 바꾸지는 않는다.

| 장면 | 예시 내용 |
| --- | --- |
| 문서 없이 토론 | 독서 기록 앱을 만들고 싶어. 아직 문서나 코드는 작성하지 말고, 기능과 방향부터 토론하자. 여러 대화를 주고받으며 읽은 책 필터와 제목 검색을 구체화한다. |
| 플랜·티켓 초안 | 지금까지의 대화를 토대로 플랜과 티켓 초안을 작성해 줘. 아직 구현하지 마. 이 시점에 처음 문서가 생긴다. |
| 사람이 문서 읽기 | 플랜과 티켓을 읽는다. 플랜의 열린 질문에 필터 선택 유지와 메모 검색 포함 여부가 남아 있음을 확인한다. |
| 질문 논의·문서 갱신 | 질문을 하나씩 설명하고 선택의 영향을 논의한다. 필터는 현재 방문 동안만 유지하고 메모 검색은 이번 범위에서 제외한다. 결정 내용을 플랜·티켓에 반영하도록 요청하고 사람이 다시 읽는다. 질문이 남으면 이 과정을 반복한다. |
| 검토 후 구현 | 열린 질문 섹션을 유지한 채 `없음`을 확인한다. 최종 문서에 문제가 없으면 검토한 티켓을 선행 관계에 맞춰 순서대로 구현하도록 요청한다. |
| 결과 검토·다음 논의 | 휴대폰에서 좁은 검색창을 발견해 필터를 아래로 내리도록 피드백한다. 필요하면 다시 논의하고 관련 문서를 갱신한 뒤 수정·재검증한다. |

처음에는 정지 상태로 시작하고 재생·일시 정지·이전/다음 대화·장면 이동·다시 보기를 제공한다. 대화 시점에 따라 문서 없음, 초안, 열린 질문과 결정 반영, 구현 기록이 일관되게 바뀐다. 언어 전환과 되감기에도 대화와 문서의 시점을 함께 유지한다. 사용자가 읽고 있는 중에는 강제로 다음 메시지로 스크롤하지 않는다.

재생 진행 막대와 경과/전체 시간, 배속 선택을 제공한다. 진행 막대에서 원하는 시점으로 이동하면 재생을 멈추고 대화와 문서를 함께 되돌린다. 재생 대기·재생 중·일시정지·재생 완료를 구분하며 완료 후 다시 재생할 수 있다. 배속 변경이나 일시정지·언어 전환으로 현재 메시지 안의 진행 시간이 초기화되지 않는다.

사용자가 제공한 Codex.app 화면을 참고해 채팅·플랜·티켓을 하나의 창으로 구성한다. 왼쪽은 대화와 읽기 전용 입력창, 오른쪽은 문서 탭·경로·본문·간결한 파일 목록이다. 파일 탭·목록·대화의 문서 링크는 같은 선택과 문서 시점을 공유하고, 초안 생성 전에는 생성된 파일을 보여주지 않는다. 재생 컨트롤은 모의 앱 바깥에 둔다. 실제 캡처·대화 내용은 넣지 않고 기존 가상 독서 프로젝트를 사용한다.

예시는 가상 대화임을 표시하고 실제 채팅 입력이나 AI 실행으로 오해할 컨트롤을 넣지 않는다. 질문 섹션을 삭제하는 것으로 해결을 대신하지 않는다. 티켓마다 수동 지시를 쓰거나 보드에 폴더를 연결해야 AI 작업이 진행되는 것으로 설명하지 않는다. 보드와 Markdown은 단일 예시 데이터를 공유하며 인벤토리 생성을 시작 조건으로 요구하지 않는다.

#### 설치하고 첫 작업 시작

제목: `스킬을 설치하고, 만들고 싶은 것을 이야기하세요.`

본문: `설치 요청문을 Codex에 전달한 뒤, 작업할 프로젝트에서 첫 요청을 시작하세요.`

1. 스킬 설치: 처음 설치와 기존 스킬 업데이트를 구분한다. 공식 출처와 요청문 확인·복사, 직접 설치·배포 파일·소스 보기를 제공한다. 버전 정보는 확인된 배포 계약이 있을 때만 표시한다.
2. 첫 작업 논의: 문서·코드를 쓰지 않고 기능과 범위를 논의하는 요청을 제공한다.
3. 플랜·티켓 초안: 이번 사례의 논의가 충분히 끝난 뒤 플랜과 티켓 초안을 함께 요청한다. 아직 구현하지 않는다.
4. 열린 질문 검토: 사람이 문서를 읽고 질문을 AI와 다시 논의한다. 결정이 반영된 플랜·티켓을 다시 읽고, 질문이 남으면 반복한다.
5. 구현·검토·수정: 질문 해소와 최종 문서 검토 후 순차 구현을 요청한다. 결과에서 바꾸고 싶은 점이 생기면 논의·문서 갱신·수정·재검증을 이어간다.

첫 요청 예시:

```text
$implementation-ledger를 사용해 줘.
독서 기록 앱에 읽은 책 필터와 제목 검색을 넣고 싶어.
우선 기능과 범위를 함께 논의하자. 아직 문서나 코드는 작성하지 마.
```

플랜·티켓 초안 요청 예시:

```text
지금까지의 대화를 토대로 플랜과 티켓 초안을 작성해 줘. 아직 구현하지 마.
```

열린 질문 논의와 결정 반영 요청 예시:

```text
플랜에 남아 있는 열린 질문을 하나씩 설명해 줘.
답에 따라 무엇이 달라지는지 함께 논의하자.
```

```text
방금 결정한 내용을 플랜과 티켓에 반영해 줘. 내가 다시 읽고 확인할게.
```

구현 요청 예시:

```text
플랜과 티켓을 확인했어. 검토한 티켓을 선행 관계에 맞춰 순서대로 구현해 줘.
```

설치 요청 복사 성공: `요청문을 복사했어요. Codex에 붙여넣어 설치를 진행하세요.`

업데이트 요청 복사 성공: `요청문을 복사했어요. Codex에서 기존 설치본과 비교한 뒤 업데이트를 진행하세요.`

작업 요청 복사 성공: `요청문을 복사했어요. 작업할 프로젝트의 Codex 채팅에 붙여넣으세요.`

복사 실패: `요청문을 선택했어요. 직접 복사해 Codex에 붙여넣으세요.`

복사만으로 설치 완료를 표시하지 않는다. 대화상자 닫기·Escape·호출 버튼으로 포커스 복원, 언어 전환 중 선택 모드 유지, 키보드 탭 이동을 기존 공통 UI에 맞춘다. 승인된 시안에서 인라인 또는 모달 표현을 정하되 요청문·배포 데이터의 출처를 중복 구현하지 않는다.

#### 칸반과 작업 기록을 함께 읽기

- 별도 하단 소개가 아니라 첫 화면의 보드와 이어지는 사례에서 설명한다.
- 본문: `칸반에서 전체 진행을 살피고, 티켓을 열어 합의한 범위와 남은 결정, 구현·검증 결과를 확인하세요.`
- 보조 설명: `필요할 때는 보드에서 상태를 바꾸거나 지시를 남길 수도 있습니다.`
- 주 버튼: `칸반 시작하기` → `/`의 기존 명시적 이동 동작.
- 보조 행동: `문서와 보드 비교하기` → 동일 가상 데이터의 보드·Markdown 예시.
- 사용 조건: `로컬 폴더 연결은 데스크톱 Chrome을 기준으로 지원합니다. 웹은 선택한 폴더의 문서를 읽으며, 문서를 서버에 업로드하지 않습니다.`

브라우저 지원과 폴더 권한은 이 사용 지점에서 설명한다. 소개를 읽는 동안 폴더 연결·파일 탐색을 시작하지 않는다. 외부 AI 도구의 데이터 처리까지 보장하는 문구로 넓히지 않는다.

#### 설치 안에 묶는 업데이트 안내와 마무리

설치 영역에서 `처음 설치`와 `기존 스킬 업데이트`를 선택한다. 업데이트 모드의 본문은 `공식 원본과 사용 중인 스킬을 비교하고, 변경 내용을 확인한 뒤 업데이트하세요.`다. 별도 대형 업데이트 홍보 영역은 만들지 않는다.

배포 계약이 연결되면 실제 버전·배포일·주요 변경 2~3개·기존 사용자 영향·문서 조치 필요 여부를 표시하고 `업데이트 요청문 복사`와 `전체 변경 이력`을 제공한다. 상단 메뉴와 재방문 링크로 곧바로 도달할 수 있어야 한다. 그 전에도 README와 같은 공식 스킬 원본과 비교 요청문으로 업데이트 안내를 제공하며, 확인할 수 없는 버전 번호·최신 배지·변경 이력 링크는 노출하지 않는다.

공통 설명: `웹 앱 업데이트와 개인 스킬 업데이트는 별개입니다. 설치한 스킬은 Codex에서 확인하고 업데이트하세요.`

마지막 제목: `AI와 만든 계획을, 한눈에 확인할 수 있는 작업으로.`

마지막 행동: `칸반 시작하기` / `스킬 설치하기`. 소스와 기존 스킬 업데이트 링크를 보조로 제공한다. 각각의 도구를 독립적으로 쓸 수 있으며, 보드 편집을 작업 완료의 필수 단계로 만들지 않는다.

### 3. 설치·업데이트와 실제 배포의 연결

- UI의 버전·배포일·변경 이력·요청문·다운로드는 AKL-10/12가 정의한 동일한 검증된 배포를 가리킨다. 실제 태그·주소·버전이 준비되기 전에는 예시 숫자나 미완성 링크를 공개 화면에 넣지 않는다.
- 배포 계약 연결 전에는 README가 사용하는 공식 `master/skills/implementation-ledger` 출처와 기존 공통 설치 요청문을 유지한다. 설치된 스킬과 해당 원본의 비교·업데이트를 요청할 수 있지만 특정 배포 버전 설치로 표현하지 않는다. 이후 버전 고정 출처로 바뀌면 한영 README의 관련 링크·요청문도 함께 맞춘다.
- 처음 설치는 공식 배포의 전체 스킬 폴더와 참조 파일 설치를 요청한다. 이미 같은 이름의 설치본이 있으면 비교·보존 경로로 전환하도록 요청문에 포함한다.
- 업데이트는 현재 설치본·설치 출처·개인 수정과 대상 배포본을 비교해 변경 내용을 먼저 설명한다. 기존 설치본 전체를 백업하고 개인 수정을 보존하며 덮어쓰기 전에 사용자 확인을 받도록 요청한다. 선택이 필요한 충돌도 설명하고, 완료 후 설치 위치·적용 출처/버전·주요 변경을 보고한다. 프로젝트 문서·코드는 변경하지 않는다. 실제 설치와 복구 검증은 AKL-12/13의 격리 환경 책임이다.
- 웹은 로컬 설치 폴더를 탐색하지 않는다. 현재 설치 버전, 최신 설치 완료, 업데이트 필요 여부를 추측해 배지로 표시하지 않는다.
- 온라인에서 현재 배포를 확인한 경우와 오프라인·조회 실패로 페이지에 포함된 배포만 아는 경우를 구분한다. 후자는 최신 판정을 하지 않고 확인할 수 있는 배포 정보와 다시 확인 동작을 제공한다. 웹앱 업데이트나 설치를 강제로 유발하지 않는다.
- 현재 PWA는 해시 고정 ZIP 하나를 precache한다. 최신 확인 자료와 버전 고정 파일의 캐시 정책을 기존 PWA 계약 안에서 연결하고 오프라인에 존재하지 않는 파일을 제공한다고 약속하지 않는다.

업데이트 요청문 형식 초안은 아래와 같다. 대괄호는 제품에 그대로 노출할 값이 아니라 검증된 배포 데이터로 채울 설계 표기다.

```text
implementation-ledger를 아래 공식 배포 버전으로 업데이트해줘.

대상 버전: [배포 버전]
배포 위치: [해당 버전의 배포 URL]

현재 설치본의 위치와 출처를 확인하고, 배포본과 비교해 변경 내용을 알려줘.
SKILL.md뿐 아니라 references, assets, scripts, agents를 포함한 전체 폴더를 대상으로 해줘.
기존 설치본 전체를 백업하고 개인 수정은 보존해. 덮어쓰기 전에는 내 확인을 받아.
충돌 때문에 선택이 필요한 부분은 설명해줘. 프로젝트 문서나 코드는 변경하지 마.

완료 후 설치 위치, 적용한 출처와 버전, 주요 변경 내용을 알려줘.
```

### 4. 기존 티켓과 Mac 작업의 연결

| 책임 | 이번 작업과의 관계 |
| --- | --- |
| AKL-10 | 스킬·형식 버전과 변경 이력 계약의 기존 원장. 새 버전 규칙을 중복 정의하지 않는다. |
| AKL-12 | 고정 배포·설치본 비교·백업·복구·전체 폴더 설치의 기존 원장. |
| AKL-13 | Start/빈 프로젝트/소개가 공유하는 설치 요청·버전 안내의 기존 원장. 공통 동작은 이쪽에서 재사용한다. |
| AKL-14/15 | 이전 디자인·소개 적용의 근거. 아래 AKI 티켓은 새 제품 관점의 변경분을 담당하며 과거 완료 기록을 다시 쓰지 않는다. |
| AKI-01 | Mac 디자인 하네스에서 새로운 시안과 적용 판단을 얻는다. 배포 계약 작업과 독립적으로 시작할 수 있다. |
| AKI-02 | 승인된 구성·문구·첫 화면의 보드와 스킬을 잇는 작업 흐름을 `/intro`에 적용한다. 기존 검증된 설치 안내로도 설명 개편을 진행할 수 있다. |
| AKI-03 | 실제 배포 계약과 공통 안내가 준비되면 `/intro`의 설치·업데이트 진입 및 상태를 연결한다. AKL-13과 같은 변경에서 처리하더라도 각 티켓의 결과만 기록한다. |

Mac 담당자는 최신 master를 반영한 뒤 저장소 스킬·AGENTS·한영 README·선택 티켓·연결 플랜부터 읽고, 위 조사 커밋 이후 관련 변경만 다시 확인한다. AKI-01의 시안부터 진행하고 AKI-02는 검토 결과를 반영한다. AKI-03은 AKL-10/12/13의 배포·설치 검증 결과가 준비돼야 완료할 수 있다. 기존 디자인의 색상·폰트·공통 UI를 이어가고 첫 화면에서 보드와 스킬의 가치를 함께 드러낸다. 개인 환경의 하네스 경로를 추측하거나 새 도구 설치를 필수화하지 않는다.

후속 구현에서 공통 컴포넌트 규칙이 달라지면 AGENTS의 해당 안내를 같은 변경에서 맞춘다. 과거 디자인 문서는 이력으로 남기고 새 시안·승인·검증 결과는 저장소 상대경로나 지속적으로 접근할 수 있는 공개 참조로 연결한다. 개인 Mac 경로·세션 ID·임시 미리보기 URL·추적하지 않는 캡처 링크를 커밋하지 않는다. 이번 문서 PR의 검토·머지는 새 시안 승인·실제 구현·배포 완료가 아니다.

## 성공을 확인할 방법

- 처음 방문자는 첫 화면에서 칸반으로 확인하는 정보와 스킬이 만드는 기록의 관계를 이해하며, 칸반 시작과 스킬 설치 행동에 모두 도달한다. 폴더 연결 없이도 설치 요청과 첫 작업 요청을 읽을 수 있다.
- 기존 사용자는 상단 링크에서 업데이트 안내로 직접 이동해 실제 대상 버전·변경 내용·요청문이 같은 배포를 가리키는지 확인한다.
