# 스킬 중심 소개와 설치·업데이트 안내 계획

작성일: 2026-10-18
수정일: 2026-10-18

## 목표와 이유

처음 방문한 사람이 implementation-ledger를 핵심 제품으로 이해하고 설치한 뒤, AI와 작업 범위·완료 기준을 정하고 구현·검토까지 이어간다. 기존 사용자는 같은 `/intro`에서 공식 배포본의 변경 내용을 확인하고 자신의 설치본 업데이트를 요청한다. Alpha Kanban 웹은 같은 Markdown을 사람이 편하게 읽고 필요할 때 상태·지시를 남기는 선택적 도구로 소개한다.

스킬의 가치는 사용자가 무엇을 만들지, 무엇이 바뀌었는지, 어떻게 확인했는지, 어디서 결정해야 하는지 이해하고 참여하는 데 둔다. AI의 다음 세션을 위한 맥락 보존은 부수적인 이점으로 설명한다. 코딩 품질이나 자동 실행을 보장하는 문구는 사용하지 않는다.

이번 전달물은 계획과 실행 티켓이다. 디자인 하네스와 개발 환경이 있는 Mac에서 시안·구현·제품 검증을 이어간다. 실행 상태는 [관련 티켓](20_alpha_kanban_skill_intro_tickets.md)에 기록한다.

## 확인한 현재 상태

- `/intro`의 H1은 Alpha Kanban이고 주 행동인 시작하기는 `/`로 연결된다. 큰 칸반 예시가 첫 화면에 있으며, 스킬 설치는 하단의 첫 문서가 필요하다면 영역에 있다. 근거: `apps/web/src/IntroPage.tsx`.
- 공통 설치 대화상자는 master의 동봉 스킬 출처, 개인 수정 보존, 전체 폴더 설치 요청을 제공한다. 설치·업데이트 모드 구분과 특정 배포 버전 연결은 없다. 근거: `components/SkillGuide.tsx`.
- 최신 저장소 스킬은 사용자 참여를 우선하고, 기본적으로 티켓 문서 하나에서 시작하며 필요할 때 플랜·인벤토리를 더한다. 이전 개인 설치본을 제품 설명의 기준으로 삼지 않는다. 근거: `skills/implementation-ledger/SKILL.md`.
- 한영 README는 스킬 설치→논의→티켓 초안·검토→구현→업데이트를 중심으로 정리됐고 웹 뷰어는 선택 사항이다. 설치·업데이트 링크는 `https://kanban.giveit2.me/intro#skill`이며 기존 설치본 비교·백업·개인 수정 보존·덮어쓰기 전 확인을 요청한다. 실행·빌드는 [기여 가이드](../CONTRIBUTING.md), 운영 배포는 [배포 문서](deployment.md)로 분리됐다.
- 패키징은 이미 전체 스킬 파일, 12자리 내용 해시, 해시가 붙은 ZIP, `downloads/manifest.json`, `INSTALL.txt`를 만든다. `pwa.config.ts`의 `skillVersion`·`documentFormat`은 null이다. 번들 해시는 의미 있는 스킬 개정 번호나 호환성 선언이 아니다.
- AKL-10은 버전·형식 계약, AKL-12는 버전 고정 배포와 개인 수정 보존 설치, AKL-13은 공통 설치·버전 안내를 담당한다. 조사 시 AKL-10/12는 TODO, AKL-13은 IN_PROGRESS 50%다. 새 계획이 기존 완료 근거나 상태를 대체하지 않는다.
- PWA manifest의 `id`, `scope`, `start_url`은 `/`다. `/intro`는 프로젝트 쿼리·자동 다시 열기와 분리되어 있다. 근거: `apps/web/pwa.config.ts`, `apps/web/src/browser/browserMode.test.tsx`.
- 기존 소개 시안 승인은 보드 중심의 이전 구성에 대한 기록이다. 이번 스킬 중심 개편의 시각 배치 승인으로 간주하지 않는다.

## 할 일과 선택한 방향

### 1. 고정할 제품 관계와 경로

- implementation-ledger가 핵심이며 설치 후 AI 채팅에서 논의·기록·구현·검토까지 진행할 수 있다. 칸반 연결을 필수 완료 단계로 넣지 않는다.
- `/`는 현재 PWA 작업 화면으로 유지한다. `/intro`와 주소를 교환하거나 `/`를 홍보 페이지로 바꾸지 않는다. PWA 식별자·시작 주소·워커 수명주기도 바꾸지 않는다.
- `/intro`는 소개와 공식 설치·업데이트 안내의 진입점이다. 공개 앱 링크는 `https://kanban.giveit2.me`를 사용하고 README의 `/intro#skill` 진입을 유지한다. 업데이트 직접 진입점은 `/intro#updates`로 제공하되 `#skill`에서도 두 경로를 선택할 수 있게 한다.
- 한영 README와 소개의 설치·업데이트 정책을 맞춘다. README 전체 구성은 유지하며 실제 배포 출처·앵커·요청문 정책이 바뀌면 관련 부분을 같은 변경에서 갱신한다. 일반 사용자에게 저장소 클론·로컬 실행·빌드를 요구하지 않고 개발·배포 절차는 별도 문서에 둔다.
- 스킬·웹앱·문서 형식·브라우저 저장 구조 버전을 구분한다. 웹이 개인 설치본을 검사하거나 PWA 업데이트가 스킬을 갱신했다고 표현하지 않는다.
- 아래 문구는 Mac 시안 제작의 구체적인 초안이다. 의미와 주요 행동을 유지하며 길이·줄바꿈·세부 표현은 시안에서 검토한다. 한국어 기본과 영어 전환을 함께 제공한다.

### 2. 페이지 구성과 한국어 문구 초안

섹션 순서는 가치 → 작업 기록 예시 → 설치와 첫 작업 → 선택적 칸반 → 버전·업데이트 → 마무리다. 상단 메뉴는 사용 예시, 설치·업데이트, GitHub, 칸반 열기를 제공한다. 기존 브랜드·언어 선택·PWA 메뉴를 유지하면서 웹앱 설치와 스킬 설치가 혼동되지 않게 한다.

#### 첫 화면

- 작은 소개: `implementation-ledger · AI와 함께 개발하는 스킬`
- 제목: `AI가 무엇을 만들고, 어디까지 끝냈는지 분명하게.`
- 본문: `AI와 합의한 작업 범위, 구현 결과, 검증 내용을 프로젝트의 Markdown에 남깁니다. 필요한 결정에 참여하고, 기록을 보며 다음 작업을 이어가세요.`
- 주 버튼: `스킬 설치하기` → 같은 페이지의 설치 안내에서 처음 설치 모드.
- 보조 버튼: `실제 작업 예시 보기` → 예시 섹션.
- 재방문 링크: `이미 사용 중인가요? 최신 버전과 업데이트 안내 →` → 업데이트 영역. 최신 여부를 확인하지 못한 실행 상태에서는 최신이라고 단정하지 않는다.
- 관계 설명: `스킬만으로 계획·구현·검토를 이어갈 수 있습니다. 칸반은 기록을 한눈에 보고 싶을 때 사용하세요.`

큰 보드 예시는 칸반 소개로 옮긴다. 기존 디자인의 읽기 좋은 문서 중심 배치와 테마를 이어가며 새 장식 카드·가짜 터미널·사적인 프로젝트 캡처를 넣지 않는다.

#### 작업 기록 예시

제목: `대화에서 정한 내용을, 확인할 수 있는 작업 기록으로.`

본문: `무엇을 만들지, 무엇을 확인해야 끝나는지, 어떤 결정이 남았는지 함께 정리합니다. 구현 후에는 변경 결과와 검증 내용을 같은 기록에 남깁니다.`

가상 책갈피 프로젝트의 한 가지 작업을 요청 → 티켓 → 구현 후 기록으로 보여준다.

| 장면 | 예시 내용 |
| --- | --- |
| 요청 | 읽은 책만 모아보고 싶어. 제목 검색도 같이 됐으면 좋겠어. |
| 합의한 범위 | 읽은 책 필터와 제목 검색을 함께 적용하고, 결과가 없으면 안내한다. |
| 완료 기준 | 두 조건을 함께 적용해도 조건에 맞는 책만 표시된다. |
| 필요한 결정 | 필터 선택을 다음 방문에도 유지할까요? |
| 구현 후 기록 | 구현 결과·실제로 수행한 검증·남은 확인을 각각 구분한다. |

예시는 가상임을 표시한다. 필요한 결정은 답변 전 장면, 구현 후 기록은 그 결정이 반영된 후속 장면으로 구분한다. 미결정 상태에서 완료된 것처럼 보이게 하지 않는다. 보드와 Markdown을 함께 제시할 때는 기존 `IntroDemoBoard`의 단일 예시 데이터 원칙을 유지한다. 문서 세 종류를 모두 만드는 것을 시작 조건으로 설명하지 않는다.

#### 설치하고 첫 작업 시작

제목: `스킬을 설치하고, 만들고 싶은 것을 이야기하세요.`

본문: `설치 요청문을 Codex에 전달한 뒤, 작업할 프로젝트에서 첫 요청을 시작하세요.`

1. 스킬 설치: 처음 설치와 기존 스킬 업데이트를 구분한다. 공식 출처와 요청문 확인·복사, 직접 설치·배포 파일·소스 보기를 제공한다. 버전 정보는 확인된 배포 계약이 있을 때만 표시한다.
2. 첫 작업 논의: 문서·코드를 쓰지 않고 기능과 범위를 논의하는 요청을 제공한다.
3. 티켓 초안·검토: 합의한 범위와 완료 기준을 티켓으로 작성하고, 사용자가 이번 구현에 필요한 질문을 검토해 결정한 내용을 반영한다. 플랜·인벤토리는 필요한 경우에만 추가한다.
4. 구현·검토: 검토한 티켓으로 구현을 요청하고 결과·검증·남은 확인을 읽는다. 여기서 기본 흐름이 완결된다.

첫 요청 예시:

```text
$implementation-ledger를 사용해 줘.
독서 기록 앱에 읽은 책 필터와 제목 검색을 넣고 싶어.
우선 기능과 범위를 함께 논의하자. 아직 문서나 코드는 작성하지 마.
```

티켓 초안 요청 예시:

```text
$implementation-ledger로 지금까지 합의한 내용을 티켓 초안으로 작성해 줘.
여러 티켓이 공유하는 설계가 필요하면 플랜도 추가해 줘.
작업 범위와 완료 기준, 내가 확인하거나 결정해야 할 사항을 구분해 줘.
아직 구현하지 마.
```

구현 요청 예시:

```text
검토한 티켓을 선행 관계에 맞춰 순서대로 구현해 줘.
최신 사용자 지시와 관련된 열린 질문을 먼저 확인하고,
완료 기준을 검증한 결과와 남은 작업을 티켓에 기록해 줘.
```

설치 요청 복사 성공: `요청문을 복사했어요. Codex에 붙여넣어 설치를 진행하세요.`

업데이트 요청 복사 성공: `요청문을 복사했어요. Codex에서 기존 설치본과 비교한 뒤 업데이트를 진행하세요.`

작업 요청 복사 성공: `요청문을 복사했어요. 작업할 프로젝트의 Codex 채팅에 붙여넣으세요.`

복사 실패: `요청문을 선택했어요. 직접 복사해 Codex에 붙여넣으세요.`

복사만으로 설치 완료를 표시하지 않는다. 대화상자 닫기·Escape·호출 버튼으로 포커스 복원, 언어 전환 중 선택 모드 유지, 키보드 탭 이동을 기존 공통 UI에 맞춘다. 승인된 시안에서 인라인 또는 모달 표현을 정하되 요청문·배포 데이터의 출처를 중복 구현하지 않는다.

#### 선택적 칸반 소개

- 제목: `진행 상황을 한눈에 보고 싶다면, Alpha Kanban.`
- 본문: `스킬이 작성한 Markdown을 보드로 확인하세요. 프로젝트 폴더를 열면 티켓 상태와 진행 내용을 함께 볼 수 있습니다.`
- 보조 설명: `필요할 때는 보드에서 상태를 바꾸거나 지시를 남길 수도 있습니다.`
- 주 버튼: `칸반 열기 ↗` → `/`의 기존 명시적 이동 동작.
- 보조 행동: `문서와 보드 비교하기` → 동일 가상 데이터의 보드·Markdown 예시.
- 사용 조건: `로컬 폴더 연결은 데스크톱 Chrome을 기준으로 지원합니다. 웹은 선택한 폴더의 문서를 읽으며, 문서를 서버에 업로드하지 않습니다.`

브라우저 지원과 폴더 권한은 이 사용 지점에서 설명한다. 소개를 읽는 동안 폴더 연결·파일 탐색을 시작하지 않는다. 외부 AI 도구의 데이터 처리까지 보장하는 문구로 넓히지 않는다.

#### 업데이트 안내와 마무리

제목: `implementation-ledger는 계속 개선됩니다.`

본문: `새 버전의 변경 내용을 확인하고, 사용 중인 스킬을 업데이트하세요.`

배포 계약이 연결되면 실제 버전·배포일·주요 변경 2~3개·기존 사용자 영향·문서 조치 필요 여부를 표시하고 `업데이트 요청문 복사`와 `전체 변경 이력`을 제공한다. 상단 메뉴와 재방문 링크로 곧바로 도달할 수 있어야 한다. 그 전에도 README와 같은 공식 스킬 원본과 비교 요청문으로 업데이트 안내를 제공하며, 확인할 수 없는 버전 번호·최신 배지·변경 이력 링크는 노출하지 않는다.

공통 설명: `웹 앱 업데이트와 개인 스킬 업데이트는 별개입니다. 설치한 스킬은 Codex에서 확인하고 업데이트하세요.`

마지막 제목: `다음 작업부터, 함께 확인할 수 있는 기록을 남기세요.`

마지막 행동: `스킬 설치하기` / `기존 스킬 업데이트`. 소스와 변경 이력의 GitHub 링크를 보조로 제공한다. 웹을 열어야 시작이 끝나는 구조로 되돌리지 않는다.

### 3. 설치·업데이트와 실제 배포의 연결

- UI의 버전·배포일·변경 이력·요청문·다운로드는 AKL-10/12가 정의한 동일한 검증된 배포를 가리킨다. 실제 태그·주소·버전이 준비되기 전에는 예시 숫자나 미완성 링크를 공개 화면에 넣지 않는다.
- 배포 계약 연결 전에는 README가 사용하는 공식 `master/skills/implementation-ledger` 출처와 기존 공통 설치 요청문을 유지한다. 설치된 스킬과 해당 원본의 비교·업데이트를 요청할 수 있지만 특정 배포 버전 설치로 표현하지 않는다. 이후 버전 고정 출처로 바뀌면 한영 README의 관련 링크·요청문도 함께 맞춘다.
- 처음 설치는 공식 배포의 전체 스킬 폴더와 참조 파일 설치를 요청한다. 이미 같은 이름의 설치본이 있으면 비교·보존 경로로 전환하도록 요청문에 포함한다.
- 업데이트는 현재 설치본·설치 출처·개인 수정과 대상 배포본을 비교해 변경 내용을 먼저 설명한다. 기존 설치본 전체를 백업하고 개인 수정을 보존하며 덮어쓰기 전에 사용자 확인을 받도록 요청한다. 선택이 필요한 충돌도 설명하고, 완료 후 설치 위치·적용 출처/버전·주요 변경을 보고한다. 프로젝트 문서·코드는 변경하지 않는다. 실제 설치와 복구 검증은 AKL-12/13의 격리 환경 책임이다.
- 웹은 로컬 설치 폴더를 탐색하지 않는다. 현재 설치 버전, 최신 설치 완료, 업데이트 필요 여부를 추측해 배지로 표시하지 않는다.
- 온라인에서 현재 배포를 확인한 경우와 오프라인·조회 실패로 페이지에 포함된 배포만 아는 경우를 구분한다. 후자는 최신 판정을 하지 않고 확인할 수 있는 배포 정보와 다시 확인 동작을 제공한다. 웹앱 업데이트나 설치를 강제로 유발하지 않는다.
- 현재 PWA는 해시 고정 ZIP 하나를 precache한다. 최신 확인 자료와 버전 고정 파일의 캐시 정책을 기존 PWA 계약 안에서 연결하고 오프라인에 존재하지 않는 파일을 제공한다고 약속하지 않는다.

업데이트 요청문 형식 초안은 아래와 같다. 대괄호는 제품에 그대로 노출할 값이 아니라 검증된 배포 데이터로 채울 설계 표기다.

```text
implementation-ledger를 아래 공식 배포 버전으로 업데이트해줘.

대상 버전: [배포 버전]
배포 위치: [해당 버전의 배포 URL]

현재 설치본의 위치와 출처를 확인하고, 배포본과 비교해 변경 내용을 알려줘.
SKILL.md뿐 아니라 references, assets, scripts, agents를 포함한 전체 폴더를 대상으로 해줘.
기존 설치본 전체를 백업하고 개인 수정은 보존해. 덮어쓰기 전에는 내 확인을 받아.
충돌 때문에 선택이 필요한 부분은 설명해줘. 프로젝트 문서나 코드는 변경하지 마.

완료 후 설치 위치, 적용한 출처와 버전, 주요 변경 내용을 알려줘.
```

## 성공을 확인할 방법

- 처음 방문자는 첫 화면에서 스킬이 핵심이고 칸반이 선택적임을 설명할 수 있으며, 폴더 연결 없이 설치 요청과 첫 작업 요청에 도달한다.
- 기존 사용자는 상단 링크에서 업데이트 안내로 직접 이동해 실제 대상 버전·변경 내용·요청문이 같은 배포를 가리키는지 확인한다.
- 한영 README에서 /intro#skill로 들어와 설치와 업데이트 양쪽에 도달하며 /intro#updates 직접 진입도 동작한다. 배포 계약 연결 전의 원본 비교 안내와 연결 후의 고정 버전 안내를 각각 확인하고, README·화면·복사 요청문의 출처와 덮어쓰기 확인 정책이 일치해야 한다.
- Mac Chrome에서 1440×900과 390×844, 한국어·영어의 섹션 순서·줄바꿈·가로 넘침·초점·앵커·설치/업데이트 진입·복사 성공 및 거부 fallback을 확인한다. 실제 제품 캡처를 시안과 비교하고 결과를 티켓에 남긴다.
- `/intro` 직접 진입·새로고침·뒤로가기와 루트 자동 다시 열기 on/off를 검증한다. `/`의 작업 화면 및 PWA `id`·`scope`·`start_url`이 유지되고 소개에서 프로젝트 쿼리·폴더 권한 요청·문서 쓰기·AI 실행이 발생하지 않아야 한다.
- 수정 범위에 맞춰 `browser/browserMode.test.tsx`, `i18n/uiCopy.test.ts`, `i18n/i18n.test.tsx`, `pwa/contracts.test.ts`와 관련 테스트를 보강한다. `pnpm test`, `pnpm typecheck`, `pnpm build`로 실제 구현을 검증한다. UI 개편만으로 전체 PWA 복구 검증을 반복하지 않고, 자산/캐시 계약을 바꾼 경우 해당 오프라인·업데이트 경로를 추가 검증한다.
- 설치 요청·배포 자료와 격리 설치 결과의 일치는 AKL-12/13 증거를 참조한다. 브라우저에서 복사한 사실만으로 설치 검증을 통과 처리하지 않는다.
- 현재 문서 작업은 strict ledger 검사, 링크·의존 티켓·실제 코드 위치·사용자 요구 대조와 docs-only diff로 검증한다. 제품 테스트는 후속 구현에서 수행한다.

## 확인·결정이 필요한 사항

- Mac에서 만들 새 시안의 배치·카피·상호작용을 적용안으로 채택할지 사용자 검토가 필요하다. 현재 이해는 이 문서의 구성·문구를 시안의 출발점으로 삼는 것이며, 검토 결과가 AKI-02/03의 실제 UI 적용을 결정한다. 이전 AKL-14 승인을 새 시안의 승인으로 재사용하지 않는다.
