# Alpha Kanban 설치형 PWA와 오프라인 수명 관리 계획

작성일: 2026-10-18
수정일: 2026-10-18

## 목표와 이유

- Chrome에서 Alpha Kanban을 아이콘과 독립된 창을 가진 앱으로 설치하고, 최초 온라인 준비가 끝나면 인터넷 없이 다시 실행해 로컬 문서를 읽고 수정한다.
- 새 버전을 받을 때 입력과 파일 저장을 중단시키지 않고, 폴더 연결·사용자 설정·복구 기록을 보존한다.
- 잘못된 서비스 워커가 옛 화면을 계속 제공하거나 기능 폐기 후에도 등록된 채 남는 상황에 대비해 교체·복구·퇴역 절차를 처음부터 마련한다.
- 2026-10-18 후속 요청으로 AKP-01부터 구현을 승인했다. 폴더 연결·사용자 설정을 보존하고 격리된 로컬 정적 빌드에서 검증한다. 개인 스킬, DNS와 공개 배포는 변경하지 않는다.

## 영향 범위

- Repository: `alpha-kanban`
- `apps/web`: 설치 정보, 오프라인 앱 파일, 업데이트 안내, 입력·저장 보호, 앱 복구 진입점
- `apps/web/src/browser`: 기존 폴더 참조·설정·복구 기록 보존과 저장 구조 변경 처리
- `apps/web/vite.config.ts`, `apps/web/public-browser`, `scripts`: 정적 배포물·업데이트 정보·서비스 워커·복구 산출물
- `README.md`, `AGENTS.md`, `docs`: 운영·폐기 절차와 실제 Chrome 검증 기록
- 실행 티켓: [16_alpha_kanban_pwa_tickets.md](16_alpha_kanban_pwa_tickets.md)
- 선행 제품: [로컬 파일 기반 정적 웹 전환 계획](13_alpha_kanban_browser_local_plan.md), [AKL 실행 티켓](14_alpha_kanban_browser_local_tickets.md)

## 구현 전 확인한 상태

- 조사 기준은 브라우저 전환 작업 브랜치의 `c00de3b`다. `apps/web/vite.config.ts`와 앱 진입 코드에는 설치 manifest와 서비스 워커 등록이 없다. 현재 탭을 계속 사용하는 것과 브라우저를 닫은 뒤 오프라인으로 재실행하는 것은 다르다.
- `BrowserRepository`가 파일 핸들로 Markdown을 읽고 쓰므로 문서 처리에는 Node API가 필요 없다. 다만 최초 앱 로딩·배포 파일 받기는 HTTP 요청이며, 사용자가 허용한 외부 이미지와 GitHub 링크도 별도 네트워크 기능이다.
- `apps/web/src/browser/storage.ts`의 IndexedDB `alpha-kanban.browser.v1`에는 폴더·프로젝트·문서 참조, 최근 선택, 보드 순서와 저장 복구 기록이 들어간다. 언어·문서 필터·정렬·상세창 크기 등의 보기 설정은 localStorage에도 있다.
- `BrowserRepository.write()`는 쓰기 전 원문·예정 결과를 보존하고 파일 쓰기 종료 후 재읽기로 검증한다. 복구 기록은 앱 업데이트용 캐시가 아니므로 정리 대상으로 삼지 않는다.
- Raleway와 Pretendard는 자체 배포 파일이다. Pretendard의 필요한 글자 묶음만 받는 현재 방식은 방문하지 않은 화면·글자의 오프라인 표시까지 보장하지 않는다.
- `apps/web/public-browser/_headers`는 현재 `connect-src 'none'`이다. 업데이트 정보 조회와 앱 자산 확보를 위해 동일 출처 통신 허용 범위를 검토해야 한다.
- `scripts/package-browser-assets.mjs`의 bundle version은 내용 해시다. 스킬 개정 번호·문서 형식·웹앱 호환 범위는 기존 AKL-10~13의 미완료 작업이며 PWA가 대신 정의하지 않는다.

## 할 일과 선택한 방향

### 1. 설치, 서비스 워커, 버전 관리의 역할

| 역할 | 담당 | 경계 |
| --- | --- | --- |
| 앱 이름·아이콘·시작 URL·독립된 창 | Web App Manifest와 Chrome 설치 기능 | 서비스 워커 없이도 설치 가능. Electron 런타임이나 Node 권한을 얻는 것은 아님 |
| 인터넷 없이 앱을 새로 열기 | 서비스 워커와 완결된 앱 자산 캐시 | 최초 온라인 준비 이후에 제공 |
| 로컬 폴더 탐색·Markdown 저장 | 기존 웹앱의 BrowserRepository | 워커로 옮기거나 문서 복제본을 원장으로 만들지 않음 |
| 웹앱 새 배포 확인·적용 안내 | 웹앱의 업데이트 제어 코드와 배포 정보 | 워커는 새 파일 준비·전환을 수행하며 제품 정책을 대신하지 않음 |
| 스킬·문서 형식 호환 판단 | AKL-10~13의 공통 계약과 앱·설치 도구 | 개인 설치 스킬을 추정·자동 수정하지 않음 |
| 상시 폴더 감시·AI 실행 | 이번 범위 없음 | 워커를 항상 켜진 로컬 서버나 에이전트로 취급하지 않음 |

사용자는 후속 답변에서 전체 오프라인 지원을 원한다고 밝혔다. 따라서 이 계획은 설치만 제공하는 안이 아니라 서비스 워커로 앱의 오프라인 재실행까지 지원하는 안이다. 워커 필요 여부를 미결정 사항으로 되돌리지 않는다.

### 2. 설치와 오프라인 지원의 범위

- 데스크톱 Chrome을 검증 대상으로 유지한다. HTTPS 정적 배포, 안정적인 manifest `id`, `start_url`, `scope`, `display: standalone`, 앱 이름과 설치 아이콘을 제공한다. manifest의 앱 식별자는 배포 버전마다 바꾸지 않는다.
- 2026-10-18 사용자 결정으로 최초 정식 설치 주소는 `https://kanban.giveit2.me`로 확정한다. 이 출처의 연결·검증을 마친 뒤 정식 설치를 안내하고 임시 호스팅 주소와 preview는 별도 검증용으로 구분한다. 주소 결정은 구현·DNS 연결·공개 배포 승인이 아니다.
- 설치 가능 이벤트를 받은 경우에만 앱 안에서 설치 동작을 제공한다. 이미 설치됐거나 이벤트가 없는 경우 고장 난 버튼·반복 팝업을 만들지 않고 실제 가능한 브라우저 설치 경로를 안내한다. 설치 완료와 오프라인 준비 완료를 구분한다.
- 오프라인 준비 대상은 HTML, 실행에 필요한 모든 JS/CSS 청크, 아이콘, 지원하는 한영 표시의 폰트 글자 묶음, 로컬 사용 안내와 해당 배포의 스킬 자료다. ZIP은 해시로 고정된 한 배포본만 포함하고 동일 자료의 별칭 파일을 중복 저장하지 않는다. 최초 다운로드 크기를 측정한다.
- 핵심 자산을 모두 확보한 뒤에만 오프라인 준비 완료로 표시한다. 받기 실패·용량 부족이면 성공으로 표시하지 않으며, 정상 동작하던 기존 버전을 먼저 제거하지 않는다.
- 준비 완료 후 앱·Chrome을 닫고 인터넷을 끊은 상태에서 다시 켜도 Start, /intro, /all, /w/:id, 문서·티켓 직접 링크가 동작해야 한다. 폴더 재연결, 프로젝트·문서 탐색, 필터·정렬, 로컬 상대 리소스 열람, 사유·수동 지시 저장과 복구 검토도 로컬 파일 접근 권한 안에서 동작한다.
- 처음 방문한 브라우저의 완전한 오프라인 설치, 외부 AI/GitHub 접근, 미리 받지 않은 외부 이미지, OS가 아직 다운로드하지 않은 클라우드 파일은 보장하지 않는다. 앱을 설치했다고 로컬 폴더 권한이 무조건 영구 유지되는 것도 아니므로 기존 사용자 동작 기반 재허용 흐름을 유지한다.
- 로컬 원본 Markdown이나 폴더 경로를 HTTP 캐시·배포 정보에 넣지 않는다. 외부 이미지 허용 동작을 유지하되 오프라인 실패가 문서 전체를 막지 않게 한다. 원본 파일은 로컬 디스크에 있다는 원칙을 바꾸지 않는다.

### 3. 정상 업데이트와 적용 시점

- 서비스 워커 주소는 같은 출처의 `/sw.js`로 고정하고 범위도 유지한다. 파일명에 배포 해시를 넣지 않는다. JS/CSS 등 앱 자산에는 내용 해시를 사용한다.
- 제안 기본 주기: 온라인 앱 시작, 충분한 간격을 둔 화면 복귀·네트워크 복구, 화면을 사용 중일 때 약 30분 간격, 사용자의 수동 확인. 중복·실패 요청을 제한하고 숨겨진 창이나 종료된 앱의 정확한 실행 주기를 약속하지 않는다.
- 새 배포 발견, 자산 다운로드 중, 적용 준비 완료, 적용 보류, 조회 실패를 구분한다. 오프라인은 현재 설치된 버전을 계속 사용하며 최신 여부를 확인할 수 없는 상태다. 오프라인이라는 이유만으로 로컬 편집을 차단하지 않는다.
- 새 자산 준비가 끝나면 사용자가 업데이트를 적용하거나 나중으로 미룰 수 있게 한다. 모든 앱 창·탭이 닫힌 뒤 다음 시작에 준비된 버전이 자연스럽게 적용되는 동작도 지원한다.
- 즉시 적용 전 모든 관련 탭과 설치 앱의 미저장 입력·진행 중 저장을 확인하고, 확인과 전환 사이에 새로운 쓰기가 시작되지 않도록 막는다. 다른 창이 응답하지 않거나 입력·저장 중이면 기다리거나 그 창을 닫도록 안내한다. 워커 교체 이벤트만 보고 모든 창을 강제 새로고침하지 않는다.
- 입력 내용을 사용자 승인 없이 Markdown에 자동 저장하지 않는다. 보존 가능한 초안은 안전하게 복원하고, 그렇지 않으면 저장·취소를 선택하기 전 적용을 미룬다. 원본 저장은 close와 readback 검증까지 끝나야 한다.
- 새 워커와 이전 화면 코드가 섞인 상태에서 쓰기·저장소 변환이 시작되지 않도록 검증한다. 일반 배포에 무조건적인 skipWaiting과 clients.claim을 넣지 않는다.
- 다운로드가 실패하면 이전 버전으로 계속 사용한다. 전환이 끝나면 필요 없는 우리 앱의 구버전 자산만 정리한다. 종료하지 않은 구버전 화면이 필요로 하는 청크를 먼저 제거하지 않는다.
- Cloudflare CDN의 이전 파일 보존을 보장으로 사용하지 않는다. 설치된 배포의 자산 완결성, 누락 청크 대응, 부분 다운로드 실패와 다시 시도를 직접 검증한다.

### 4. 폴더 연결과 사용자 설정 보존

- 정상 업데이트·앱 복구·워커 퇴역은 같은 출처의 IndexedDB와 localStorage를 그대로 보존한다. 배포마다 DB 이름을 바꾸거나 storage.clear, deleteDatabase, 광범위한 Clear-Site-Data로 초기화하지 않는다.
- 앱 자산, 재생성 가능한 색인, 영구 사용자 설정, 미해결 복구 기록의 소유권을 구분한다. 기록이 불명확하면 삭제보다 보존을 우선한다. 캐시 청소는 명시된 우리 앱 전용 이름·범위에 한정한다.
- 저장 구조 버전은 앱 버전과 별도로 관리한다. 지원하는 이전 버전에서 여러 배포를 건너뛰어도 연결·정렬·설정을 변환하고, 실패 시 원본 상태를 유지한다. 복구 기록에 담긴 원문·예정 결과도 보존한다.
- 구버전 탭이 새 구조에 계속 쓰거나 이전 코드로 되돌린 배포가 새 구조를 잘못 수정하지 않도록 호환 검사를 둔다. 코드 복구는 호환되는 수정 배포를 기본으로 하고 저장소 구조의 무조건적인 다운그레이드를 금지한다.
- 저장 공간 지속성 요청의 허용 여부와 실제 부족 상황을 처리한다. 앱 설치나 지속 저장 요청으로 데이터가 영구 보존된다고 약속하지 않는다. 브라우저 설정에서 사용자가 직접 사이트 데이터를 지우면 재연결이 필요하다.
- 동일 브라우저 프로필·동일 출처 안의 보존과 다른 주소로의 이전은 구분한다. 정식 설치와 이후 업데이트는 kanban.giveit2.me를 유지한다. 기존 localhost나 임시 호스팅 주소 검증 환경의 연결·설정은 정식 주소로 자동 승계되지 않으며, 다른 브라우저 프로필 사이 자동 이전도 범위 밖이다.

### 5. 서비스 워커 복구와 폐기

- 서비스 워커의 실행 프로세스는 브라우저가 필요에 따라 종료·재시작한다. 관리 대상은 계속 등록된 워커와 그 요청 처리 동작이며, 등록 코드나 파일만 지우는 것을 철거 완료로 간주하지 않는다.
- 일반 개발 서버에서는 등록을 끈다. PWA 검증은 별도의 고정 테스트 출처와 브라우저 프로필을 사용하고 검증 후 그 앱 소유 등록·캐시만 정리한다. 같은 localhost의 다른 앱 등록을 일괄 해제하지 않는다.
- 고장 복구는 기존 `/sw.js`에 요청을 가로채지 않는 최소 워커를 배포하는 절차를 준비한다. 새 페이지 코드가 실행되지 않는 상황에서도 브라우저의 워커 업데이트로 전달되는 경로를 검증한다. 워커 무력화와 등록 해제, CacheStorage 삭제는 서로 다른 작업이다.
- 사용자용 앱 복구는 온라인에서 정상 배포를 다시 받을 수 있는지 확인한 뒤 진행한다. 오프라인에서 마지막 정상 앱 캐시를 지워 실행 불가능하게 만들지 않는다. 입력·저장·미해결 복구 기록 보호는 정상 업데이트와 동일하다.
- 앱 번들에 의존하지 않는 작은 복구 페이지를 두고 정상 워커에서 캐시·SPA fallback 대상에서 제외한다. 다만 모든 요청을 잘못 가로채는 고장 워커까지 복구 페이지 하나로 우회할 수 있다고 약속하지 않으며, 같은 워커 URL의 운영 복구 배포를 별도로 유지한다.
- 영구 폐기 시 새 등록을 중단하고 이전 주소에 퇴역용 워커를 계속 제공한다. 요청 가로채기를 중단한 뒤 해당 등록을 해제하고 소유 앱 캐시를 정리하되 사용자 DB·설정은 남긴다. 이미 제어 중인 창의 전환·종료까지 확인한다.
- 퇴역 워커를 온라인에서 받은 뒤 오프라인으로 활성화되는 경우에는 정리를 보류한다. 마지막 완결 앱을 임시 제공하고, 온라인 복귀 후 퇴역 배포를 확인하고 활성 작업 잠금이 없을 때 등록·소유 캐시만 정리한다.
- 장기간 접속하지 않은 사용자도 돌아와 정리될 수 있도록 배포 이력이 있는 워커 URL과 출처를 운영 목록으로 보존한다. 현재 계획에서 새 버전별 워커 URL은 만들지 않는다. 옛 도메인 운영을 종료하면 남은 등록을 원격으로 회수할 수 없다는 한계를 기록한다.
- 안전한 구버전으로 복구하는 경우에도 이미 바뀐 저장 구조와의 호환성을 확인한다. 워커 복구가 성공했다는 이유로 파일 저장 복구 기록을 자동 적용하거나 삭제하지 않는다.

### 6. 스킬·웹앱·문서 버전과 안내

- 웹앱 배포 버전/빌드 ID, 스킬 버전, Markdown 형식 버전, 브라우저 저장 구조 버전, 설치 manifest의 앱 식별자를 구분한다. 워커나 캐시의 해시는 호환성 판단을 대체하지 않는다.
- 앱 업데이트 확인은 정적 배포 정보와 현재 실행 버전을 비교하는 웹 코드로 구현한다. 워커는 선택된 배포를 받는 역할만 맡는다. Node API·알림 서버·상주 프로세스를 새로 추가하지 않는다.
- AKL-10~13의 배포 계약을 재사용해 동봉 스킬 버전과 읽기/수정 가능한 문서 형식을 안내한다. 앱을 업데이트해도 개인 설치 스킬은 그대로이며 그 버전을 자동 추정하거나 설치 폴더를 탐색하지 않는다. 계약 미완료 시 가짜 버전·호환 판정을 만들지 않는다.
- 미지원 문서 형식 처리와 안전한 스킬 설치는 기존 티켓의 책임이다. 스킬 업데이트는 사용자가 외부 AI/설치 도구에 요청하며 PWA나 서비스 워커가 대신 실행하지 않는다.
- 앱 정보에는 현재 실행 버전, 업데이트 확인/적용, 해당 배포의 실제 변경 사항과 앱 복구 진입점만 제공한다. 일반 화면에 로드맵·개발 진행률·검증 대기 문구를 붙이지 않는다. 사용자가 필요한 시점에만 오프라인 준비, 업데이트 보류 이유, 재연결 등 실제 상태를 설명한다.
- `/sw.js`, 최신 배포 정보와 복구 페이지는 오래된 HTTP 캐시·워커 캐시·SPA fallback에 갇히지 않게 처리한다. 버전 고정 자산과 최신 여부 확인 자료의 캐시 정책을 분리한다.
- 현재 CSP의 connect-src를 필요한 동일 출처 자산·배포 정보 조회가 가능하도록 최소 조정하고 워커 실행 범위도 명시한다. 로컬 문서·경로·사용자 입력을 서버에 전송하지 않으며 원격 스크립트를 실행하는 업데이트 구조를 만들지 않는다.

## 성공을 확인할 방법

- AKP-01: 실제 Chrome에서 설치·취소·재실행과 독립 창, manifest의 동일 앱 식별을 확인한다.
- AKP-02: 최초 온라인 준비 뒤 브라우저를 완전히 종료하고 실제 네트워크를 끈 상태에서 재실행한다. 미방문 경로·한글 글자·문서 탐색·저장·상대 이미지·스킬 자료를 확인하고 HTTP 문서 업로드가 없음을 검사한다.
- AKP-03: 이전 버전에서 업데이트 준비·거절·적용·다음 시작을 확인한다. 입력 중, 저장 중, 두 탭과 설치 창, 응답 없는 창, 네트워크 단절, 자산 404를 재현한다.
- AKP-04: 폴더 핸들·문서 ID·최근 프로젝트·순서·언어·필터·상세창 크기·복구 기록의 업데이트 전후 동등성을 확인한다. 브라우저 권한 재허용은 실제 OS 폴더로 검증하고 가짜 핸들 테스트와 구분한다.
- AKP-05: 잘못된 워커를 배포한 격리 환경에서 같은 URL의 복구·퇴역 워커로 정상 요청을 되찾고, 사용자 저장소를 남긴 채 등록·앱 캐시만 정리되는지 검증한다.
- AKP-06: 앞선 결과와 운영 복구 산출물을 묶어 출시 판단 기록을 만든다. 정적 preview와 Cloudflare의 kanban.giveit2.me 헤더·경로 검증을 구분하고 공개 배포·DNS 변경은 별도 승인 후 진행한다.
- 티켓은 구현·검증 증거에 따라 갱신한다. 계획 파일 작성과 형식 검사만으로 PWA 구현·실사용 검증을 완료 처리하지 않는다. AKP-03은 AKP-04의 보존·전환 보호를 연결한 뒤 완성한다.

## 참고 근거

2026-10-18에 확인한 공식 자료다. 아래 동작과 현재 앱의 실측 결과는 구분하며 실제 설치·복구 검증은 후속 티켓에서 수행한다.

- [MDN: 설치 조건과 manifest](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable): 설치와 서비스 워커는 별개이며 독립 창을 위한 manifest 정보를 정의한다.
- [MDN: Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API): 네트워크 요청·오프라인 캐시를 처리하는 이벤트 기반 워커다.
- [서비스 워커 생명주기](https://web.dev/articles/service-worker-lifecycle): 설치·대기·활성화, 같은 워커 URL 유지, 강제 전환의 혼합 버전 위험을 설명한다.
- [Workbox: 업데이트 안내와 적용](https://developer.chrome.com/docs/workbox/handling-service-worker-updates): 준비된 업데이트의 사용자 확인과 전환 예시다. 앱의 입력·여러 창 보호는 별도 구현이 필요하다.
- [Workbox: precaching](https://developer.chrome.com/docs/workbox/modules/workbox-precaching): 배포 자산의 revision과 설치·활성화 시 캐시 갱신을 제공한다.
- [Workbox: 고장 난 워커 제거](https://developer.chrome.com/docs/workbox/remove-buggy-service-workers): 같은 URL의 요청 비개입 워커와 광범위한 사이트 데이터 삭제의 위험을 설명한다.
- [MDN: 저장소 범위·수명](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria): 출처별 저장소 분리와 브라우저의 저장 공간 정책을 설명한다.
- [Cloudflare Pages: 정적 경로·캐시](https://developers.cloudflare.com/pages/configuration/serving-pages/): SPA fallback, 응답 헤더와 이전 자산 보존의 한계를 확인한다.
