# 문서 정리 성능과 저장 검증

2026-11-04, [AKD-19](25_alpha_kanban_team_documents_tickets.md#akd-19-문서가-많은-프로젝트의-정리-대기와-화면-멈춤-개선)의 로컬 검증 결과다. 문서 정리의 변환 규칙과 렌더러는 유지하고, 분석에 필요한 파일을 읽고 처리하는 경로를 개선했다.

## 변경한 동작

- 보드 목록 재구성과 진행률 계산을 거치지 않고 선택 문서를 직접 읽는다. 같은 검사 안에서 전체 본문을 두 번 읽거나 다른 파일의 브라우저 ID를 만들지 않는다.
- 선택 문서를 먼저 분석한다. ID 중복 확인에는 다른 문서의 완결된 헤더를 읽고, 삭제 후보 섹션이 있을 때만 참조 확인에 필요한 전체 Markdown을 읽는다. 긴 front matter나 헤더는 끝까지 읽으며 고정 길이에서 잘라 판정하지 않는다.
- 파일 읽기는 최대 6개씩 겹쳐 진행한다. 연결 경계·제외 폴더·파일 크기·발견 개수 제한을 유지한다.
- 참조 분석과 정리 결과 계산은 별도 Worker에서 수행한다. 미리보기 취소·문서 전환 시 작업을 종료하고 늦은 결과를 표시하지 않는다. Worker 실행 실패는 저장 없이 재시도할 수 있다.

화면용 Markdown 의존성이 Worker에서 `document`를 사용하던 시작 오류를 고쳤다. 배포 빌드는 Worker에만 같은 패키지의 DOM 없는 디코더를 사용한다. 개발 서버는 Worker와 의존성 최적화 경로를 공유하므로 이 디코더 하나에 같은 경로를 지정한다. 개발 서버의 실제 미리보기와 빌드된 Worker 실행을 각각 확인한다.

## 같은 파일로 측정한 결과

macOS의 기존 Chrome 156에서 생성한 실제 폴더를 선택했다. 합성 Markdown 503개, 총 4,824,877바이트이며 이 중 502개는 각각 20개 티켓을 포함한다. 운영 문서나 기존 앱의 연결 정보를 사용하지 않았다.

변경 전후 코드를 별도 실행 파일로 보존하고 동일한 `BrowserRepository.previewMigration` 호출을 각각 세 번 측정했다. 선택 문서의 최초 발견·목록 로딩은 미리 마쳤으며, 측정에는 선택 문서 읽기부터 최종 미리보기 반환까지 포함한다. UUID를 고정해 결과를 비교했다. 아래는 세 번의 중앙값이다.

| 측정 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 레거시 섹션 정리 미리보기 | 3,947ms | 2,101ms |
| ID·Owner만 보완하는 미리보기 | 2,249ms | 153ms |
| 섹션 정리 중 최대 프레임 간격 | 1,635ms | 18ms |
| 섹션 정리 중 50ms 초과 긴 작업 수 | 1 | 0 |
| 섹션 정리의 파일 읽기 횟수 | 1,006 | 503 |
| 섹션 정리의 읽은 바이트 | 9,649,754 | 4,824,877 |
| ID·Owner 보완의 읽은 바이트 | 9,649,754 | 2,061,808 |

레거시 정리는 약 47%, 메타데이터 보완은 약 93% 빨라졌다. 섹션 정리의 세 실행에서 관측한 가장 긴 프레임 간격은 변경 전 1,968ms, 변경 후 18ms였다. 메타데이터 보완은 전후 모두 긴 작업이 없었다. 헤더 보완도 ID 중복 확인을 위해 다른 파일을 열지만 전체 본문은 읽지 않는다.

여섯 쌍의 미리보기 JSON 해시가 모두 일치했다. 개발 서버와 배포 번들에서 Worker 시작을 확인했고, 실제 앱의 변경 전후 diff도 정상 표시됐다. 이 수치는 합성 문서에서의 미리보기 측정이며, 다른 프로젝트의 시간이나 저장 완료 시간을 보장하지 않는다. 파일 구성·크기·디스크·브라우저 상태에 따라 달라진다.

## 저장 안전과 렌더링

Apply는 미리보기 결과를 그대로 신뢰하지 않는다. 쓰기 스트림을 열기 전과 연 뒤에 파일·참조·ID·설정·연결 상태를 새로 읽어 확인한다. 원문 해시·수정 시각 검사, 문서 잠금, 영속 복구 사본, 저장 후 다시 읽기 검증을 유지했다. 미리보기의 빠른 읽기 경로가 이 두 검사를 대체하지 않는다.

실제 폴더에서 메타데이터 보완과 레거시 정리를 각각 적용했다. 선택한 두 파일만 바뀌었고 다른 501개는 SHA-256이 같았다. 정리 파일은 공용 변환기의 예상 바이트와 일치하고 실제 Ticket List 본문은 그대로였다. 보드의 20개 티켓과 제목·상태·진행률·우선순위·저장소·선행 티켓도 유지됐다. 삭제로 인한 원본 행 번호 변화는 정상이다.

자동 검사는 긴 헤더·BOM·UTF-8·청크 경계·동시 읽기 제한·취소, 새 참조와 중복 ID의 적용 전/스트림 개방 후 유입, 설정·폴더·연결 변경, 복구 사본 실패와 불확실한 저장을 포함한다. 빌드된 Worker를 DOM 없이 실행해 공용 엔진 결과와 비교하고, PWA 오프라인 자산 목록에 Worker가 포함되는 것도 확인했다. 이번 변경에서 Windows 실기나 새 오프라인 브라우저 세션은 별도로 실행하지 않았다.

## 재현

```sh
pnpm test:maintenance-worker
node scripts/prepare-maintenance-smoke.mjs before
# 개선 후 소스로 전환한 뒤:
node scripts/prepare-maintenance-smoke.mjs after
python3 -m http.server 5227 --bind 127.0.0.1 --directory output/playwright/maintenance-performance
```

`before`와 `after`는 현재 체크아웃을 해당 이름으로 빌드한다. 과거 코드를 자동으로 가져오지 않으므로 변경 전 소스에서 `before`를 준비하고 같은 코드를 두 이름으로 비교하지 않는다. 실행 파일·합성 폴더·해시 목록은 무시되는 `output/playwright/maintenance-performance`에 생성된다. 이미 만든 fixture는 재실행해도 덮어쓰지 않는다.

기존 앱과 다른 테스트 origin에서 각 실행 파일을 열고 `fixture` 폴더만 연결한다. 먼저 변경 전후의 `Run 3 samples per scenario`와 결과 다운로드를 완료한 후 저장 검증을 수행한다. 측정 중 탭을 전면에 두고 빌드·테스트를 병행하지 않는다. 저장 버튼은 마지막 미리보기의 선택 문서만 변경한다. 적용 이후의 fixture로 이전 측정과 비교하지 않는다. 원본 비교가 다시 필요하면 기존 증거를 보존하고 새로운 합성 fixture를 준비한다.
