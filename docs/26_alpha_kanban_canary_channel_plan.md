# Alpha Kanban 카나리 채널·공식 문서 계획

작성일: 2026-11-03
수정일: 2026-11-05

## 목표와 이유

정식 사용자에게 새 기능을 바로 배포하지 않고, 별도 주소와 설치 앱에서 카나리를 먼저 사용한다. 정식과 카나리는 같은 화면 배치와 사용법을 유지하되, 앱을 실행하기 전과 사용 중 모두 어느 쪽인지 쉽게 구분할 수 있어야 한다.

스킬 이름은 `implementation-ledger`를 유지한다. 각 앱이 제공하는 스킬 묶음을 비교·백업·확인 후 같은 설치 폴더에 교체할 수 있으며, 카나리를 사용한 뒤 정식 앱의 재설치 기능으로 정식 스킬로 돌아올 수 있게 한다.

README는 제품 이해와 빠른 시작, 릴리즈 노트는 변경 이력, 공식 docs는 계속 찾아보는 사용 설명을 맡는다. 설정 없이 시작하는 기본 사용부터 선택적인 팀 문서 관리까지 안내하며, 큰 업데이트의 소개 글에서 해당 사용 가이드로 연결한다.

2026-11-03 사용자 확인으로 아래의 시각 구분과 운영 구성을 모두 확정했다. 카나리는 보라색·플라스크·CANARY 표기, `kanban-canary.giveit2.me` 주소, `alpha-kanban-canary` Pages 프로젝트, `release/canary` 배포 브랜치를 사용한다. 정식과 카나리 UI를 공통 코드로 관리하고 빌드 설정으로 선택하는 규칙을 포함해 [구현 티켓](27_alpha_kanban_canary_channel_tickets.md)을 작성했다. 최초 요청의 범위는 문서 갱신이었으며 코드 변경·브랜치 생성·커밋·DNS 설정·배포는 포함하지 않았다.

같은 날 README 개선·상시 공식 docs·게시판형 릴리즈 페이지를 범위에 추가했다. 페이지 디자인은 OpenDesign Cloud를 거쳐 검토하고, 구현은 내부 컴포넌트를 가장 먼저 재사용하며 없는 요소만 shadcn에서 선별한다. 최초 작성에서는 이 순서와 완료 기준을 문서화했다.

이후 사용자 요청으로 AKC 구현에 착수한다. 선행 조건이 없는 AKC-01부터 진행하며, 스킬의 리뷰·QA 기능 확장은 이번 구현에 포함하지 않는다. 공개 배포·브랜치 승격은 AKC-05의 별도 승인 범위를 유지한다.

2026-11-05 사용자가 남은 검증부터 카나리 배포까지 진행하도록 승인했다. 확정된 카나리 브랜치·Pages 프로젝트·도메인을 대상으로 준비·배포·공개 검증을 수행한다. 정식 서비스의 복귀 경로는 별도로 확인하며 카나리 전체 기능을 정식에 자동 승격하지 않는다.

같은 날 사용자가 정식 서비스에는 복귀 기능만 별도로 배포하도록 승인했다. 기존 master 위의 최소 변경으로 비교·전체 백업·명시적 재설치를 제공하며 정식 스킬 묶음과 팀 기능은 바꾸지 않는다. 카나리 공개 및 정식 복귀 기능의 실제 배포 결과와 남은 실기 검증은 [운영 기록](deployment.md#2026-11-05-deployment-receipt)에 구분한다.

2026-11-04 후속 요청은 프로젝트 통합 검색, 설치 스킬 연결 UX, 문서·릴리즈 시안의 제품 코드 도입, 업데이트·문제 해결 예시 개선, 추가 기능의 화면별 살펴보기를 계획과 티켓에 반영하는 것이다. `implementation-ledger` 전용 폴더 드롭과 기존 폴더 선택을 함께 지원하는 방향을 확정했다. 같은 스킬의 여러 설치 위치 관리와 리뷰·QA 별도 스킬의 배포는 아래 열린 질문으로 구분한다. 최초 후속 요청은 계획·티켓 범위였으며, 이후 사용자가 검색 구현과 탐색 링크 교정 후 AKC-10 진행을 요청했다. 개인 스킬 변경·배포는 포함하지 않는다.

## 계획 작성 당시 확인한 상태

- 정식 주소는 `https://kanban.giveit2.me`다. `pwa.config.ts`의 앱 이름은 `Alpha Kanban`, manifest의 `id`·`start_url`·`scope`는 `/`, 서비스 워커 주소는 `/sw.js`다. [현재 배포 규약](deployment.md)
- 정식은 연두색 강조색과 `FolderKanban` 아이콘을 사용한다. 색상과 라이트/다크 값은 `styles.css`가 관리하며 `theme.ts`가 실제 화면 표면색에 맞춰 브라우저·PWA 창 색상을 갱신한다.
- `ReleaseInfo`에는 빌드·스킬 묶음·릴리즈 정보가 있지만 배포 채널 구분은 없다. `AK_PWA_MODE`는 정상·복구·퇴역 구분으로, 정식·카나리 구분과 별개다.
- 빌드 산출물은 `apps/web/dist-browser` 하나이며, 스킬 JSON·ZIP은 실행 중인 앱에 고정된다. 설치 요청문과 ZIP의 `INSTALL.txt`에는 정식 주소 및 master 안내가 남아 있다. 카나리 화면의 색상만 바꾸면 스킬 설치 경로가 정식으로 돌아갈 수 있다.
- [AKU-08](23_alpha_kanban_release_skill_tickets.md)은 로컬 구현·검증을 마쳤다. 미확인 설치본도 내용을 확인하고 동의하면 백업 후 앱 제공본으로 재설치한다. 일반/PWA 업데이트 보호와 대상 번들의 호환성 검사는 유지된다. 정식 서비스에 이 기능이 배포됐다는 증거는 아직 없다. [검증 범위](release_skill_validation.md)
- 저장소에는 Cloudflare의 실제 계정 설정을 확정할 자료가 없다. 기존 정식 프로젝트의 연결 방식·브랜치·환경 변수는 운영 설정을 읽어 확인할 항목이며, 여기서 확인한 것처럼 기록하지 않는다.
- 현재 README에는 설치·작업 흐름·소유자 설정·업데이트·복구 설명이 함께 들어 있다. `/intro`와 앱 내 사용 안내는 있지만 독립된 `/docs`·`/releases` 경로는 없다.
- 릴리즈 데이터는 `apps/web/releases.json`과 `pwa/releases.ts`의 논리 ID·순서·날짜·한영 요약을 사용한다. `ReleaseCenter`는 실행 중이거나 실제 적용 대기 중인 릴리즈를 팝업에 표시한다. 독립 페이지를 추가해도 이 대상 판정과 적용 승인은 유지해야 한다.

## 할 일과 선택한 방향

### 1. 채널별 주소와 배포를 분리한다

| 항목 | 정식 | 카나리 |
| --- | --- | --- |
| 앱 이름 | Alpha Kanban | Alpha Kanban Canary |
| 고정 주소 | `kanban.giveit2.me` 유지 | `kanban-canary.giveit2.me` |
| Pages 프로젝트 | 기존 프로젝트 유지 | `alpha-kanban-canary` 별도 프로젝트 |
| 배포 브랜치 | 기존 master 운영 유지 | `release/canary` 전용 브랜치 |
| 빌드 채널 | `stable` | `canary` |
| 설치 스킬 이름·호출 | `implementation-ledger` | `implementation-ledger` |

- 별도 Pages 프로젝트를 사용한다. 카나리 프로젝트의 배포 브랜치·환경 변수·도메인·복구 이력을 따로 관리하면서 소스와 빌드 코드는 공유한다. 각 프로젝트에서 지정한 브랜치만 배포하도록 설정하고, 임의 기능 브랜치를 지속 사용하는 카나리 주소로 연결하지 않는다. Cloudflare는 프로젝트별 배포 브랜치 및 자동 배포 제어를 제공한다. [공식 브랜치 설정](https://developers.cloudflare.com/pages/configuration/branch-build-controls/)
- 현재 작업 브랜치의 승인된 변경을 전용 카나리 브랜치에 반영하는 흐름으로 계획한다. 카나리 테스트 완료가 자동 master 병합이나 정식 배포를 뜻하지 않는다. 정식 승격 때는 검증한 변경을 검토하고 정식 설정으로 다시 빌드한다.
- 카나리 도메인을 Pages 프로젝트에 먼저 연결하고 DNS·TLS·실제 응답을 검증한다. DNS 레코드만 추가한 상태를 도메인 연결 완료로 보지 않는다. 기존 정식 DNS는 유지한다. [공식 사용자 도메인 설정](https://developers.cloudflare.com/pages/configuration/custom-domains/)
- 배포는 전용 브랜치에 승인된 커밋을 push하면 카나리 프로젝트가 빌드하는 방식을 사용한다. 이 계획 확정은 push나 자동 배포 설정 변경의 수행 요청이 아니다.

### 2. 같은 배치에서 색상·형태·이름을 함께 구분한다

**정식의 연두색·폴더 아이콘을 유지하고, 카나리는 보라색·플라스크 아이콘·CANARY 표기를 함께 사용한다.** 색상만 다르게 두면 작은 아이콘이나 흑백 화면에서 구분이 약하므로 형태와 이름도 함께 바꾼다.

| 구분 지점 | 정식 | 카나리 |
| --- | --- | --- |
| 주요 버튼·선택·포커스 강조 | 현재 연두색 | 보라색 |
| 앱·시작 메뉴·Dock 아이콘 | 연두 배경 + 폴더 형태 | 보라 배경 + 흰 플라스크 형태 |
| 브라우저 탭 아이콘 | 기존 아이콘 | 작은 크기에서도 구분되는 플라스크 실루엣 |
| 브라우저 탭 제목 | 기존 제목 규칙 | 제목 앞에 `[Canary]` 표시 |
| 화면 상단 | 기존 브랜드·프로젝트명 | 같은 위치에 플라스크 + `CANARY` 표식 |
| 상단·설치 앱 창 색상 | 기존 라이트/다크 표면 | 라이트는 옅은 보라, 다크는 어두운 보라 계열 표면 |
| 화면 배치·크기·조작 | 기존 구성 | 동일한 헤더·보드·사이드바·상세 배치 |

- 노란색·새 아이콘은 카나리라는 이름에는 잘 맞지만 현재의 연두와 가깝고 경고색과도 겹친다. 기존 연두에 작은 `C`만 붙이는 안은 앱 전환 중 식별력이 약하다. 보라색과 플라스크는 그 두 문제를 피하기 위해 선택했다.
- 플라스크는 기존 Lucide 계열의 선 굵기와 형태를 사용한다. 앱 아이콘에서 쓰는 굵은 형태와 화면 안의 작은 아이콘을 같은 모티프로 맞춘다. 이모지나 작은 글자 하나에 식별을 의존하지 않는다.
- 시작·프로젝트·전체 티켓·소개 화면뿐 아니라 전체 화면 티켓 상세, 업데이트·스킬 교체 화면에서도 채널이 보이게 한다. 기존 제목 줄과 아이콘 영역을 활용하며 카나리만 별도의 탐색 메뉴나 상시 설명 배너를 추가하지 않는다.
- `styles.css` 안에서 채널별로 기존 의미 토큰을 덮어쓴다. 컴포넌트마다 보라색을 직접 넣거나 별도 디자인 체계를 만들지 않는다. 업무 상태 점·오류·경고·성공 색상과 문서 본문의 의미는 채널 때문에 바꾸지 않는다. P1 뱃지와 진행률 막대는 기존 primary 테마 토큰을 유지하여 카나리에서 보라색으로 표시한다.
- 상단의 실제 배경과 `theme-color`를 맞춘다. 하나의 meta 태그, 현재 테마 선택·복원, 라이트/다크 전환 규칙을 유지한다. 구현 시 관련 `AGENTS.md` 규약도 함께 갱신한다.
- 정확한 색상 값과 아이콘 크기는 같은 화면을 라이트/다크·좁은 폭으로 비교한 뒤 결정한다. 정식의 기존 색상 값과 레이아웃은 기준으로 유지한다.

### 3. 빌드부터 업데이트까지 채널을 고정한다

- 빌드 설정 `AK_RELEASE_CHANNEL=stable|canary` 하나가 채널, 정규 주소, 앱 이름, 아이콘, 릴리즈 기록, 설치 안내 주소를 결정한다. 정식 Pages 프로젝트에는 `stable`, 카나리 프로젝트에는 `canary`를 고정한다. 로컬 비교 검증에서도 같은 설정을 명시해서 사용한다. URL 쿼리나 localStorage 설정으로 이미 설치된 앱의 채널을 바꾸지 않는다.
- 정식·카나리의 색상·아이콘·브랜드 정의와 이를 선택하는 코드 모두 master에 함께 머지한다. 활성 채널을 소스에서 바꾸는 커밋을 브랜치마다 유지하지 않는다. 브랜치는 배포할 기능의 버전을 고르고, 배포 프로젝트의 빌드 설정은 그 버전을 어느 채널로 제공할지 결정한다.
- 공통 채널 설정을 앱 브랜드 컴포넌트, CSS 토큰 선택, manifest·favicon·PWA 아이콘 생성과 설치 안내가 함께 사용한다. 각 화면에서 브랜치명·호스트명으로 제각각 채널을 추측하거나 서로 다른 조건으로 색상과 이름을 선택하지 않는다.
- 승격은 검증한 변경을 master에 머지한 뒤 `stable` 설정으로 새로 빌드하는 과정이다. 카나리 산출물을 정식 프로젝트로 복사하지 않고, 머지할 때 카나리 스타일·아이콘 코드를 제거하거나 되돌리는 절차도 만들지 않는다.
- 개발 기본값은 현재 정식 동작을 유지한다. 배포 빌드는 브랜치·대상 프로젝트·채널 설정이 맞지 않거나 알 수 없는 채널 값이면 실패시킨다. 채널은 앱 build ID 계산에도 포함한다.
- `ReleaseInfo`·서비스 워커의 배포 정보·업데이트 비교에 채널을 연결한다. 채널 필드가 없는 기존 정식 릴리즈는 정식에 한해 호환 처리한다. 카나리는 명시적 채널 정보가 필요하고 다른 채널의 대기 워커·릴리즈는 적용하지 않는다.
- 정식의 manifest ID·scope·start URL과 `/sw.js`는 유지한다. 카나리는 자신의 고정 origin에서 `/`·`/sw.js`를 사용하고 앱 이름·아이콘을 다르게 제공한다. manifest의 상대 ID는 start URL의 origin을 기준으로 해석되므로 별도 origin의 앱으로 구분할 수 있으며, 실제 동시 설치도 검증한다. [manifest ID 규칙](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/id)
- 정식 릴리즈 이력은 보존하고 카나리 이력은 별도로 관리한다. 반복 빌드마다 사용자 알림을 만들지 않으며, 공개할 변경 단위의 설명과 build ID를 구분한다. 카나리 내용이 정식 릴리즈 노트에 자동으로 섞이지 않게 한다.
- `dist-browser` 경로는 유지하되 두 채널을 별도 checkout 또는 빌드 디렉터리에서 생성한다. 생성 스킬 파일·manifest·아이콘·워커가 이전 채널의 산출물과 섞이지 않도록 각 빌드를 완결하고 검사한다.
- 업데이트 승인·초안 보호·다중 창 조정·오프라인 캐시 무결성·복구·퇴역 절차는 두 채널에서 동일하게 유지한다. 카나리라는 이유로 강제 새로고침이나 무확인 적용을 허용하지 않는다.

### 4. 스킬 이름은 유지하고, 제공하는 묶음과 교체 대상은 분명히 한다

- `implementation-ledger-canary`라는 별도 스킬은 만들지 않는다. 카나리 앱도 같은 이름·호출 방식의 스킬을 제공한다. 한 설치 폴더를 교체하면 그 폴더를 사용하는 다른 프로젝트에도 영향이 있다는 점은 교체 확인 화면에서 짧게 안내한다.
- 설치 요청문, 업데이트 요청문, ZIP의 `INSTALL.txt`, 설치 완료 후 등록 링크가 현재 채널의 고정된 묶음·주소를 가리키도록 한다. 카나리에서 복사한 설치 요청이 master 최신 스킬을 받아 오는 동작은 막는다. 최초 설치는 기존처럼 외부 agent가 수행한다.
- 앱은 자신의 빌드에 고정된 JSON·ZIP·SHA-256을 사용한다. 스킬 묶음 ID는 내용 해시로 유지하므로 실제 내용이 같다면 두 채널의 묶음 ID도 같을 수 있다. 채널을 새로운 스킬 의미 버전이나 문서 형식 버전으로 취급하지 않는다.
- 스킬 교체 화면에서 `정식 제공 스킬` 또는 `카나리 제공 스킬`과 실제 변경 내용을 함께 표시한다. 파일 비교 없이 설치본의 출처를 카나리라고 단정하지 않는다.
- 일반·PWA 업데이트와 재설치의 파일 비교는 문서 정리와 같은 CodeDiff를 사용한다. 추가·삭제 줄을 색상과 기호로 구분하고, 긴 문맥은 펼쳐 읽으며 좁은 화면에서는 한 열로 표시한다. 대화상자 본문만 스크롤하고 제목과 닫기 버튼은 유지한다.
- 일반 업데이트와 PWA 결합 교체는 기존 공식 스냅샷·호환성·확인 조건을 유지한다. 카나리 빌드라는 이유만으로 알려진 공식 스냅샷 목록에 추가하거나 호환성을 승인하지 않는다. 미확인 설치본의 명시적 재설치는 AKU-08을 사용하며 대상 배포본의 호환성 미확인은 계속 차단한다.
- 정식으로 돌아올 때는 카나리 앱과 해당 스킬을 쓰는 작업을 마친 뒤 정식 앱에서 같은 설치 폴더를 등록·비교하고, 현재 설치본을 새로 백업한 다음 정식 제공본으로 재설치한다. 정식 앱에 카나리 도메인의 백업이 있어야 하는 것은 아니다.
- **카나리 스킬을 실제 사용자의 설치 폴더에 배포하기 전**, 정식 서비스에서도 AKU-08 복귀 경로가 제공되는지 확인한다. 현재 로컬 완료만으로 이 조건을 충족했다고 하지 않는다. 그 전의 구현 검증은 스킬 복사본에서 수행한다.
- 스킬을 되돌려도 카나리가 변경한 문서나 개인 설정을 자동으로 되돌리지는 않는다. 기존 문서 하위호환 규칙과 명시적 문서 정리 절차를 유지한다.

AKC-10은 기존 교체 엔진을 유지하면서 최초 연결 절차를 개선한다.

- 연결 목적은 앱 업데이트 때 사용 중인 릿저 스킬도 함께 맞출 수 있게 하는 것이다. 등록·권한 허용은 파일 교체가 아니며, 업데이트별 변경 비교·명시적 동의·전체 백업·현재 앱에 고정된 배포본 검증과 복구 규칙을 유지한다.
- 사용자는 설치된 `implementation-ledger` 폴더 자체를 드롭하거나 기존 폴더 선택 버튼으로 연결한다. 드롭은 해당 디렉터리 핸들을 받는 경로이고, 필요한 쓰기 권한은 명시적 사용자 동작으로 확인한다. 상위 `skills`·홈 폴더를 요구하거나 다른 스킬을 자동 탐색하지 않는다. 폴더 안의 `SKILL.md`와 기존 설치본 검사로 릿저인지 확인하며, 폴더 이름이나 외부 AI 도구의 기본 경로만으로 정답을 판단하지 않는다.
- 설치 안내는 외부 AI가 실제 설치 위치를 확인해 알려주는 흐름과 이어진다. 지원하는 환경에서는 Finder/탐색기로 해당 폴더를 여는 안내를 제공하고, 폴더 선택을 쓸 때는 경로 이동·붙여넣기 방법을 행동 지점에서 설명한다. 웹이 임의의 절대경로를 바로 열거나 경로 텍스트만으로 파일 권한을 얻는 것처럼 표현하지 않는다. 다른 AI 도구의 지원·인식 여부는 검증 전 확정하지 않는다.
- 드롭 미지원, 파일만 드롭, 상위 폴더·다른 스킬·잘못된 설치본 선택, 권한 거부·취소는 기존 연결과 파일을 그대로 두고 필요한 다음 행동을 알려준다. 연결 완료·재사용·권한 재요청·연결 변경/해제를 구분한다. 드롭 지원은 실제 macOS·Windows Chrome의 스모크 폴더로 검증하며 가짜 핸들 검사만으로 완료하지 않는다.
- 최초 연결·연결됨·권한 만료·잘못된 대상 상태를 Local Codex에서 검토하고 기존 내부 컴포넌트로 구현한다. 업데이트·문제 해결 예시와 화면별 투어는 이 실제 연결 흐름을 기준으로 후속 작성한다. 여러 폴더 동시 등록·일괄 갱신은 아직 확정하지 않는다.

여러 에이전트의 같은 릿저 설치본과 리뷰·QA 같은 별도 스킬은 서로 다른 확장이다. 다중 폴더 드롭만으로 배포 대상을 알아낼 수 있는 것은 아니다. 별도 스킬을 지원한다면 `SKILL.md`의 이름은 종류를 식별할 후보이고, 어떤 공식 배포본으로 갱신할지는 관리 대상 스킬과 검증된 배포본의 대응 규칙이 필요하다. 폴더명·스킬 이름만으로 미확인 파일을 덮어쓰지 않는다. 구체적인 식별자·배포 목록 형식은 아직 채택하지 않으며, 이 미결정은 확정된 단일 릿저 연결 UX의 선행 조건이 아니다.

### 5. 브라우저 저장소 분리와 실제 파일 공유를 구분한다

- 서로 다른 origin은 폴더 연결·문서 URL 식별자·최근 목록·필터·테마·백업을 각각 저장한다. 카나리에서는 사용자가 필요한 폴더를 새로 연결한다. 기존 키와 DB 이름을 채널 때문에 일괄 변경하거나 정식 데이터를 초기화할 필요는 없다. [브라우저 저장소의 origin 경계](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria#how_do_browsers_separate_data_from_different_websites)
- 다른 채널로 이동하는 링크는 해당 앱의 시작 화면을 연다. 문서의 브라우저 내부 ID나 개인 경로를 상대 앱 URL로 옮기지 않고, 연결·백업 자동 복사도 제공하지 않는다.
- 같은 로컬 문서나 스킬 폴더를 두 앱에 연결하면 실제 파일은 하나다. 별도 앱이라는 이유로 테스트용 복사본이 생기거나 실제 파일 수정이 격리되는 것은 아니다.
- Web Locks는 origin 사이에서 공유되지 않는다. 기존 해시·수정시각 검사와 저장 후 검증은 유지하되, 두 채널의 동시 쓰기를 배제하는 전역 잠금으로 설명하지 않는다. 동일한 스킬 교체는 다른 채널의 작업을 끝낸 뒤 순서대로 수행하며, 최초 검증은 별도 스모크 폴더를 사용한다. [Web Locks 범위](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API#concepts_and_usage)
- 백업은 작업한 채널의 앱에서 확인·복원한다. 카나리 중단·복구도 그 origin의 기존 보존 규칙을 따르고, 정식 백업이나 원본 파일을 지우지 않는다.

### 6. README·공식 docs·릴리즈 노트의 역할을 나눈다

| 표면 | 역할 | 포함할 내용 |
| --- | --- | --- |
| 한국어·영어 README | 제품 이해와 빠른 시작 | 한 문장 소개, 공개용 예시 화면, 대화→계획·티켓→구현·검증 흐름, 설치·첫 사용·업데이트 진입 |
| `/docs`와 문서별 주소 | 현재 제공하는 기능의 상시 사용 설명 | 기본 사용부터 선택적 팀 기능, 작업별 안내, 설정 명세, 문제 해결 |
| `/releases`와 릴리즈별 주소 | 무엇이 언제 바뀌었는지 확인 | 날짜순 제목·요약 목록, 개별 상세 글, 큰 변경의 화면·예시와 관련 docs 링크 |

- README는 implementation-ledger 설치·사용·업데이트를 중심으로 정돈하고 웹 뷰어는 선택적인 동반 도구로 소개한다. 긴 설정·복구 설명은 공식 docs로 연결하되 첫 사용에 필요한 설치 요청과 확인 절차는 쉽게 찾을 수 있게 한다. 한영판의 구성과 주요 링크를 맞춘다.
- 로컬 실행·빌드·테스트는 `CONTRIBUTING.md`, 배포 운영은 `docs/deployment.md`에 유지한다. 제품 문서에는 사용자가 기능을 이해하고 실행하는 데 필요한 내용만 싣는다. 개인 프로젝트·로컬 경로·무시되는 캡처 대신 공개용 예시와 저장소에서 관리하는 자료를 사용한다.
- 공식 docs는 큰 업데이트 때만 쓰는 설명문이 아니라 기본 사용까지 포함하는 상시 문서다. 시작하기, 기본 사용, 팀 문서 관리, 문서 관리, 로컬 링크, 설정 참고, 업데이트와 문제 해결을 첫 목차로 삼는다. 작업별 따라 하기와 정확한 설정 명세를 연결하며 같은 설명을 여러 페이지에 복제하지 않는다.
- 설정 없이 작성·수정하는 경로를 먼저 안내한다. 소유자 구분은 선택 기능이며 `.ak.config`의 공유 정책과 `.ak.user`의 개인 사용자, 커밋 여부, 기본값·우선순위·workspace 연결·linked worktree 상속을 실제 판정 도구와 맞춘다. Owner를 권한이나 다른 사람의 작업 실행 허가로 설명하지 않는다.
- 문서 이동·인수인계·PC 경로 보정은 CLI의 명시적 작업이고, 브라우저의 로컬 링크 연결은 원본 Markdown을 바꾸지 않는다는 차이를 사례로 설명한다. ID 발급·문서 정리는 명시적인 기능이며 기존 문서의 렌더링·기본 사용을 막는 필수 절차로 안내하지 않는다.
- 공개 문서만 저장소에서 명시적으로 선택해 앱과 함께 빌드한다. 내부 플랜·티켓·검증 기록이나 사용자의 로컬 문서를 자동 공개하거나 검색 대상으로 삼지 않는다. 정식 docs는 정식 빌드의 기능, 카나리 docs는 카나리 빌드의 기능을 설명하고 기본값·예시·검색 결과도 같은 기준을 따른다. 배포되지 않은 기능을 정식 사용법으로 노출하지 않는다.
- docs는 왼쪽 탐색, 본문, 오른쪽 현재 페이지 목차를 기본으로 검색·코드 복사·문단별 링크를 제공한다. 페이지 전체가 스크롤되고 상단 헤더·왼쪽 탐색·오른쪽 목차는 sticky로 남는다. 본문 안쪽 스크롤을 두지 않으며 넘치는 탐색 목록만 자체 스크롤을 쓴다. 한영 목차를 맞추고 좁은 화면의 탐색과 키보드 사용, 라이트/다크를 함께 설계한다. 앱 도움말·README·릴리즈 글에서 연결하며 기존 투어·가이드와 보드의 입력 초안 보존을 유지한다.
- 메인(`/`), 소개(`/about`), 공식 문서와 릴리즈는 기본 56px인 공통 헤더를 쓴다. 이동 링크는 `칸반 → 공식 문서 → 릴리즈 → 소개`로 통일하고 좁은 화면에서는 같은 메뉴로 접는다. 언어·테마 뒤에 구분선을 두고 메인의 스킬 업데이트·도움말·전체 티켓·앱 관리, 공개 문서의 가이드 검색을 화면별 도구로 둔다. 모바일에서는 공통 두 줄 배치를 쓰며 필요한 도구를 잘라내지 않는다. 푸터에는 제품명과 GitHub만 남기고 설치·업데이트 안내는 해당 본문에 둔다. 공통 헤더는 상단에 고정하며 본문 앵커는 실제 헤더 높이를 피해서 표시한다. 문서 루트와 내부 스크롤 영역은 `scrollbar-gutter: stable`로 자리를 유지한다. 기존 `/intro`는 쿼리와 `#skill`·`#updates`를 유지한 채 `/about`으로 히스토리를 대체하며 자동 이동한다. 메뉴·README·스킬 안내는 `/about`을 사용하고 과거 스킬의 업데이트 주소는 계속 검증 가능해야 한다. 프로젝트 보드와 전체 티켓 헤더는 이번 정리 범위에서 제외한다.
- AKC-07은 보관 중인 공개 docs 시안을 실제 앱의 경로·공통 컴포넌트·한영 콘텐츠로 통합한다. 문서 관리와 로컬 링크 등은 기능의 목적·조건 설명 뒤에 캡처 또는 조작형 예시를 둔다. 업데이트·문제 해결 예시는 AKC-10의 실제 폴더 드롭/선택·권한·연결 상태·변경 비교·적용·백업 복원 흐름으로 교체하며, 시안의 추상적인 조작을 그대로 제품에 옮기지 않는다.
- AKD-21 프로젝트 통합 검색의 대상·문서 묶음 결과·일치 티켓 보드·문서 일치 위치 이동과 전체 보기/해제 동작을 실제 화면에 맞춰 안내한다. 공개 docs 검색은 공개 안내 콘텐츠만, 프로젝트 검색은 허용된 로컬 문서만 대상으로 하며 둘을 혼동시키지 않는다.
- 릴리즈 페이지는 날짜순 목록과 공유 가능한 상세 주소를 제공한다. 작은 수정은 간단히, 큰 업데이트는 무엇이 달라지고 기존 사용자가 무엇을 하면 되는지 화면·예시로 설명한다. 당시의 변경 사실은 릴리즈 글에 남기고 현재 사용법은 docs에서 갱신한다.
- 기존 릴리즈 기록을 확장·참조해 팝업과 페이지의 논리 ID·날짜·요약을 함께 관리한다. 정식·카나리 기본 목록을 분리하고 해당 빌드의 공개 이력까지만 보여준다. 과거 요약만 있는 릴리즈도 읽을 수 있어야 하며, 임의의 의미 버전이나 과거 배포 사실을 만들지 않는다. 상세 본문 형식은 공개 콘텐츠 구조와 함께 정하되 별도 서버나 CMS를 도입하지 않는다.
- 업데이트 팝업은 요약과 현재 적용 동작을 유지하고 전체 이력·관련 가이드로 연결한다. 페이지 읽기만으로 업데이트 동의·미열람 릴리즈의 일괄 읽음·초기 알림 기준을 변경하지 않는다. 대기 워커의 안내를 최신 서버 글로 대체하지 않으며 현재 빌드에 없는 상세는 검증된 팝업 요약으로 읽을 수 있게 한다.
- `/docs`·`/releases`는 폴더 연결 없이 열 수 있는 공개 페이지다. 직접 방문·새로고침으로 작업 폴더를 스캔하거나 권한을 요청하지 않고 마지막 보드로 자동 이동하지 않는다. 공개 콘텐츠·검색 자산은 해당 앱 빌드에 포함해 오프라인 준비 후에도 같은 내용과 링크를 읽을 수 있게 한다.

### 7. 페이지 디자인을 먼저 검토하고 내부 컴포넌트로 구현한다

- 설치된 디자인 프로그램의 Local Codex에 기존 앱의 의미 토큰·글꼴·채널 구분과 재사용 가능한 컴포넌트를 기준으로 전달한다. docs 본문·탐색·검색과 릴리즈 목록·상세를 공개용 예시 콘텐츠로 설계하고 한영·라이트/다크·데스크톱/좁은 화면의 주요 상태를 검토한 뒤 페이지 구현으로 넘어간다. 구체적인 화면·내용·검토 기준은 [AKC-06 디자인 브리프](design/akc-06-public-docs/brief.md)에 둔다.
- 컴포넌트 선택 순서는 기존 내부 컴포넌트 재사용, 기존 공통 래퍼의 필요한 확장, 내부에 없는 요소의 shadcn 선별 도입이다. 새로 채택한 요소도 `components/ui`와 기존 `styles.css` 토큰을 따르며 별도 색상·반경·글꼴 체계를 만들지 않는다. 디자인 산출물의 코드를 그대로 제품 소스로 교체하지 않는다.
- 디자인 단계에서 각 요소의 기존 컴포넌트 대응과 부족한 요소만 정리한다. README는 GitHub Markdown의 표현 범위 안에서 같은 브랜드·공개 예시를 활용한다. 기존 보드·소개·설치 화면 전체의 재설계로 확장하지 않는다.

### 9. 추가된 기능을 실제 화면의 살펴보기로 안내한다

- AKC-11은 기존 Driver.js와 Help 진입을 재사용한다. 프로젝트 통합 검색·일치 티켓과 전체 보기, 전체보드 검색·소유자 필터, 경로 소유자와 문서 속성, 문서 정리 미리보기·적용, 로컬 링크 연결·연결 문서 페이지, 스킬 연결·업데이트·복원, 공식 docs·릴리즈의 탐색을 각 화면의 맥락에 맞게 나눈다.
- 보드·공개 페이지는 해당 화면에서, 문서 정리·연결·스킬 관리는 사용자가 연 대화상자 안에서 필요한 부분만 안내한다. 한 투어가 다른 화면을 강제로 열거나 권한 창을 띄우지 않는다. OS 폴더 선택·권한 창은 웹 투어로 조작하지 않고 앞 단계의 안내와 공식 문서 예시로 설명한다.
- 투어는 현재 존재하고 보이는 제어 요소만 대상으로 삼으며 필터·빈 상태·미연결·좁은 화면에서도 없는 단계를 건너뛴다. 모달 안의 초점 경계를 유지하고 언어·테마·화면 변경, 종료·건너뛰기 후 기존 초안·선택·스크롤을 훼손하지 않는다. 실제 폴더 연결·문서 저장·스킬 교체를 투어 동작으로 수행하지 않는다.
- 기존 완료·건너뜀·초대 기록을 유지하고 새로운 안내를 이유로 모든 사용자에게 투어를 다시 강제하지 않는다. 수동 재실행과 화면별 종료 상태를 제공하며, 투어와 공개 예시의 버튼명·순서·실제 결과를 함께 검증한다.

## 성공을 확인할 방법

- 같은 checkout 내용으로 채널만 달리 빌드했을 때 앱 식별·아이콘·주소·릴리즈 정보는 의도대로 다르고, 레이아웃과 기능 흐름은 같다. 기본 정식 빌드는 기존 주소·설치 ID·저장 키를 유지한다.
- 머지 후 동일한 소스로 `stable`과 `canary`를 각각 빌드하는 회귀 검증을 둔다. 정식에서 카나리 이름·플라스크·보라색·카나리 주소가 선택되거나 카나리의 표식이 누락되면 실패한다. 공통 코드에 두 채널 정의가 존재하는 것은 정상이며, 실제 렌더링·선택된 자산·배포 메타데이터를 검증한다.
- 정식·카나리 프로젝트의 채널 설정을 뒤바꾼 경우와 카나리 산출물을 정식에 재사용하려는 경우를 검사한다. 대상 프로젝트·브랜치·채널 불일치는 공개 전에 거절한다.
- 브라우저 탭·Dock 또는 시작 메뉴·설치 창·모든 주요 화면·전체 화면 상세에서 이름이나 형태만으로도 카나리를 식별할 수 있다. 라이트/다크, 한영, 좁은 화면, 작은 favicon에서 확인한다. 색상 값·대비는 이때 확정한다.
- 정식과 카나리를 동시에 설치하고 각 앱을 새로고침·종료·재시작·오프라인 실행한다. 연결·선택·테마·백업·읽은 릴리즈 기록은 각 앱에서 유지되며 상대 앱의 설치를 대체하지 않는다.
- 카나리 A→B 업데이트와 실패·복구·퇴역을 시험하는 동안 정식의 워커·자산·연결·백업이 바뀌지 않는다. 초안·저장 중 업데이트 보호와 오래된 정식 릴리즈의 채널 호환도 검증한다.
- 스킬 설치 요청·완료 링크·JSON·ZIP·오프라인 다운로드가 실행 중인 채널의 같은 묶음을 사용한다. 잘못된 채널·누락된 자산·해시 불일치는 교체를 시작하지 않는다.
- 스킬 복사본에서 정식→카나리→정식 재설치와 각 origin의 백업 복원을 순서대로 수행한다. 개인 수정·추가 파일·외부 변경·부분 실패를 포함하고, 다른 채널이 파일을 바꾼 뒤 오래된 비교 결과로 적용하면 거절되는지 확인한다. 이 결과를 서로 다른 origin의 동시 쓰기 안전성 증거로 확대하지 않는다.
- 별도 로컬 출처와 가짜 핸들 검증, 실제 OS 폴더 검증, 실제 공개 도메인 검증을 나누어 기록한다. macOS·Windows 설치 이름과 아이콘 구분은 각 실기기 결과로 확인한다.
- Local Codex 설계와 구현 화면을 비교하고 내부 컴포넌트 우선 적용, 필요한 shadcn 요소만 채택했는지 확인한다. docs·릴리즈의 한영·라이트/다크·반응형·키보드 탐색을 확인한다.
- 폴더를 연결하지 않은 새 세션에서 docs·릴리즈의 직접 주소·문단 링크·새로고침·검색·코드 복사를 확인한다. 이 방문이 폴더 권한이나 문서 쓰기를 시작하지 않으며, 기존 보드의 초안·연결·업데이트 승인 흐름이 유지된다.
- 무설정 기본 사용과 선택적 소유자 설정을 별도 예시 프로젝트에서 안내대로 따라간다. CLI 이동·경로 보정과 브라우저 링크 연결의 파일 변경 범위, 설정 우선순위·worktree 상속을 구현 계약과 대조한다.
- README 두 언어의 설치·첫 사용·업데이트 진입, 이미지·공개 링크·앵커를 검사한다. 채널별 docs·검색·릴리즈 목록에 다른 채널 전용 내용과 내부 작업 기록이 섞이지 않는지 확인한다. 과거 요약만 있는 릴리즈와 현재 빌드에 없는 대기 릴리즈 상세도 처리한다.
- 공개 후 두 고정 주소의 manifest·`release.json`·`sw.js`·스킬 JSON/ZIP·오프라인 자산 및 HTTPS·MIME·캐시 헤더를 확인한다. DNS 설정이나 빌드 성공만으로 배포 완료라고 하지 않는다.
- 승인된 배포의 `/docs`·`/releases` 및 상세·문단 주소를 직접 열고 실제 채널·언어·콘텐츠와 준비 완료 후 오프라인 읽기를 확인한다. 아직 배포하지 않은 정식 신규 페이지를 공개 검증 완료로 기록하지 않는다.
- 드롭/폴더 선택으로 같은 스모크 릿저를 연결하고 권한 거부·취소·재시작·재허용·연결 변경을 확인한다. 잘못된 폴더와 여러 항목 드롭이 암묵적으로 기존 연결을 바꾸지 않고, 등록만으로 스킬·문서를 쓰지 않는지 확인한다. 기존 업데이트별 확인·고정 배포본·백업·복구 검증을 재사용한다.
- 문서·릴리즈 시안이 실제 앱 경로와 공통 컴포넌트에 통합됐는지 확인하고, 업데이트 예시는 개선된 연결 화면을 직접 따라가며 대조한다. 화면별 투어의 한영·라이트/다크·좁은 화면·키보드·모달 초점과 기존 완료 기록·초안 보존을 검증한다.

## 확인·결정이 필요한 사항

- 같은 implementation-ledger를 여러 에이전트·전역/프로젝트 위치에 따로 설치한 경우 여러 설치 폴더를 동시에 등록·관리할 것인가? 현재 확정 범위는 전용 폴더 하나의 드롭 또는 선택이다. 확장한다면 연결 구분·중복 설치 위치·대상별 업데이트 선택과 실패/복구 범위를 정해야 하며, 확정된 단일 연결 UX의 선행 조건으로 두지 않는다.
- 리뷰·QA 기능을 implementation-ledger 안에 둘 것인가, 독립된 스킬 폴더로 배포할 것인가? 별도 스킬을 택하면 다중 드롭과 별개로 스킬 종류·공식 배포본·설치 위치의 대응 및 지원 범위를 정해야 한다. 스킬 이름만으로 공식 설치본이라고 신뢰하거나 다른 묶음으로 덮어쓰지 않는 원칙만 유지하며 구체적 배포 형식은 보류한다.

## 제외 범위

- 명시적으로 승인하지 않은 브랜치 변경, 커밋·푸시·DNS 수정·공개 배포. 최초 문서 작성 이후 승인된 AKC 구현은 위 순서로 진행한다.
- 앱 내 채널 전환 토글, 두 origin의 연결·설정·백업 동기화, 사용자 파일의 자동 복사·이동.
- 별도 이름의 카나리 스킬, 무확인 스킬 교체, 호환성 검사 우회, 자동 문서 변환·되돌리기.
- origin을 넘는 전역 파일 잠금이나 로컬 서버·agent 실행 기능.
- 채널을 위한 별도 보드 레이아웃·내비게이션, 장황한 실험 경고, 구현 진행 상황을 제품 화면에 노출하는 안내.
- 고객 계정·권한·과금·테스트 참여자 관리 시스템, 정식 채널의 자동 승격.
- 문서 전용 서버·CMS·댓글·게시글 작성 계정, 과거 모든 앱 버전을 선택하는 문서 시스템, 내부 작업 기록의 자동 공개, 기존 보드·소개 화면 전체 재설계.
- 미확정인 여러 설치 폴더 동시 등록·일괄 교체, 리뷰·QA 스킬 분리와 다중 스킬 배포 엔진. AKC-10의 단일 릿저 폴더 드롭/선택과 기존 보호 개선은 이 보류 사항에 포함하지 않는다.
